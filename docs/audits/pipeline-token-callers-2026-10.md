## How to read the table

- Scope: `fleet` means a workflow propagated by `.mergepath-sync.yml` and byte-identical on all eight repos, so the row runs eight times, each with that repo's own secrets. `hub` means mergepath only. `fiveacross` means a copy that exists only in that consumer.
- Executed ref: where the workflow definition and the code it runs come from. `refs/pull/N/merge` is candidate-controlled for a same-repo branch.
- Token: the expression the caller resolves. "CI actor" is shorthand for `secrets.CI_ACTOR_TOKEN || secrets.REVIEWER_ASSIGNMENT_TOKEN`, the first non-empty of the two (`CI_ACTOR_TOKEN` is the `nathanpayne-robot` PAT; the fallback is a reviewer PAT).
- Permissions use the fine-grained PAT names, which match the GitHub App permission names. "Issues or PR: write" means either permission satisfies a label or comment write on a pull request. "User token" marks `GET /user`, which needs no repository permission but fails for a GitHub App installation token.
- Standing: the token's login must be in `available_reviewers`. Attribution: the write must appear as `nathanjohnpayne`. An identity proof (the login must equal `author_identity`) without a write is noted as such, not as attribution.

## Callers that run on `pull_request_target`

- C8 `auto-clear-blocking-labels.yml` `evaluate-and-clear` gate and label removal (CI actor), with `branch-requirements.sh` reached through it.
- C9 protective retraction, through its line 654 call site in the same step (`AUTHOR_MERGE_TOKEN` as identity material).
- C13 and C14 `dependabot-auto-merge.yml` approve (reviewer PAT) and merge (author PAT), with `required-head-checks.sh` and `dependabot-commit-provenance.sh` reached through C13.
- C15 `merge-queue-authorization.yml` (author PAT; dormant).

Since 2025-12-08, `pull_request_target` takes its workflow file and checkout commit from the repository's default branch: `GITHUB_REF` is the default branch, `GITHUB_SHA` is its latest commit, and environment rules evaluate against the default branch ([GitHub changelog, 2025-11-07](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/); [events reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target)). So C8, C9, C13, C14 and C15 run default-branch definitions whatever branch a PR targets, and a branch cannot substitute its own copy of these workflows. The remaining base-branch exposure is in what those definitions check out: C13 and C14 check out `pull_request.base.sha` and run that commit's `scripts/` with both PATs in the environment, with no guard that `base.ref` is the default branch (open question 16), so a same-repository PR against another branch runs that branch's scripts. A base-is-default guard closes it; C15 already requires a `main` base. An earlier version of this section (from #2762) said these workflows ran the PR base branch's definition, which was GitHub's behaviour only before 2025-12-08.

Every other caller runs on `pull_request` or `pull_request_review` (C1 to C7, whose workflow definition comes from the candidate merge ref), on `workflow_run`, `repository_dispatch` or `schedule` (default-branch definitions), or on `workflow_dispatch` (C18 to C26). A `workflow_dispatch` run executes the definition from whatever ref the dispatcher picks. The `github.ref_name == github.event.repository.default_branch` job guard in `daily-feedback-rollup.yml:56`, `pr-audit.yml:37`, `weekly-feedback-sweep.yml:59` and `weekly-drift-audit.yml:65` lives in that same definition, so it stops only an unmodified branch copy; a branch copy that deletes it runs with the secret. `thread-resolution-lane.yml:41-46` records this as the reason C17 accepts only `repository_dispatch`.

The exposure belongs to each secret, not to these callers. All three tokens are live repository secrets in the hub and in all seven consumers (names-only readback, 2026-10-22; see [Secret placement drift](#secret-placement-drift)), so a same-repo branch pusher can also add a new workflow (for example `on: push`) on their branch, and it runs with every repository secret whatever triggers the existing callers use. Changing a caller's trigger removes one path to the secret. Moving the secret into an environment whose deployment branch policy admits only the default branch makes it unreadable to a branch's own workflows, but on its own it does not close the exposure: C13 and C14 pass such a rule, because `pull_request_target` environment rules evaluate against the default branch, and then run the `scripts/` of whatever base they check out. Closing it needs both the environment move and the C13 and C14 base-is-default guard (open question 16).

## Secret placement drift

The code treats `AUTHOR_MERGE_TOKEN` as an environment secret of `merge-queue-policy`: `dependabot-auto-merge.yml:35` says so, and `scripts/lib/merge-queue-protection.sh:884-887` requires it to be absent from repository secrets. The live placement does not match. A names-only readback through the Actions secrets API on 2026-10-22, as the owner, covered the hub and all seven consumers. Each holds `AUTHOR_MERGE_TOKEN`, `CI_ACTOR_TOKEN` and `REVIEWER_ASSIGNMENT_TOKEN` as repository secrets, the `merge-queue-policy` environment holds no secrets in any of them, and none has Dependabot secrets. Every job that names that environment therefore receives the repository secret, and so does every other workflow in the repository.

Two consequences for #2731. The `dependabot-auto-merge.yml:35-37` comment's claim that no candidate-controlled workflow can reach the token does not hold today, because the token never depended on the environment. And because `merge-queue-policy` has no deployment branch policy and no protection rules (live API, same date), moving the token into it unchanged would not close the branch exposure either: the environment needs a default-branch-only policy first. The merge-queue topology validator rejects this placement (`scripts/lib/merge-queue-protection.sh:880-887` requires the three queue secrets to be absent from repository secrets), but it runs only on the merge-queue paths, which are dormant (open question 13), so nothing has flagged the drift.
