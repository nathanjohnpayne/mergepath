# Review Feedback Accounting

Feature: every bot-authored or registered external-reviewer finding on a pull request is mechanically reconciled with finding-bound disposition evidence before another Codex review is requested, before a Phase 4b reviewer is dispatched, and before merge. One caller carries a scoped exception: the Codex request itself skips only the two providers its governing base policy names as CodeRabbit and code scanning (#1100, detailed under Enforcement points). Codex's own findings block it, and so does every registered `available_reviewers` identity including a Phase 4b adapter review — the skippable set is enumerated rather than the blocking set, so a renamed, unmodelled, or absent reviewer keeps blocking. Phase 4b dispatch and the pre-merge run are unchanged and still require every provider. The accounting answer comes from GitHub's complete paginated review history rather than from merge-state fields, a success count, current-HEAD-only scans, or review-thread resolution state. This closes the failure classes recorded in #1000: unread findings hidden by automatic resolution, a finding carried only in a top-level review body, prior-head findings stranded by a push, and a late `COMMENTED` review that never changes GitHub's merge-state summary.

The mandatory Phase 4b observation filer can create issues through the cloud REST transport using its exact long-option command (#2335): explicit repository and title, one body file, repeated labels and assignees. The verified author token sends one issue-create POST; a separate GET must verify the expected author and requested content/metadata before success. Unknown grammar refuses before mutation. Creation errors and uncertain/mismatched readback remain failures, without an automatic duplicate create or cloud merge authority. Native wrapper/REST fixtures cover the exact filer arguments, body bytes, byline/metadata refusals and transport failures.

The disposition-tier resolver distinguishes an absent feedback-policy block from an error reading a present policy file. The scalar reader preserves parsing-pipeline errors in a scoped subshell even when the caller has disabled `pipefail`. A read error returns status 2 with no tier output for required, discretionary and ignored dispositions; an absent file or block retains the existing defaults. `tests/test_feedback_policy_helpers.sh` injects the read-error status independently of host file permissions.

Relay completion authority (#1546) is bound to actual default-branch Actions evidence rather than the `github-actions[bot]` login. A v2 terminal comment names both the historical source run and the publishing relay run. Readers verify the publisher's repository, `workflow_run` event, exact relay workflow path, default branch and full SHA, then require a successful persistence step and runner-generated PR/source bindings in its job log. A PR-controlled workflow or inert handoff can copy a comment but cannot mint these facts. Direct v2 publisher proofs run before optional legacy recovery, and output retains the original comment order. Legacy v1 completion comments recover the same proof from workflow history after filtering the canonical workflow metadata, probing at most the three nearest timestamp candidates within ten seconds and the overall 60-second read deadline. A spent legacy budget grants no legacy completion and cannot erase already verified v2 evidence; unavailable or expired logs grant no completion, so an old source run may need an exact rerun or owner recovery. An unverified completion cannot erase a failure. These checks do not make other archived payload claims independently trustworthy. Before starting an uncached API subprocess, the reader recomputes its remaining provenance allowance after any CLI capability probe and refuses an exhausted allowance. The API timeout uses that fresh remainder with the existing 20-second cap; initial exhaustion, ordinary JSON reads and cached-read reuse retain their behavior (#2309).

Propagation comments carry no exemption authority. Triage, merge clearance and wave audit recompute byte equality for the live head/base pair using trusted code and reviewed canonical Git objects, then fence that pair against a fresh API read. The verifier returns `1` for definitive exemption ineligibility, including a policy opt-out, a non-lane ref or a byte mismatch; unavailable setup, source lookup or proof infrastructure returns `2` and grants no eligibility decision.

## Finding inventory

- `scripts/review-feedback-accounting.sh <PR_NUMBER> [REPO]` resolves the policy governing the pull request from its base branch, then reads all pages of `pulls/{pr}/comments`, `pulls/{pr}/reviews`, and `issues/{pr}/comments`. Accounting always materializes the target repository's policy at the exact PR-base SHA through `resolve_base_policy.sh`; a checkout merely named like the default branch is not trusted because it may be behind, ahead, or dirty. A failed or unparseable policy or history read is an infrastructure error, never an empty finding set.
- An inline finding is a root-thread Codex or CodeRabbit comment whose body is classified by the shared `codex_tier_of` / `coderabbit_tier_of` ladder. A bot re-raise in the same root thread supersedes the earlier instance, so the latest classified bot comment is the one logical finding that needs evidence after its staleness floor.
- A `github-advanced-security[bot]` (GHAS code scanning / CodeQL) inline comment is likewise an inline finding (#1101), but its severity is not in the comment body — only a link to the alert. The gate resolves it via `scripts/lib/ghas-alert-severity.sh`, which reads `repos/{owner}/{repo}/code-scanning/alerts/{number}` — the alert's permanent identity, not a ref-scoped list — fetched lazily, only when the PR carries at least one such comment, and maps the matching alert's `rule.security_severity_level` through `ghas_severity_tier` onto the shared ladder (`critical`→`p0`, `high`→`p1`, `medium`→`p2`, `low`→`p3`). It is memoized per (repo, alert number) via a FILE named by `GHAS_SEVERITY_CACHE`, not a plain shell variable — a value read back through `severity=$(ghas_alert_severity ...)` would silently lose a variable-backed cache to that command substitution's subshell — created and removed once per caller invocation via `ghas_severity_cache_init` / `ghas_severity_cache_cleanup`. #1101 originally scoped this by `?ref=refs/pull/{pr}/head`, because the unscoped list endpoint does not reliably include an alert that exists only on the PR branch — confirmed live against nathanjohnpayne/nathanpaynedotcom#809, where dropping `ref` silently omitted a `high`-severity PR-only alert. #1113 replaced that with the single-alert-by-number form, which resolves correctly for any head that ever raised the finding, closing a second gap the ref-scoped list traded into: a finding raised on an earlier, since-superseded head could not resolve its severity either, since the list is scoped to whichever head is queried. An unresolvable severity — the alert number can't be parsed from the comment, or the rule carries no `security_severity_level` — maps to `p2` rather than being dropped from inventory; a FAILED read (network, auth, rate limit) is distinct and fails the gate (`exit 2`) rather than guessing `p2`, so a systemic security-events permission gap surfaces loudly. GHAS findings ARE covered by the archive mechanism described below (#1113): `codex-p1-gate.yml`'s archive job resolves an about-to-disappear GHAS comment's severity before archiving it and hands the tier to `scripts/render-feedback-archive.sh` (which stays network-free by design) as an explicit `GHAS_TIER` argument, stored in the archive payload's optional `ghas_tiers` field, so an edited or deleted GHAS comment remains enumerated exactly like a Codex/CodeRabbit finding. Archive-time resolution preserves the one-shot prior body after a failed read and records unresolved severity possibilities `p0`, `p1`, `p2` and `p3`, with a visible warning. Accounting selects the strongest nonignored possibility under the governing policy, so ignoring one guessed tier cannot silently discard an unknown-severity record; explicitly ignoring every tier excludes its obligation while preserving the raw archive. A successful read with no assigned severity remains a known `p2` classification. A delayed eligible inline alert link can preserve the same uncertainty without a privileged lookup when the current and retained roles no longer identify GHAS; this is conservative evidence, not authenticated past-provider attribution. `scripts/review-feedback-surface-fingerprint.sh`'s before/after consistency hash likewise includes every referenced alert's current severity, so a same-window severity change or newly-resolvable alert is detected rather than hashing identically across it.
- A top-level Codex, CodeRabbit, or registered `available_reviewers` review body whose body is classified by the applicable ladder is an independent review-body finding. Review objects are not assumed to be summaries: a `COMMENTED` or `CHANGES_REQUESTED` review can carry the only copy of a finding.
- A Codex or CodeRabbit PR-level issue comment whose body is classified by the same ladder is an independent issue-comment finding. This covers summary-only findings that have neither an inline comment nor a review object.
- GitHub does not expose prior bodies of edited PR-level comments, inline comments, or top-level review bodies through the paginated REST APIs (the GraphQL edit history of one inline comment does carry each revision's text, and accounting reads it for the single narrow decision described below, but it is per-comment, cannot be event-driven, and is not a durable record), and a deleted comment disappears from its original endpoint. On a configured bot's PR-comment edit/deletion, a configured bot/registered reviewer's inline-comment edit/deletion, or a configured bot/registered reviewer's top-level review edit, the trusted default-branch workflow renders the complete previous body and marker set into append-only `github-actions[bot]` archive records before running the gate. A record that fits is one v1 comment; a near-limit body is a content-bound v2 set of at most 32 chunks, and the producer emits no partial set when that limit would be exceeded. A missing or conflicting chunk is an infrastructure error rather than a partial finding. Editing or deleting an Actions-authored archive or relay-terminal comment re-emits its exact prior record so the history surface repairs itself; a lookalike from any other login is never promoted into a trusted record, and a restored archive retains the payload's original evidence floor instead of inheriting the replacement comment's timestamp. Same-repository events normally persist records directly. Fork and Dependabot events have read-only tokens, so their native runs upload inert JSON handoffs under a non-required check name; a trusted `workflow_run` consumer treats the display title only as a candidate selector and positively binds the source run to that PR before any privileged write. It validates the actual source event, workflow path, base and source repository identities, source branch, actor, fork boundary, and either exactly one distinct PR number among GitHub's nonempty associations matching the trusted source provenance or exactly one historical PR candidate from the fully paginated source-origin lookup; a missing, contradictory, ambiguous, or unsupported source stays inert rather than failing the title-selected PR. The artifact event must equal the trusted source event, and a pull-request-family artifact head must equal the trusted source-run head; `issue_comment` is separately bound to the trusted default-branch producer because that run head is not a PR head. Delayed legitimate archives remain valid after a push, but the artifact head never becomes a Checks API target: the main relay snapshots the positively bound PR's current API head immediately before opening its lease and fences a successful publication against another live head read. The consumer validates every archive record without executing artifact content, persists the complete set, and only then publishes the required PR-head check. An artifact-lookup error follows the same always-run missing-handoff failure publisher, so it cannot leave an older successful PR-head check authoritative, and a source-resolution error publishes the same PR-head failure only after retrying the complete positive binding predicate. If the initial trusted checkout fails, that retry bootstraps only the resolver and its pagination dependency through the contents API at the workflow-run event's trusted default-branch `GITHUB_SHA`; a failed bootstrap authorizes no PR write. Failure-only publishers prefer a fresh API head and retain the resolver's validated API-head snapshot as a fallback when that refresh is transiently unavailable, so the added read cannot leave an older success authoritative. A failure cleanup closes any relay lease abandoned after publication starts and records a terminal failure, but preserves an already-completed check when only later artifact deletion fails. A completion marker for a source run supersedes a failure marker for that run in either posting order, because the archive a completion records cannot be un-persisted by a later rerun and because restoring an edited or deleted marker reposts it under a new comment id and timestamp, which makes recency an unreliable ordering signal. When every marker for one source run is `failed`, recovery is to rerun that exact historical Actions run, which keeps its run id and can publish the matching completion marker, only while GitHub still permits reruns (up to 30 days after the run initially occurred); a new PR head or different workflow run cannot clear it. If the historical run is no longer rerunnable or its rerun does not publish the completion marker, the PR remains blocked and requires owner intervention. The scheduled sweep refuses to clear either read-only path while any matching source run lacks a durable relay-completion marker, recursively splits time windows at GitHub's 1,000-result filtered-query ceiling, bounds only runs matching the target PR, and treats a missing handoff as a durable infrastructure error. Both workflows read webhook payloads from `GITHUB_EVENT_PATH` without appending transport bytes, avoiding the environment-string limit for large reviewer bodies while preserving the exact source fingerprint. Accounting validates every archive payload, binds it to the configured source kind, identity, and comment or review id, and retains every distinct archived finding version; duplicate deliveries and a live body with the same source kind, id, and body fingerprint collapse, while a distinct live rewrite does not suppress its archived predecessor. The latest trusted archive timestamp for a live top-level review's id and source login advances its evidence floor beyond immutable `submitted_at`, regardless of which earlier body fingerprint the archive carries, so an acknowledgement before an A → B → A re-raise cannot clear it. PR-level archives use the normal source-comment acknowledgement token, inline archives use `[mergepath-inline-ack: <comment id> <fingerprint>]`, and review-body archives use the normal `[mergepath-review-ack: <review id> <fingerprint>]` channel; all apply a post-archive evidence floor, so a pre-edit disposition cannot clear the archived finding. Because a CodeRabbit acknowledgement is an edit, the relay archives the revision being acknowledged; an archived CodeRabbit inline revision that, with its trailing footer and confirmation run removed, a leading `<!-- coderabbit-ai-generated:v1 -->` line and the blank lines after it removed, and carriage returns and trailing blank lines dropped (trailing spaces are content, so a Markdown hard break counts), equals the live body treated the same way is the same finding and collapses with it rather than demanding its own `[mergepath-inline-ack]`, whether the record is a v2 archive or a v1 record that carries its body; a v1 record without a body is inventoried as before (#1167).
- Archive rendering preserves the exact UTF-8 body bytes, including trailing newlines, through both fingerprint ingestion and payload encoding (#1741). A schema-valid version-2 payload whose body does not match its expected fingerprint remains an infrastructure error unless another complete Actions-authored record has a verified body fingerprint and exactly the same payload metadata (every field except `body`, including archive version, source kind/id/login, original `archived_at`, expected fingerprint, and all tier arrays). Version-2 payloads must explicitly name a valid source kind through either marker format; missing, null, or false kinds are malformed and never receive the legacy version-1 default. Recovery requires the configured source identity and any surviving live object's identity to match; a live body alone is never recovery evidence. All matching valid copies must carry the same complete body, so conflicting valid candidates fail closed even if their short fingerprints collide. Recovery is independent of delivery order, leaves the physical history records intact, and preserves the original finding, acknowledgement token, and post-archive evidence floor when the live source changes or disappears. Malformed trusted payloads, unmatched corruption, untrusted lookalikes, and missing or conflicting chunk sets cannot be recovered by a valid copy.
- CodeRabbit inline, PR-level, and review-body surfaces are scanned outside CommonMark fenced code and outside a structurally paired `pre_merge_checks_walkthrough` block. A visible, nonempty `CodeRabbit review command invocation` marker followed by the exact `⚠️ Action not completed` summary identifies that summary line as provider status rather than reviewer feedback; only that line is excluded, so real severity markers elsewhere in the same body remain inventoried. A missing, empty, quoted, reordered, or near-match invocation/summary pair fails toward classification. Quoted source markers and check-table warnings are not invented into reviewer findings; an unpaired block marker fails toward classification rather than suppressing the remainder of the body.
- When one top-level body carries multiple classified severity markers, the inventory excludes ignored markers and assigns the strongest remaining tier (`p0` through `nitpick`) after excluding those non-finding regions. An ignored marker therefore cannot hide a required or discretionary finding regardless of their relative strength or document order.
- Exact `Outside diff range comments (N)` section-heading lines are structural, with or without the warning glyph: the shared CodeRabbit tier extractor excludes the bold heading and HTML `summary` forms, including blockquote presentation and a trailing opening `blockquote` on the summary line. The decimal count and complete heading line must match; additional finding text or unknown wording remains classified. Only the heading line is excluded. Nested Minor, Trivial and required findings retain their own badges and configured policy; the standalone `Outside diff range` category remains gradeable. The original source body and acknowledgement fingerprint are unchanged. Regression coverage lives in `tests/test_feedback_policy_helpers.sh`, `tests/test_coderabbit_severity_gate.sh` and `tests/test_review_feedback_accounting.sh` (#1407).
- Inventory is intentionally not HEAD-pinned. A push does not erase the obligation to disposition a finding from an earlier head. Tiers configured as `ignore` are excluded; required and discretionary tiers remain inventoried because both represent surfaced feedback.
- Markerless review bodies and unclassified bot narration are not invented into findings.

The scheduled sweep compares each trusted relay source-run ID with its terminal-run inventory. An empty source inventory or an inventory whose source runs are all terminal permits normal gate evaluation. Any source run absent from the terminal inventory holds that PR without becoming a configuration error; the sweep still evaluates subsequent PRs. `tests/test_codex_p1_workflow_runtime.sh` exercises these three cases through the checked-in workflow's complete multi-PR loop. A relay verifier failure stops the reduction there and fails that PR closed as an infrastructure error, without passing the verifier's empty output to `jq` (#2907). A relay whose own failure path could not post `status=failed`, for example during an Actions or API incident, used to hold its PR until someone re-ran the relay by hand. The sweep now recovers it through `scripts/workflow/relay-stall-recovery.py`, which needs `actions: write` on the sweep job (#2907). Once a pending source run has been complete for `RELAY_STALL_SECONDS` (one hour), the helper reads the failed relay runs created since, nearest first and at most 20 per sweep. It binds each one to its source through the runner-rendered `SOURCE_RUN_ID` env line in the job log and re-runs a relay bound to a stalled source, up to two re-runs per relay. The binding protects a relay that is still in flight. Only a completed, failed relay created at or after the start of its source's latest attempt is re-run. A relay left by an earlier attempt was created before that start, so it is never re-run for the latest one. Another relay for the latest attempt would need another completion, which restarts the stall clock. Queued or running relays, for this PR or any other, are neither read nor waited on. The helper never clears anything: the PR stays pending until the re-run relay posts its own terminal marker, and unreadable relay history only leaves it pending. A source run with no failed relay run to re-run is named in a warning; a relay that never ran still needs its source run re-run by hand.

## Retained archive identity registry (#1437)

Ordinary archival authorizes source kind and login before reading, classifying, rendering, relaying or posting the old body. `feedback_archive.identities` is a dedicated, per-repository-owned registry in the trusted `.github/review-policy.yml`; it is independent of `available_reviewers` and the current provider login fields. Each verified entry declares `login`, provider (`codex`, `coderabbit`, `ghas`, or `reviewer`) and status (`active` or `retired`). Codex/CodeRabbit may archive issue comments, inline comments and review bodies; GHAS is inline-only; reviewers may archive inline and review bodies. Retired enrollment remains archival eligibility by the [owner decision](https://github.com/nathanjohnpayne/mergepath/issues/1437#issuecomment-6113059061), so a delayed edit or deletion after removal from the current reviewer list preserves the sole previous body. Active entries must match exactly one current configured provider or reviewer role; a missing or conflicting active role is an invalid registry. Retired entries retain their explicit historical role independently of current provider logins and reviewer membership, and no missing identity is synthesized from those current lists. It grants no current review, acknowledgment, approval or merge standing. The retained provider role governs source-kind admission. After admission, accounting preserves all existing serialized classifier arrays, so a later current-provider change cannot erase captured tier evidence. Equal-live-body and CodeRabbit acknowledgment-suffix deduplication require a current role that inventories the source kind and a nonignored live tier that covers the selected archived obligation. Eligible cross-provider quoted markers can consequently require extra dispositions; these tier possibilities do not establish authenticated provider attribution for a historical revision.

The producer and privileged relay read the trusted default-branch policy; accounting reads its existing exact governing base-policy snapshot. Never derive enrollment from current reviewer membership, event authors, source-body badges, candidate configuration, or unprivileged handoff content. Missing, malformed, duplicate or conflicting registry entries fail closed when archival eligibility or archive inventory is needed. Unrelated live accounting and empty handoffs do not need enrollment during migration. Unknown kind/login pairs produce no ordinary archive, but an already parsed Actions archive with missing or ineligible retained source enrollment is an infrastructure error, never an omitted finding or empty-success verdict. `github-actions[bot]` is excluded from reviewer enrollment and retains only its existing single-record issue-comment restoration path. Other Actions issue-comment bodies remain inert even when the registry is missing or malformed; a recognized restoration record still undergoes its existing shape validation. Fork/Dependabot handoffs remain inert; the registry constrains accepted source claims without authenticating artifact attribution or repairing the separately documented payload-omission residual.

A handoff carries one ordinary source identity/id and at most 32 records for one complete prior body, or one restoration record. Each base64 chunk is limited to 60,000 characters; missing, duplicate, mixed-source or excessive ordinary parts are refused before relay posting. Existing body fingerprints, one-shot GHAS severity capture, source repository/PR/head/run binding and relay/publisher fences remain in force. The renderer emits no partial oversized source body. Legacy handoffs without the new optional `archive_source` binding are validated from the decoded enrolled source record; historical runs cannot gain new workflow YAML on retry. Metadata-absent v2 sets, including a single `part=1/1` record, must decode to a complete enrolled source. An explicit fixed Actions issue-comment restoration with a positive source id may carry one incomplete v2 chunk or terminal record. Legacy metadata-absent singleton restorations retain compatibility only when the relay passes the existing independently verified `issue_comment` source-run context after repository/default-branch binding and the handoff tuple check; the payload event alone grants no restoration authority. Present-but-invalid source metadata never falls back to that legacy route. Complete restored sources with explicit Actions `archive_source` metadata, including `part=1/1`, validate decoded source shape independently of current retained enrollment. Renderer, native producer and privileged relay apply this narrow restoration before loading the retained registry, so a missing or malformed registry cannot erase the sole durable record. This restores the exact prior Actions record after an accidental registry removal; accounting then reports the missing enrollment as infrastructure failure instead of losing the sole body and clearing on a later sweep. Ordinary fresh sources and every metadata-absent complete source still require enrollment: verified legacy `issue_comment` run context alone cannot distinguish a fresh old-producer body from an Actions restoration. Legacy partial/terminal restoration keeps its verified source-run binding. Unknown complete legacy source claims remain inert; existing relay failure cleanup preserves a non-review failed-run marker and a failed check on the positively bound head, and accounting retains that failure across repeated sweeps. A rejected handoff is not retired by the success-only retirement step, but its raw body is available only for the configured one-day artifact retention. The durable failure marker preserves the block, not indefinite raw-body recovery; an actually unrecoverable historical run needs owner intervention. No new hold scheme or writer is added, and a never-enrolled source is not promoted into reviewer feedback. Restoration retains the documented artifact-attribution residual.

Rollout prerequisite: seed this per-repository-owned registry on the trusted target branch before delivering the mirrored scripts/workflows. Verify current and historical provider/reviewer identities, explicitly enroll custom logins, retain removals as retired, and preserve enrollment when changing current review policy. Do not add the policy to the propagation manifest or edit a generated sync PR to seed it. The hub seeds the verified three configured bots and three registered agent reviewers; `nathanpayne-robot` is a service identity with no reviewer history and is excluded. Pinned inspection of the seven consumer configurations on 2026-10-11 found the same three registered reviewers and only the default configured provider logins; absent provider fields use the existing documented default identities. These seeds are configuration prerequisites, not evidence that consumer behavior has been remediated.

After exact retained identity/source-kind admission, accounting conservatively inventories all existing serialized classifier arrays. This preserves delayed old bodies and new edited/deleted bodies even after subsequent provider configuration changes. It neither authenticates immutable per-revision provider attribution nor adds enrollment, source-kind admission or acknowledgment standing. Cross-provider quoted markers can create an extra disposition obligation on an already eligible source; this is the explicit precision cost of preserving captured evidence without a new provenance system. Equal live text and CodeRabbit acknowledgment-suffix equivalence collapse history only when the matching current role actually inventories a nonignored tier at least as strong as the archive-selected possibility; a parser that omits the conservative evidence cannot erase it. Current live standing is resolved independently of the retained historical provider role; the latter controls source-kind admission, while CodeRabbit suffix equivalence applies only to the current CodeRabbit role.

An archive-time GHAS lookup failure is represented by the existing `ghas_tiers` array containing the possible severities `p0`, `p1`, `p2` and `p3`; none is asserted as known. Accounting chooses the strongest nonignored possibility under the governing policy, so `p1: ignore` with `p2: required` and the usual `p2: ignore` split both retain the unresolved obligation. Explicitly ignoring every GHAS tier excludes it from inventory as a policy decision; the complete unresolved archive record remains durably preserved. A successful read with no assigned severity still classifies as `p2`; live lookup failures still exit `2`. When delayed delivery follows another provider change and neither retained nor current role still identifies GHAS, the network-free renderer recognizes the existing alert-number link syntax on an already admitted inline body and stores unresolved `p0`–`p3` possibilities. It performs no privileged lookup and claims no authenticated past GHAS authorship. Eligible quoted alert links can create an extra archive disposition obligation; never-enrolled sources and source kinds not admitted by the retained role remain inert. Non-inline links alone create no GHAS evidence.

Offline coverage lives in `tests/test_feedback_archive_identities.sh` and `tests/test_review_feedback_accounting.sh`: never-enrolled tier-quoted sources, edits and deletions without live prior-body recovery, retained delayed histories, current-standing separation, bounds, restoration and conservative unknown enrollment. The CI kit directly requires `scripts/lib/feedback-archive-identities.sh`; the archive test’s own requirement does not protect a kit-only filtered sync. `tests/test_sync_to_downstream.sh` verifies that a current archive test with a missing or stale identity library blocks the live CI-kit closure, while a complete current closure permits sync.

## Disposition ledger vocabulary

The canonical deferral disposition is `deferred-to-followup`, the existing resolver, rollup and feedback-ledger spelling; this avoids changing the larger existing vocabulary (#1677). `deferred-to-follow-up` is a permanent input/read alias across accounting envelopes, overrides, thread tags, targeted resolver dispositions and local feedback ledgers. Both envelope spellings remain schema-valid. Readers normalize the alias in memory, and new records, rendered accounting blocks, ledger rows and thread tags emit only the canonical disposition. Previously persisted bytes and the accounting record version remain unchanged. The CodeRabbit recorder accepts explicit `deferred`, `tracked`, `split`, `deferred-to-followup` and its alias verdicts and records disposition `deferred-to-followup`, matching the resolver tag. Raw verdict and reason remain in each append-only row. Existing fixed/rebutted rows and aliases retain their meaning; changing disposition appends a superseding row, and equivalent aliases are idempotent. Codex records usefulness reactions and its raw verdict instead; CodeRabbit writes no GitHub reactions or other mutations. A current explicit deferred row is not fix/rebuttal proof for the resolver, including when an earlier row or reply exists; a later fixed/rebutted row restores normal evidence handling. When reviewer comments share a timestamp second, the last non-agent comment in complete thread order supersedes earlier finding IDs for both deferral and fix evidence. A ledger row for that selected finding ID proves the recorder observed it; local recorded-at timestamps are not ordered against GitHub timestamps because the clocks may differ. Unreadable ledger state or an unusable newest row for the selected finding holds actioned classification and emits a warning naming the ledger, so a partial append cannot erase a current deferral. Only a usable later verdict may restore actioned classification. Recorder coverage is in `tests/test_coderabbit_record_feedback.sh`, with resolver integration in `tests/test_resolve_pr_threads_rationale_tag.sh`.

## Resolver disposition polarity (#1001)

An incidental commit touching a finding's file must not turn a recognized current deferral or rebuttal into a fix. After existing marker/routing precedence and before the file-touch heuristic, the resolver preserves current `deferred-to-followup` ledger disposition (including its permanent alias), `rebutted` disposition or raw `-1` verdict. Canonical `fixed` disposition retains the existing fix-proof requirements. Ledger verdicts use the writers’ finite, case-insensitive aliases: `fixed`, `real`, `useful`, `+1`, `thumbsup`, `thumbs-up`, `up`; `rebutted`, `false-positive`, `false_positive`, `falsepositive`, `not-useful`, `not_useful`, `notuseful`, `-1`, `thumbsdown`, `thumbs-down`, `down`; and CodeRabbit deferral aliases `deferred`, `tracked`, `split` and the canonical deferral spellings. Codex rows retain that raw verdict plus `reaction` and omit disposition; CodeRabbit rows retain the raw verdict plus canonical disposition and omit reaction. A supplied reaction/disposition must agree with recognized verdict polarity; unknown or contradictory fields hold actioned classification. Missing reaction remains compatible with legacy rows, and existing explicit metadata-only deferral rows remain deferred. A usefulness alias is not independent proof of a fix: finding binding and the existing file-touch/fix proof still apply. Rows still bind to the latest current-round finding ID, use newest append order within each ledger and require recorded-at metadata; ledger clocks are not ordered against GitHub clocks. Unknown, unusable or unreadable current ledger state holds actioned classification. Across ledger/reply evidence, explicit deferral dominates rebuttal and either dominates positive evidence until superseded in its own source.

Reply polarity is finite, case-insensitive leading vocabulary: `defer`, `deferred`, `deferring`, `follow-up`, `wontfix`, the canonical deferral spellings, or `tracked in` followed by a local/cross-repository issue reference mean deferral; leading `rebuttal`, `rebutted` or `disagree` retain rebuttal polarity with the existing thirty-character substance floor. An optional leading `Disposition:` introduces the same vocabulary. The existing leading-`Fixed` reader provides positive reply polarity. Only eligible non-marker agent replies after the latest non-agent comment participate; the latest recognized reply wins in thread order. Unknown/general prose cancels no recognized polarity and otherwise follows the existing heuristic/fallback; it is not interpreted as a new intent guarantee. Use explicit targeted dispositions or recorder verdicts when prose lies outside this vocabulary. Generated markers, their existing authority/freshness, complete-thread and human-thread boundaries remain unchanged. Native coverage is in `tests/test_resolve_pr_threads_rationale_tag.sh`.

## Disposition evidence

- An inline finding is accounted when, after its latest reviewer raise or edit, a configured author/reviewer identity posts a substantive reply in that thread. Ordinary reply evidence must have a `created_at` strictly later than the finding's evidence floor; GitHub timestamps have one-second precision, so equality cannot prove that a reply followed a same-second edit. The evidence object must be an actual reply with `in_reply_to_id` bound to the finding root; a registered reviewer's root finding can never count as its own reply. The reply must contain at least two alphanumeric tokens and twelve normalized characters; punctuation, emoji, and generated `[mergepath-resolve: ...]` tags do not count. Codex-solicited reactions and recorder ledgers remain required analytics inputs, but neither is standalone accounting evidence: reactions can be deleted without an event that reruns the required check, while `.mergepath/` ledgers are worktree-local and gitignored, so accepting either would let different checkouts or later reaction state compute different answers.
- CodeRabbit acknowledges a disposition by editing its finding rather than replying, in more than one shape: the finding's own `auto-generated comment` footer rewritten to the `auto-generated reply` marker with a confirmation line appended; reply marker, confirmation line, reply marker; reply marker, confirmation line, comment footer; confirmation line then either footer; the footer rewritten to the reply marker with no confirmation line at all, after a reply it does not confirm; and any of them stacked when it acknowledges again. The confirmation wording varies (`✅ Confirmed as addressed by @<identity>`, `✅ Addressed in commit <sha>`). The edit advances the comment's `updated_at` without re-raising the finding. Recognition is therefore anchored on the vendor's generated footer markers, either kind, not on the wording: the trailing run of footer markers and `✅` confirmation lines at the end of the body acknowledges when it holds at least one of each, and then the finding's evidence floor stays at its creation and the substantive reply the acknowledgement answers remains evidence (#1167). A `✅` line is a confirmation when it carries a known confirmation wording or when the non-blank line directly above it is the reply marker; a content line that happens to start with `✅` before the finding's own footer is content. The run is trusted only when the raw body and its fence-aware visible text agree on it (the raw run being the tail of the visible run): a run followed by other visible content or by a code fence, or a run inside a fence, is an ordinary edit, and ordinary edits still invalidate older replies. `✅` lines with no marker at all are content, not a run. When the relay's record holds archived revisions of the finding, the record decides what the latest edit did: if some archived revision has the live body's content the edit was content-free and the floor is the newest archived revision whose content differs, or the finding's creation, which is how the shape with no confirmation line is recognised; if none does, the edit changed content and the floor is that edit even when an acknowledgement came with it. Without a record the marker-based rule stands for every shape but the no-line one: when that shape is left unaccounted and no record applies, GitHub's own edit history of the comment (`userContentEdits`, paginated) decides, and the floor is the oldest revision in the unbroken run, from the newest revision back, whose content compared as above equals the live content; GitHub lists the creation as the oldest revision, so a history identical throughout keeps the floor at the finding's creation, while a revision that differs, that GitHub withholds, or that was deleted ends the run at the newer edit. A history that cannot be read, that does not resolve, or whose newest revision is not the live content leaves the rewrite an ordinary edit, with the cause written to stderr (#2598). A v1 record's body is used only when it matches the record's fingerprint, as for v2. On a pull request whose head is not the base repository itself (compared by repository identity, since the fork flag of the head is also set on every branch of a repository that is itself a fork), or whose head repository is gone, the record is fork-supplied and accepted by the relay on marker shape alone, so it never lowers a floor: the marker-based rule stands, an acknowledgement-only archived revision still collapses, and every other archived revision stays inventoried with its token. GitHub's edit history is not fork-supplied, so the no-line shape is decided from it on a fork pull request too. When the login-naming wording names a configured identity, that identity's substantive reply at exactly the finding's creation timestamp also counts. The acknowledgement edit can also prepend the invisible `<!-- coderabbit-ai-generated:v1 -->` header to a finding created without it; that line, when it is the body's first line, is vendor framing like the footer markers, so revisions are compared with it and the blank lines after it removed. A header anywhere else, or content added with it, is compared as written (#2568).
- A top-level review-body finding is accounted by a PR-level comment whose first line is exactly the emitted `[mergepath-review-ack: <review id> <fingerprint>]` token and whose rationale below it is at least 12 normalized characters containing at least two alphanumeric tokens. Its GitHub timestamp must be strictly later than the finding's latest raise, edit, or archive because second-precision equality cannot prove ordering. The fingerprint covers the whole review body, including trailing newlines represented by GitHub's JSON string, so editing a review invalidates an earlier acknowledgement without requiring the review id to change.
- A PR-level issue-comment finding uses the equivalent emitted `[mergepath-comment-ack: <comment id> <fingerprint>]` token and rationale. Its staleness floor is the finding comment's latest edit, and its fingerprint covers the whole current body.
- The acknowledging identity must be the configured author identity or one of `available_reviewers`. A bot, an unrelated account, an earlier comment, a bare token, or a token embedded below the first line is not evidence.
- A resolved review thread is not disposition evidence by itself. Resolution is a separate conversation-state gate and cannot make an unread finding disappear from accounting.

## CLI contract

The script emits one compact JSON object with `status`, `repo`, `pr_number`, `posted`, `accounted`, `missing_count`, `findings`, and `missing`. Every finding carries its shape, reviewer, tier, identifier, disposition state, and evidence kind; review-body and issue-comment misses also carry the exact acknowledgement token needed to retire them.

The Dependabot immediate-squash workflow grants Actions read to its `GITHUB_TOKEN` so accounting can authenticate relay workflow runs, jobs and logs. The live propagation verifier uses the shared YAML reader, including the guaranteed bootstrap `yq` path, without requiring Ruby.

The governing policy is parsed once into JSON and all accounting decisions consume that representation, so block-style and flow-style YAML are equivalent. The preferred mikefarah `yq` path requires exactly one parsed YAML document before conversion, matching the Python and Ruby rejection of additional documents. A document-count or conversion failure returns nonzero with empty stdout; separator text inside a scalar remains ordinary data. Runtime validation requires `jq` and Python 3 for authenticated relay provenance, plus one YAML parser: mikefarah `yq`, Python 3 with PyYAML, or Ruby with its standard YAML library. Python must be installed even when Ruby or `yq` supplies YAML parsing; the CLI refuses a missing interpreter before reading GitHub state. If none is available, or if parsing/schema validation fails, the gate exits `2` rather than applying layout-dependent defaults.

- Exit `0`: every inventoried finding is accounted (`posted == accounted`).
- Exit `1`: one or more findings are unaccounted. JSON is still emitted and stderr names the remediation for each missing finding.
- Exit `2`: usage, configuration, cryptographic-tooling, or GitHub API failure. Callers fail closed.

## Manual handoff freshness (#2157)

The manual renderer accepts bare PR numbers and explicit `owner/repo#number` refs. A bare-ref repository lookup that fails or succeeds with an empty repository exits `3` without an artifact. Every parsed repository/PR pair must be nonempty before any feedback accounting or metadata/rendering begins, including in a mixed batch (#1441). Normal resolver output and the parsed table retain their structural newline behavior. `tests/test_post_phase_4b_handoff.sh` exercises empty and malformed successful output, ordinary lookup failure, and valid bare/explicit forms.

The manual Phase 4b renderer uses the shared Codex Review Summary parser before emitting any single or batch artifact. A current-head Running or unknown summary at least as recent as the latest exact-head review or verdict holds with exit `5` and empty stdout. A configured author's exact request newer than the head anchor and within the governing review timeout likewise holds until a substantive exact-head review, anchored verdict, or Completed summary answers it. A later request supersedes an older response. A timed-out request with no active summary permits the existing Phase 4b fallback; a genuinely Running summary still holds independently of the request budget. Unreadable provider history, policy or head fencing fails with exit `3`, never a ready handoff.

If the renderer returns its active-review exit `5` while `phase-4b-review.sh` is preparing a manual fallback, the caller retains the hold as exit `6`, `barrier_pending: true`, a 30-second retry interval and `fell_back_to_manual: false`. It emits no manual briefing instruction or approval. The request-authority revalidation still precedes that outcome. Accounting for the adapter failure that led to rendering remains fail-closed evidence; the hold does not claim that adapter succeeded.

`Threads:` and the batch count come from complete-history accounting's undispositioned finding count, rather than raw unresolved conversations. Accounting must succeed with a valid matching repo/PR result and reconciled totals before rendering. The handoff still instructs reviewers to resolve outstanding conversations through the normal pre-merge gate. Counts and provider state are observations of this rendering pass; later activity requires a fresh render. No review request, comment or label is posted.

## Enforcement points

- `scripts/codex-review-request.sh` runs the gate immediately before an author-attributed `@codex review` write. An accounting miss **from a provider that gates this request** exits `6` and posts no trigger (#1100): Codex's own findings, and any reviewer identity including a Phase 4b adapter review. An outstanding CodeRabbit or code-scanning finding does not refuse this one write. The exception is structural, not a relaxation of the accounting answer: the Phase 4b barrier waits for Codex to be terminal on the current head while its Codex arm is read-only, so this write is the only thing that can make Codex terminal, and an all-provider precondition here is a livelock rather than a checkpoint — each fix commit dispositioning CodeRabbit is a new head for CodeRabbit to find more on. Every other enforcement point below, and the pre-merge run, still require `posted == accounted` across all providers.
- That exception enumerates the providers that MAY be skipped, never the ones that must block, so an unmodelled, renamed, or absent reviewer keeps refusing. The skippable logins are resolved from the governing base policy through `resolve_base_policy.sh` — the same policy accounting classifies `.missing` with — so a PR that edits `.github/review-policy.yml` cannot nominate its own skippable set, and an unresolvable base policy means nothing is skippable rather than falling back to the candidate checkout. After successful governing-policy parsing, absent or empty `coderabbit.bot_login` and `code_scanning.bot_login` use accounting's established `coderabbitai[bot]` and `github-advanced-security[bot]` defaults. An explicit login replaces its default; a failed parse or field extraction leaves the whole skippable set empty. These identity defaults do not change provider enablement. "The same policy" is one resolution, not two agreeing ones: the caller materializes the base policy once and hands accounting that snapshot through `REVIEW_FEEDBACK_ACCOUNTING_CONFIG`, because a base that advances between two independent resolutions could classify `.missing` under one revision and build the relax set from another, and a newer revision that moved a gating login onto a skippable provider is internally consistent and so raises no collision. Provider, author, and reviewer logins are normalized case-insensitively for both collision detection and matching against observed `.missing[].reviewer` values, since GitHub treats login casing as non-semantic while policies are hand-written. Because `validate_governing_policy` validates `codex`/`coderabbit`/`code_scanning` `bot_login` only as optional strings and `available_reviewers` only as non-empty strings, nothing in the schema requires those identities to be distinct; a base policy that gives a skippable provider the Codex bot's login, the author identity, or a registered reviewer's login therefore voids the whole skippable set rather than any part of it being honored. An accounting result that reports unaccounted without naming who is outstanding — an absent, empty, or non-array missing set, or output that does not parse — is refused, not read as "nothing blocking".
- `scripts/phase-4b-review.sh` runs the gate immediately before the reviewer adapter, including on dry-runs because the scarce operation is the reviewer reasoning round. An accounting miss exits `7`, dispatches no adapter, and renders no manual handoff.
- `scripts/post-phase-4b-handoff.sh` runs the same gate before rendering a manual-review handoff. An accounting miss exits `4` and emits no handoff, so consumers with automated Phase 4b disabled get the same dispatch-time protection.
- The manual handoff resolves each PR's reviewer from its governing base policy and exactly one visible, configured `Authoring-Agent` declaration through the shared PR-body parser. A missing or ambiguous author, unreadable policy, unavailable cross-agent reviewer or same-agent/unregistered override exits `3` without rendering. Single and mixed-author batch prompts name the reviewer per PR and express approval gate (b) AND signal/substitute gate (c); they do not claim a Codex signal alone clears the approval gate.
- `scripts/codex-p1-gate.sh` runs accounting default-on in every consumer before consulting the legacy current-HEAD required-tier toggle. This supplies a merge-time CI backstop for top-level review-body and PR-level findings, plus discretionary-tier findings that review-thread state cannot represent; `codex.p1_gate.enabled: false` disables only the older thread scan.
- Event-driven and scheduled Codex P1 publishers open an `in_progress` check generation on the PR head before evaluation and PATCH only that generation when evaluation finishes. Generation creation order is therefore stable even when an older run finishes after a newer event: the older PATCH cannot become the newest check. The required native-check jobs deliberately carry no Actions `concurrency` block because GitHub can cancel a queued native check even with `cancel-in-progress: false`, leaving an unretirable required-check failure. The scheduled loop contains an unreadable or unparseable per-PR API response before opening a lease, records that infrastructure error, and continues with later PRs without a check-run mutation for that PR. Both paths also fingerprint all three feedback surfaces before and after evaluation; a readable changed fingerprint discards the verdict and reevaluates from fresh state within the bounded snapshot-recovery contract below; an unreadable fingerprint fails closed without retrying it as ordinary drift. An event-driven trusted checkout can use the sole bootstrap warning when its checked-out default branch does not yet contain the workflow or when that workflow does not yet reference the helper; an existing workflow that cannot be searched is an infrastructure failure. The scheduled job has no bootstrap window because it loads the workflow and helper from the same default-branch revision, so a missing helper fails every readable PR-head lease before evaluation and leaves the scheduled native job failed as well.
- `scripts/admin-merge-codeowners-blocked.sh` runs the gate itself immediately before dispatching `gh pr merge`, after its zero-unresolved-thread gate and before the head-pinned merge call. That dispatcher is the one merge path that can pass `--admin`, which bypasses the required-check backstop above, and a finding carried only in a top-level review body or a PR-level comment has no review thread for the conversation gate to catch. Any non-zero exit — an accounting miss or an infrastructure error — refuses that PR's merge. The generic identity wrappers (`scripts/gh-as-author.sh`) are deliberately not wired: they attribute arbitrary `gh` writes rather than dispatching merges, so the gate would run on PR creation, edits, and comments.
- `.github/workflows/dependabot-auto-merge.yml` runs the gate immediately before its immediate-squash fallback. The workflow's primary path is `gh pr merge --auto`, which GitHub releases only once the repository's required checks pass, so the CI backstop above already covers it. The fallback fires on exactly the condition that removes that backstop — `--auto` reported unavailable, meaning the repository has no branch protection and therefore no required check to release against — and it squashes without waiting for CI beyond the configured `lint` proxy. Running the gate there restores parity with a protected repository: the same accounting answer decides both paths. Any non-zero exit, miss or infrastructure error, refuses the squash and leaves the PR approved-but-unmerged, which keeps the weekly audit's reviewer-approval gate satisfied while the findings are dispositioned. A missing or non-executable gate script in the base checkout is also refused, so a consumer that receives the workflow ahead of the script stalls rather than merging unaccounted; the manifest's `requires:` closure keeps that window shut.
- Every other human- or agent-driven merge path runs the accounting command immediately before merge as agent procedure, alongside the independent zero-unresolved-thread and recorder checks, and relies on the required-check backstop above for mechanical enforcement.

After `scripts/phase-4b-review.sh` posts an `APPROVED` review, it uses the accounting gate's emitted token to acknowledge only that invocation's exact review body when needed. The gate emits its parsed governing `feedback_policy` alongside the inventory, and automatic acknowledgment requires that policy to allow the orchestrator's step-9 dispositions; `CHANGES_REQUESTED` and unrelated or changed review bodies are never automatically acknowledged. When rendered findings are nonignored by the governing policy, a clear accounting result without the expected review id and exact body is an acknowledgment failure, not proof that no acknowledgment is needed. Governing ignore tiers create no obligation even if an older local policy filed issues for them. Gradeable nonignored markers in the freeform summary lack structured step-9 evidence, so their approval body is left for acknowledgment repair. The orchestrator waits a second before posting under the selected reviewer identity, then re-reads accounting to verify that exact body is accounted. Failure returns exit `7` with `review_posted: true` and `review_acknowledgment: "failed"`; the posted approval and its ledger record remain truthful, and the operator should repair its acknowledgment rather than repeat the review. This does not retire a check from another producer lineage or guarantee that every other merge gate is clear (#1261).

## Bounded feedback snapshot recovery (#1825)

The event and scheduled producers retain their existing names, original PR head, and original in-progress lease. `scripts/workflow/codex-p1-snapshot-retry.py` owns evaluation through publication: a head read, complete pre-evaluation fingerprint, head-pinned gate, post-evaluation fingerprint, fresh head read, and final publication fingerprint. A change at either fingerprint comparison discards the result and starts a fresh attempt; no previous success or neutral conclusion is reusable. The event preparation step does not prematurely fail its native execution on drift. Its closing step returns the driver's final verdict, so a successful reevaluation and successful lease PATCH also complete that same native job successfully.

Bounds are three total evaluations, two seconds between drift retries, and a shared 180-second monotonic deadline across evaluation and all nested transport processes, including pagination. A locked counter admits at most 200 nested `gh` commands across all attempts. This is a command/transaction budget, not a claim of 200 HTTP pages: `--paginate` may fetch several pages per admitted command, all under the same hard wall deadline. Normal three-attempt recovery performs at most three gate evaluations and nine complete fingerprint scans; inventory size is unchanged. The bounds allow two overlapping bot updates without permitting indefinite churn. Code-scanning severity, complete review/comment histories, edits, archive records and deletions remain fingerprint inputs.

The native deadline fixture first verifies the production driver's remaining timeout: with ten elapsed seconds on a controlled clock, the unchanged180-second budget must supply170 seconds to communication. Only after checking that value does the fixture wait for a descendant’s recorded readiness and shorten the real communication wait to one second, including with a deliberately slower launcher. The readiness wait has a ten-second bound and failure cleanup. It then releases any survivor after lease failure and observes process death before accepting absent escape evidence. The observation and descendant both have independent bounds; a zombie cannot resume execution. Removing the production timeout, miswiring its clock or replacing group termination with a leader-only kill must fail the fixture. Production deadline calculation, actual kill path and original failure lease remain unchanged (#2462).

Exit `3` identifies exhausted snapshot recovery (attempt, time or API-command budget), distinctly from exit `2` for unreadable input, configuration/head errors or publication failure. Exit `1` is stable blocked feedback and exit `0` requires stable clear feedback plus successful publication. Genuine gate errors never become retriable merely because a comment also changed. The scheduled loop closes each readable PR's original lease and continues with later PRs, while any exhausted/infra result also fails its native sweep job. Archive failures and pending trusted relay work retain their existing fail-closed preparation path.

Pending on non-blocking dispositions (#2618). When the event-driven caller names `CODEX_P1_PENDING_VERDICT_FILE`, the driver removes that file, hands each gate attempt its own private `MERGEPATH_GATE_VERDICT_FILE`, and writes `pending` to the caller's file only when the published verdict is exit `1`, the gate wrote exactly `pending` on that same non-drifted attempt, and the red lease PATCH succeeded. The gate writes `pending` only when accounting's undispositioned findings are all non-blocking (`p2`, `p3` or `nitpick`, required by neither the gate's blocking set nor the governing policy) and the exact-head fence and legacy blocking-tier thread scan found nothing after them; any blocking-tier or unknown tier, malformed answer or read error leaves no verdict. The caller then concludes its job-native run non-failing only after `scripts/gate-api-lineage-blocking.sh` confirms the red Checks-API lineage. Exit codes, lease conclusions and titles are unchanged, and without the variable the driver and gate behave exactly as before.

Closure has a separate reserve of three PATCH attempts, ten seconds each. Once a PATCH fails or times out, further closure attempts may only publish failure; they never replay a success whose fence has aged. Publisher launch errors also spend this reserve and switch every remaining attempt to failure; even a successful failure-close retains infrastructure exit 2. An exit-versus-timeout race cannot renew an uncertain success. Unexpected setup/driver errors report infrastructure exit 2 with closure explicitly unconfirmed, rather than masquerading as an ordinary blocked-feedback exit 1. Exhausting that reserve is explicitly reported as an unclosed pending lease and non-successful execution. No retry creates a new generation, so an older completion cannot displace a newer opened lease. GitHub offers no conditional feedback-snapshot PATCH: the residual interval between the final read and remote write remains, as with the original fence.

During first delivery only, an event workflow may run against trusted main before that main workflow references the new retry driver. Positive reference absence permits the previous single-shot head/fingerprint-fenced evaluation with a warning; the legacy gate verdict is captured conditionally under the Actions shell’s errexit behavior so blocked and configuration-error verdicts still close the original lease as failure; an unreadable workflow, dangling path or referenced missing/non-executable driver fails closed. Scheduled workflow and helper come from one trusted revision and receive no skew exception. Offline acceptance lives in `tests/test_codex_p1_workflow_runtime.sh`, `tests/test_codex_p1_gate.sh` and the feedback-accounting/fingerprint suites. Installed nathanpaynedotcom native-run acceptance remains required before closing #1825; hub source tests alone do not establish consumer recovery.

## Explicit single-thread disposition (#2196)

`resolve-pr-threads.sh <PR> --thread <thread-node-id|original-comment-id> --disposition fixed|rebuttal|deferred-to-followup|addressed-elsewhere` selects exactly one review thread from the complete paginated PR inventory. A missing or ambiguous selector fails before writes. The original comment ID is GitHub's numeric review-comment database ID. Bulk/list modes and `--no-tag-reply` cannot be combined with this explicit mode. The registered reviewer identity check, bot-author boundary, resolve mutation confirmation and independent resolved-state readback still apply; real human and registered agent threads are never resolved by this bot-only mode.

The operator's explicit disposition determines the marker without file-touch inference or automatic upgrading: `fixed` and `addressed-elsewhere` record `addressed-elsewhere`, `rebuttal` records `rebuttal-recorded`, and `deferred-to-followup` records that exact class and requires a positive `--issue <number>`. Optional `--commit <SHA>` (7–40 hexadecimal characters) and `--rationale <text>` are citations in the reply, not automatic proof of a fix. This permits a cross-file fix or an explicit deferral on a touched file, including an older-head finding. The requested marker must be posted successfully before resolution; failure leaves the thread open. Other threads are untouched, dry-run writes nothing, and success covers only the selected thread. An already resolved selection is a no-op; correcting historical markers is outside this mode. This adds no exemption to finding accounting or review policy.

Targeted disposition-reply confirmation validates only the mutation's JSON stdout. Diagnostic stderr stays separate, so a warning accompanying a confirmed marker does not cause a parse refusal or duplicate marker retry. Failed writes still inspect both streams for proxy refusal evidence and leave the thread unresolved; the temporary diagnostic capture is removed on success and failure. Native tag-emission tests cover warning-plus-valid-JSON, failures on either stream, missing markers and resolved-state readback.

## Reserved review-trigger text (#2158)

Author and reviewer write wrappers inspect literal Codex-trigger text case-insensitively anywhere in comment/review bodies, including code fences. They cover CLI inline/file/stdin bodies and REST comment/review writes through raw or typed fields and JSON input. Ordinary file/stdin payloads are snapshotted privately and the same bytes are passed to `gh`; a permitted genuine command is normalized to canonical request bytes so the existing exact-body counter sees it. Body text is never logged. Unknown or unreadable write payloads fail closed. Interactive comment editing cannot change a body after inspection. The REST transport retains its existing materialized-file-only CLI grammar and refuses CLI stdin even after inspection; raw API stdin is inspected and snapshotted separately.

Ordinary prose containing the reserved phrase is refused with a request to reword it. The complete command is accepted only on the canonical requester's author-attributed PR-comment path, with its current-head context and a fresh read-only authorization through the requester's existing governing request/blocking budgets and feedback accounting. The internal context marker grants no budget exception. The PreToolUse hook catches literal inline and readable-file triggers too; file/stdin data unavailable before command execution is deferred only to the mandatory runtime wrapper guard. No request counter is reset, and no review is triggered by this inspection. This is a guard over the documented comment write forms, not a new security boundary against an operator who already holds the owner credential.

The hook inspects each command-position native `gh` invocation in its existing compound-command scan before the noun walk may return on an earlier read (#2341). A comment/review payload counts as a guarded write for the existing split-compound requirement, including raw API forms. Each inspection must return exactly one JSON object with a Boolean `guarded`; missing, malformed, mistyped or unreadable metadata refuses the command. The noun walk also requires an explicit Boolean classification for every command-position `gh` token it reaches, including through a wrapper. A missing index means inspection is incomplete and refuses with `exit 2`, rather than becoming an unguarded read. Native, prefix, separator and wrapper pairs plus a controlled missing-index copy exercise this invariant (#2467). Verified wrapper identity checks and runtime inspection of deferred data remain required. Native read-only compounds retain their existing allowance. Coverage is in `tests/test_gh_pr_guard.sh`.

## Safe write and readback rule

The shared write-token resolver replays identity-check diagnostics when an ambient candidate succeeds, including the explicit unidentifiable-token override warning (#1544). Rejected ambient candidates keep their checker diagnostics private while the existing fallback notice and keyring lookup continue. Empty legacy 40-hex header capture emits a generic stderr note without token or response content. Credential classes, explicit override decisions, selected token and stdout contracts remain unchanged; `tests/test_identity_check.sh` exercises the real resolver and checker for both write identities, quiet fallback and empty-success/failed header probes.

The native hook lends the cached reviewer PAT to its self-approval metadata read only when `REVIEW_REPO` or inherited `GH_REPO` explicitly supplies a validated plain `OWNER/REPO`, in addition to the existing canonical-host and URL checks (#2312). An absent repository is not proof: GitHub CLI may infer a different host from the checkout despite `GH_HOST=github.com`. A PR URL alone does not replace this explicit repository requirement. Other cases keep the CLI's own credentials and fail closed when those are unavailable; ambient credentials are never replaced by this fallback. Native fake-CLI controls cover inferred and explicit repository contexts without real credentials or network access.

The requester's propagation entry directly requires both write wrappers, the hook, the runtime trigger-guard library and its parser (#2281). A commit-path sync checks those direct edges against the consumer so shipping only requester markers cannot leave its enforcement half stale. The existing manifest and propagation-closure suites cover dependency validation; wrapper behavior remains covered by `tests/test_gh_comment_trigger_guard.py`.

Disposition replies and top-level acknowledgements are posted through the identity-checked author/reviewer wrappers using `--body-file` (or an equivalently structured stdin/JSON payload). Shell-sensitive Markdown is never interpolated into a double-quoted `--body` argument. After a write, the caller re-reads the GitHub object and reruns accounting; a wrapper's exit code or printed success count is not proof that the intended payload landed.
- Known residual, fork and Dependabot paths only. A handoff carries three record shapes. Two are reviewer content the trusted job cannot obtain any other way, because GitHub exposes no prior body for an edited comment and no body at all for a deleted one; the trusted consumer positively binds the source run to the repository and PR, cross-checks the event and pull-request-family source head, and derives the actor, fork boundary, and publication head itself, but the record payload bodies are asserted by the unprivileged producer, which on a fork PR the fork controls. Adding or altering a record is the fail-closed direction: it becomes another archived finding that must be dispositioned. Omitting one can hide a body that no longer exists live, and never the current copy, because accounting inventories the live surface through the trusted checkout's own API reads rather than through the artifact. The third shape is a relay terminal comment, which a fork-supplied handoff can also manufacture. A copied completion grants no authority: readers now require the actual trusted relay run, successful persistence step and matching runner-generated PR/source bindings described above. Missing-handoff recovery additionally requires a completed required-check generation already on the bound head. Reviewer payload omission remains a separate residual risk.

## Non-goals

- The gate does not judge whether a rationale is persuasive; it verifies that a finding-bound disposition record exists.
- The gate does not replace severity-specific merge policy, external-review clearance, reviewer approval, or GitHub conversation resolution. Those remain independent gates.
- The gate does not auto-resolve threads, post acknowledgements, react to findings, push commits, or merge.

Missing-handoff provenance outages publish a failed check on the bound PR head. Artifact retirement is a separate best-effort step after successful persistence, and cleanup recognizes both completion-marker versions. Live lane verification classifies the configured branch prefix before requiring author metadata, and wave policy resolution uses its initially observed base SHA.

Comment payload inspection includes the documented closing-comment form and value-taking options before the command group. Comment-free closes retain their existing hook scope. Explicit API GET requests keep their read semantics. Within comment writes, ambiguous pre-verb comment and reason flags must move after the verb, where review flags and closing text have distinct meanings.

Spell short Boolean flags separately from body or API parameter flags; ambiguous clusters are refused before any write. Raw GraphQL inspection (#2276) recognizes the known comment/review mutation calls in the guard's explicit inventory, ignoring quoted strings, GraphQL comments and operation names. It scans query literals and all supplied variable/JSON strings for the same reserved phrase. Inline fields, typed file fields, JSON/stdin input and URL query parameters are covered; runtime file inputs are snapshotted even for reads so a later edit cannot substitute a mutation. At hook time, every GraphQL file input requires the verified runtime wrapper, including an existing file currently containing a safe read; preceding shell commands may replace it before execution. Ordinary queries and non-comment mutations retain their behavior. Unsupported string escapes on a recognized comment mutation are refused. This is conservative document inspection: unused mutation definitions or variables can also cause refusal; it does not resolve GraphQL execution or bind arbitrary input fields. Operation-name exclusion applies only outside selection braces, so keyword-named fragment spreads cannot hide a following comment field. Valueless `key[]` fields retain their documented empty-array form; they contribute no body text and do not suppress inspection of other fields. Raw GraphQL never gains the canonical requester's command authorization. GraphQL tokenization ignores U+FEFF only outside literals and recognizes only escaped triple quotes inside block strings; ordinary backslashes remain literal. BOM-separated calls and escaped block-string defaults cannot hide a comment mutation.

Relay CLI escape-support detection distinguishes failed probes from successful legacy help (#2310). Before the first uncached text read, it permits two help attempts total, each capped at ten seconds and the fresh remaining evidence allowance. A successful probe alone caches support or legacy non-support. Timeout, OS error or nonzero exit never caches a capability result; two failures refuse the text read and cannot promote completion. JSON and cached reads retain their existing probe-free behavior. Fake-clock and executable fake-CLI cases in `tests/test_marker_provenance.py` cover recovery, persistent failure, successful legacy caching and deadline exhaustion between attempts.
