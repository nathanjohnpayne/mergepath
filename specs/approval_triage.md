# Approval preservation after failed triage

A failed triage job must keep approval consumption and merge blocked. It must not dismiss an exact-head registered-agent approval merely because the preceding triage job encountered an infrastructure error while the approval snapshot remains stable.

The triage PR/file-list reads and approval guard PR/review-list reads retry transient transport errors and HTTP 5xx/429 at most three times, with 250ms then 500ms backoff. Permanent authorization and not-found responses, policy decisions and writes are not retried by this helper.

When triage did not succeed, the guard may preserve only the direct registered-agent approval whose commit equals the event head. Two live PR observations must match the event head, base ref/SHA, author, body and sorted label snapshot, normalizing GitHub’s null body as the existing snapshot function does. The job still fails and emits no eligible approval or current snapshot. Observed drift, malformed/unreadable state, an old-head approval or an unregistered reviewer retains the existing conservative protection path. The workflow carries generated copies of the canonical helper for an atomic first rollout only: fallback is permitted only when the helper is absent and the trusted default-branch workflow has not adopted it. Once adopted, missing or broken canonical code fails closed. The guard routes a failed canonical-helper load through conservative approval protection before failing. Human/unregistered reviews and non-approved events remain outside automatic dismissal. Successful triage still performs the existing live policy and stable-review checks.

`tests/test_self_approval_detector.sh` tests bounded retries and the production workflow's failed-triage branch with stable snapshots, transport errors and actual drift. It also preserves the existing head/base and unstable metadata refusal regressions. This change adds no approval authority, automatic reapproval or workflow dispatch.
