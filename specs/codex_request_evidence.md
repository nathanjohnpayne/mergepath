`codex.max_review_rounds` is an enforced, per-PR cap on new author-attributed exact `@codex review` request attempts. The requester counts complete, paginated issue-comment history by deduplicated comment ID immediately before each new trigger write, including an acknowledgement retry. It defaults to `10`; an unreadable or malformed qualifying record refuses the new request. When an initial request consumes the final slot, a missing eyes acknowledgement suppresses its retry but preserves the already-posted request's ordinary bounded review poll. Current-head clearance and same-head idempotent reuse occur before this check and keep their existing behavior. The cap does not reconstruct provider responses: a clean response may be a mutable summary or an anchored affirmative verdict, and an orphan automatic provider review is not an additional requester call.

A second budget is checked first at the same write boundary (#1560 slice 3). `codex.max_blocking_reviews` (default `10`, provisional) bounds the PR's solicited blocking Codex reviews, counted from the Codex review ledger as `specs/codex_review_ledger.md` § Consumer describes. A new request is refused once that count reaches the budget, so a budget of 10 permits a request at 9 and refuses one at 10 or 11. The value is read from the same governing base policy with the same digit validation. A missing, failing or malformed ledger exits `3` with no write, as does one for another head, author or policy snapshot (`--expect-policy`, `crqe_policy_fingerprint`). The governing budget output carries that `policy_fingerprint`. An acknowledgement retry is not re-checked, and the idempotent skip (a fresh request already on the head) never runs the ledger. At a spent request ceiling the ledger still runs before the ceiling is reported, so that the blocking budget can take precedence. There, a missing or malformed ledger exits `3` rather than `7`. The stop is the exit `7` described next, with `cap_exhausted.kind: "blocking-reviews"`; when both budgets are spent it takes precedence over the request ceiling.

If a later invocation reaches the cap before it posts an initial request, the requester exits `7` (`CAP_EXHAUSTED`) with its ordinary observation fields and a `cap_exhausted` object containing `kind` (`"request-ceiling"` here, `"blocking-reviews"` for the budget above) and the consumed and configured counts of both budgets (`blocking_reviews` and `max_blocking_reviews` are null when the blocking count was not taken). Its `observed_provider_block` preserves any current `usage_limit` or `not_connected` scan result as diagnostic context only; top-level `blocked_reason` stays null, so the cap cannot acquire Phase 4b routing authority. It posts no trigger or timeout determination and does not route the PR to Phase 4b or grant clearance. This no-write stop precedes feedback accounting; when a request slot remains, the existing accounting gate still runs before any trigger write. The caller retains its already-selected advisory or required review policy; the cap does not classify the PR, route it, or create or remove a merge hold. The special final-slot acknowledgement-retry case suppresses only the retry and continues polling this invocation’s already-posted request. In polling mode the requester resumes rather than re-posts an unanswered request (#1550). Because a trigger names no commit, freshness alone never attributes it to the current head; resuming additionally requires the provider's Review Summary to report a Code Review Running on the exact current head, updated at or after the pending request. The pending request is the latest exact configured-author command with no freshness anchor (the reaction-freshness floor may be shorter than the reply deadline, and the head-push anchor falls back to an author-controlled committer date); its own deadline bounds staleness and the exact-head Running summary binds it to the head. It must not already be answered, provider-blocked, or bound to a current Phase 4a timeout determination. The resumed wait ends at that request's creation time plus `review_timeout_seconds`, and the exit decision anchors on the resumed request exactly as on a posted one. A resumed request grants no timeout authority: if its wait expires unanswered, the requester re-executes itself as a fresh invocation with resume disabled, so the replacement re-reads the live head, starts its own clock and goes through the ordinary path (including the cap check), and only a request that run posts may write a timeout determination. Without the provider evidence the requester posts as before, but unreadable evidence is not absent evidence: the resume read retries a transient failure and then exits `3`, and malformed selector output or trusted timeout-marker evidence exits `3`, rather than posting a duplicate into a review that may be running. Post-trigger scans retry a transient read failure (a fetch failure whose gh diagnostic names HTTP 5xx, 429 or a rate-limited 403, or names no HTTP status) a bounded number of times before exiting `3`; a permanent failure, a failure with no diagnostic, or an unflattenable response exits `3` at once.
