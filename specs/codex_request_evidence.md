Fresh wrapper authorization (`--authorize-trigger-write`) applies the ordinary requester's no-write decisions before budget validation or permission to post (#2282). They are the decisions of the mode the canonical requester writes from, which it names in `MERGEPATH_CODEX_TRIGGER_CALLER_MODE` (#2582). In trigger-only mode, and when the variable is absent or empty, current-head clearance, an existing same-head author trigger, or a content-free automatic trigger emits `authorized: false` with its reason and exits nonzero. In polling mode, current-head clearance refuses, and so does an unanswered pending request on the current head (#2664): `pending-request-running` when Codex's Review Summary reports it Running on HEAD since it was posted, otherwise `pending-request-unanswered`. A same-head trigger that is answered or provider-blocked does not refuse a polling-mode new request, because a new round needs a new request. Any other mode value fails closed. The eyes-ack retry names no mode, so its authorization still refuses it as `existing-trigger` and the duplicate-refusal recovery above keeps polling without spending a request. Fresh explicit requests still authorize through the existing governing budget, feedback and expected-head fences; automatic-only suppression does not affect explicit requests. The production requester fixtures in `tests/test_codex_review_request_trigger_only.sh` cover all three trigger-only refusals, the three polling-mode refusals (clearance, a Running pending request, an unanswered same-head request), the polling-mode controls for a duplicate that predates the head and for a content-free head, the absent-mode default and an unknown mode. Moving authorization above these checks fails the refusal cases. `tests/test_codex_review_request_ack.sh` posts both polling-mode new requests through the real author wrapper.

The wrapper's authorization runs inside a per-PR request claim (#1362). `scripts/lib/gh-comment-trigger-guard.sh` takes an exclusive `flock` on a per-repository, per-PR lock file before invoking `--authorize-trigger-write` and keeps it until the comment POST has returned and the posted comment id has been read back as an exact request by the configured author on that PR. The requester passes the request generation its request was decided on in `MERGEPATH_CODEX_TRIGGER_OBSERVED_GENERATION` (the sorted author request ids from `crqe_trigger_generation`): for a new request, the generation its pre-flight scan recorded (`generation` in the scan), so a caller that decided before another posted cannot adopt the newer generation from a later read; for an acknowledgement retry, its write-boundary read. The authorization pass refuses with `concurrent-request` when its own read differs or the value is absent. Without that fence, a polling-mode requester that waited for the claim would be authorized for a second request below the ceiling, because polling mode does not refuse an existing same-head trigger. A refused new request exits `3` without posting and names the request that posted first. The claim fails closed when the lock cannot be opened, confirmed (the path still names the locked inode and a second open cannot take it) or obtained before the timeout, when a trigger write is nested inside a held claim, and when the readback does not confirm the posted id. It is released by the kernel when the wrapper exits, so a crashed or refused writer leaves nothing behind. The read-only recount runs in a command substitution whose own shell closes fd 9 first (a `cmd 9>&-` redirection alone would leave it open in that shell), so a killed wrapper cannot leave a hung recount holding the claim. The POST and the id readback inherit it on purpose: a child that can still write keeps every other requester out until it ends, so killing the wrapper mid-POST cannot let a second request land beside the first. It coordinates only guarded requesters on the same machine; a direct out-of-band request is counted from the timeline afterward, never blocked, and two machines are not serialized. `tests/test_gh_comment_trigger_guard.py` holds two real wrappers at the recount, the POST and the id readback and shows that exactly one posts, and covers per-PR scope, release on refusal, release when the wrapper is killed at its recount while the recount child still runs (red under the bare `9>&-` form), and, when it is killed at its POST (native and REST) or readback, a second requester that waits until that child ends and then refuses, so at most one request lands (red when the writing child closes fd 9), the REST transport and each fail-closed case. `tests/test_codex_review_request_ack.sh` races two real requesters through the real wrapper in both request modes, and holds one requester between its decision reads and its write-boundary read while the other posts (the staggered interleaving); naming the write-boundary generation instead turns that case red with two triggers. `tests/test_codex_review_request_trigger_only.sh` covers the stale and absent generation refusals.

The polling requester's run reporting (#2664) reads only `crqe_select_codex_run_state`: the exact-head Codex Review Summary row updated at or after the request's own `created_at`, classified `running`, `completed`, `failed` (Failed/Error), `canceled`, `unknown` (any other status text) or `none` (no row since the request, including an older placeholder), plus a provider-stated retry window parsed in seconds, minutes, hours or days (a fraction rounds up, and an unreadable window reads as a year, so it can never shorten a wait). The scan also reports `overlapping_request`, which is true when another author request on the head overlaps the one waited on. "On the head" uses only the proven head transition, the latest force-push when it put HEAD in place, never the committer date or a workflow run (a run can be created after requests on the head); with none, every overlapping author request counts. The requester then reports `ambiguous` in place of any running or terminal state, because the row names no request. It does the same when the scan selects a newer author request than the one waited on (#2791), whatever the row says or with no row at all, and at the end of that wait it exits `3` with `codex_run.handoff: "superseded"` and no marker. A HEAD-anchored Codex signal in that case still exits `0`, reported `ambiguous` with `superseded_by` set. Once any scan has seen the newer request, during the eyes-ack wait or the poll, the run stays superseded even if that request is later edited or deleted, because the newer run may still be active. The requester records the state at 300 seconds and at the end of the wait. It never posts, retries or cancels on it, because no request-specific terminal evidence exists. In polling mode, `resume_pending_codex_request` holds the latest exact author request on the current head while it is unanswered, has no provider block and is tied to the head. A strong tie (posted strictly after the latest force-push, whose `afterCommit` is HEAD) holds it to its deadline, and its expiry records the timeout. The exact-head Running summary holds it only within its wait, and its expiry is reported as unattributed. With neither tie, a new counted request posts. An unreadable force-push timeline is not absent evidence: the read is retried once and then exits `3`, never posting beside a request that may be strongly tied. An edited comment (`updated_at` differs from `created_at`) is never held: its deadline would run from a time its command did not exist, so a new counted request posts. At the request ceiling the #813 cap path keeps precedence.
