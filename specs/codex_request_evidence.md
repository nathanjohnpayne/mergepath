`codex.max_review_rounds` is an enforced, per-PR cap on new author-attributed exact `@codex review` request attempts. The requester counts complete, paginated issue-comment history by deduplicated comment ID immediately before each new trigger write, including an acknowledgement retry. It defaults to `10`; an unreadable or malformed qualifying record refuses the new request. When an initial request consumes the final slot, a missing eyes acknowledgement suppresses its retry but preserves the already-posted request's ordinary bounded review poll. Current-head clearance and same-head idempotent reuse occur before this check and keep their existing behavior. The cap does not reconstruct provider responses: a clean response may be a mutable summary or a reaction, and an orphan automatic provider review is not an additional requester call.

If a later invocation reaches the cap before it posts an initial request, the requester exits `7` (`CAP_EXHAUSTED`) with its ordinary observation fields and a `cap_exhausted` object containing the consumed and configured counts. Its `observed_provider_block` preserves any current `usage_limit` or `not_connected` scan result as diagnostic context only; top-level `blocked_reason` stays null, so the cap cannot acquire Phase 4b routing authority. It posts no trigger or timeout determination and does not route the PR to Phase 4b or grant clearance. This no-write stop precedes feedback accounting; when a request slot remains, the existing accounting gate still runs before any trigger write. The caller retains its already-selected advisory or required review policy; the cap does not classify the PR, route it, or create or remove a merge hold. This requester-specific exit is distinct from `scripts/phase-4b-review.sh` exit `7`. Invalid policy and unreadable or malformed request evidence remain exit `3` infrastructure failures; only a valid observed cap is exhaustion. The special final-slot acknowledgement-retry case suppresses only the retry and continues polling this invocation’s already-posted request. At the cap, normal mode may also poll a fresh exact author request left unanswered by a trigger-only invocation or interrupted process, without posting or retrying. It returns a received response normally; a bounded wait without a response returns the cap outcome, with no timeout determination or fallback authority. An existing terminal signal is never mistaken for an unanswered request.

The configured cap accepts one to nine decimal digits, including zero; invalid values refuse new requests without changing no-spend paths. This bounds the requester's observed PR history at its write boundary. It adds no cross-process lock, immutable ledger, cross-provider budget, or cross-PR lifetime budget; simultaneous callers can still race between reading the count and posting, and commands outside this requester remain outside its enforcement.
