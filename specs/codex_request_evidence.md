# Blocked Codex request evidence (#1276)

The normal external merge-clearance delegate opts into informational request evidence on approval/external-clearance blocks. The existing BLOCKED reason, approval and clearance predicates, exit statuses, carry-forward, query modes, readiness and successful paths remain unchanged. No acknowledgement reads occur outside this opted-in block path.

Merge-authoritative issue-comment verdicts require every `Reviewed commit` anchor to equal the full 40-hex HEAD (#1752). Provider abbreviations are normalized only when GitHub's trusted revision API uniquely returns a full Commit ID, with no exact hex-named branch or tag shadowing the prefix. Each scan batches at most the 50 most recently occurring distinct prefixes into one bounded API request; a prefix-specific error grants that prefix no clearance, and an unreadable response grants none. Ambiguous prefixes, malformed values and conflicting fields grant no clearance. The shared read-side resolver serves the requester, merge checker, carry-forward and retrospective audit; the final selectors still compare full IDs exactly. Same-content carry-forward verifies the resolved source ID. The ledger may retain abbreviated anchors as historical observations without granting merge authority. Coverage uses the real production selectors and hermetic API-boundary fixtures.

A diagnostic trigger must have the exact `@codex review` body emitted by the request helper and qualify by the existing configured-author and freshness predicate; it has no immutable SHA attribution. Later prose or quoted mentions do not replace it. Separately, trigger-only request deduplication treats only a freshness-qualified author comment whose complete body is that command, matched case-insensitively, as durable duplicate evidence. Prose or quoted containment alone does not suppress the requester's exact POST; it can still cause provider activity and is not evidence that nothing is in flight. Select the latest qualifying comment, report its source timestamp and age, and check the configured bot's eyes reaction on that exact comment at or after its creation. Report configured acknowledgement/review budgets, including the requester's 30/1800-second defaults for omitted fields (#1550; 840 before it), without claiming an active waiter, remaining retry count or a new deadline. Unreadable acknowledgement evidence and unavailable/invalid timing or invalid budgets are unknown, never absent.

Use the existing current-head review/verdict/summary observations and account-block evidence. Provider activity without a qualifying author trigger is still activity; do not claim nothing is in flight or recommend a retry from missing request evidence. A terminal artifact or completed summary without required approval retains the unmet-clearance diagnosis; only a running summary advises monitoring progress. This adds no trigger, retry, new signal grammar, reaction carry-forward, workflow or persistent state. Coverage: `tests/test_codex_request_evidence.sh` plus existing request/ack and merge-clearance suites.

`codex.max_review_rounds` is an enforced, per-PR cap on new author-attributed exact `@codex review` request attempts. The requester counts complete, paginated issue-comment history by deduplicated comment ID immediately before each new trigger write, including an acknowledgement retry. It defaults to `10`; an unreadable or malformed qualifying record refuses the new request. When an initial request consumes the final slot, a missing eyes acknowledgement suppresses its retry but preserves the already-posted request's ordinary bounded review poll. Current-head clearance and same-head idempotent reuse occur before this check and keep their existing behavior. The cap does not reconstruct provider responses: a clean response may be a mutable summary or a reaction, and an orphan automatic provider review is not an additional requester call.

A second budget is checked first at the same write boundary (#1560 slice 3). `codex.max_blocking_reviews` (default `10`, provisional) bounds the PR's solicited blocking Codex reviews, counted from the Codex review ledger as `specs/codex_review_ledger.md` § Consumer describes. A new request is refused once that count reaches the budget, so a budget of 10 permits a request at 9 and refuses one at 10 or 11. The value is read from the same governing base policy with the same digit validation. A missing, failing or malformed ledger exits `3` with no write, as does one for another head, author or policy snapshot (`--expect-policy`, `crqe_policy_fingerprint`). The governing budget output carries that `policy_fingerprint`. An acknowledgement retry is not re-checked, and the idempotent skip (a fresh request already on the head) never runs the ledger. At a spent request ceiling the ledger still runs before the ceiling is reported, so that the blocking budget can take precedence. There, a missing or malformed ledger exits `3` rather than `7`. The stop is the exit `7` described next, with `cap_exhausted.kind: "blocking-reviews"`; when both budgets are spent it takes precedence over the request ceiling.

If a later invocation reaches the cap before it posts an initial request, the requester exits `7` (`CAP_EXHAUSTED`) with its ordinary observation fields and a `cap_exhausted` object containing `kind` (`"request-ceiling"` here, `"blocking-reviews"` for the budget above) and the consumed and configured counts of both budgets (`blocking_reviews` and `max_blocking_reviews` are null when the blocking count was not taken). Its `observed_provider_block` preserves any current `usage_limit` or `not_connected` scan result as diagnostic context only; top-level `blocked_reason` stays null, so the cap cannot acquire Phase 4b routing authority. It posts no trigger or timeout determination and does not route the PR to Phase 4b or grant clearance. This no-write stop precedes feedback accounting; when a request slot remains, the existing accounting gate still runs before any trigger write. The caller retains its already-selected advisory or required review policy; the cap does not classify the PR, route it, or create or remove a merge hold. This requester-specific exit is distinct from `scripts/phase-4b-review.sh` exit `7`. Invalid policy and unreadable or malformed request evidence remain exit `3` infrastructure failures; only a valid observed cap is exhaustion. The special final-slot acknowledgement-retry case suppresses only the retry and continues polling this invocation’s already-posted request. At the cap, normal mode may also poll a fresh exact author request left unanswered by a trigger-only invocation or interrupted process, without posting or retrying. It returns a received response normally; a bounded wait without a response returns the cap outcome, with no timeout determination or fallback authority. An existing terminal signal is never mistaken for an unanswered request. If the selected final request already has a validated exact-head timeout determination, normal mode preserves its existing exit `4` and marker ID without another poll or write. The live head and selected request ID must still match; stale or superseded markers add no authority, and malformed trusted evidence fails closed. Later provider signals retain their existing precedence.

In polling mode the requester resumes rather than re-posts an unanswered request (#1550). Because a trigger names no commit, freshness alone never attributes it to the current head; resuming additionally requires the provider's Review Summary to report a Code Review Running on the exact current head, updated at or after the pending request. The pending request is the latest exact configured-author command with no freshness anchor (the reaction-freshness floor may be shorter than the reply deadline, and the head-push anchor falls back to an author-controlled committer date); its own deadline bounds staleness and the exact-head Running summary binds it to the head. It must not already be answered, provider-blocked, or bound to a current Phase 4a timeout determination. The resumed wait ends at that request's creation time plus `review_timeout_seconds`, and the exit decision anchors on the resumed request exactly as on a posted one. A resumed request grants no timeout authority: if its wait expires unanswered, the requester re-executes itself as a fresh invocation with resume disabled, so the replacement re-reads the live head, starts its own clock and goes through the ordinary path (including the cap check), and only a request that run posts may write a timeout determination. Without the provider evidence the requester posts as before, but unreadable evidence is not absent evidence: the resume read retries a transient failure and then exits `3`, and malformed selector output or trusted timeout-marker evidence exits `3`, rather than posting a duplicate into a review that may be running. Post-trigger scans retry a transient read failure (a fetch failure whose gh diagnostic names HTTP 5xx, 429 or a rate-limited 403, or names no HTTP status) a bounded number of times before exiting `3`; a permanent failure, a failure with no diagnostic, or an unflattenable response exits `3` at once.

The configured cap accepts one to nine decimal digits, including zero; invalid values refuse new requests without changing no-spend paths. This bounds the requester's observed PR history at its write boundary. It adds no cross-process lock, immutable ledger, cross-provider budget, or cross-PR lifetime budget; simultaneous callers can still race between reading the count and posting, and commands outside this requester remain outside its enforcement.

The automated Phase 4b same-head barrier reuses the governing-budget resolver, exact-author command counter, and freshness-anchor helper when Codex has not reported and no trusted timeout already authorizes the existing fallback. A budget with room keeps the ordinary bounded hold. At the cap, a still-fresh final request may use that same hold without creating a timeout. If the hold expires, or no eligible final request exists, the barrier evaluates the human stops (#1560 slice 3; REVIEW_POLICY.md § Disagreements and Tiebreaking, signal 4). With none, it waives the Codex arm and the adapter runs, unless `codex.allow_phase_4b_substitute` is false: that review could not clear gate (c), so the run escalates to the manual Phase 4b handoff (exit `4`). With any stop, the orchestrator exits `8` with `human_tiebreaker_required: true` before adapter dispatch and without rendering the manual Phase 4b handoff. The orchestrator re-reads the ceiling and the stops after the adapter and before any review is posted. A current-head provider report wins before this check, and an already-recorded trusted timeout retains its established fallback behavior. Unreadable governing policy, incomplete timeline evidence, selector failure, or head movement exits `10` without adapter or handoff authority. Wave audit treats both exits as no-fan-out states.

A verdict grants clearance only when every complete Reviewed commit field equals the full 40-character current head. A newer negative verdict with a missing, empty, unresolved abbreviated, malformed or conflicting anchor remains a non-clearance observation in latest-signal ordering and raises the Phase 4b freshness floor. A complete valid anchor naming only another head does not invalidate this head. Neither an ambiguous anchor nor a later timestamp grants clearance.
