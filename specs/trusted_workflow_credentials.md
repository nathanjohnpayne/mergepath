# Trusted workflow credential boundary

Issue [#1547](https://github.com/nathanjohnpayne/mergepath/issues/1547) delivers a source boundary and an owner-run migration plan. Source delivery and metadata audit results are not proof of remediated live exposure. Candidate-controlled PR/review definitions carry read-only workflow tokens and no standing authority-secret expressions. Privileged execution uses trusted default-branch definitions and trusted checkout bytes; candidate revisions, filenames, diffs, artifacts and metadata remain inert inputs. The trusted consumer validates the intended repository and immutable PR/head/base/source binding before acquiring authority and repeats the existing live writer checks. No candidate workflow, helper, package or action is executed with authority credentials.

## Existing producers and mutations

Native Self-Review Required and Label Gate remain on the original PR trigger/head lineage, read metadata and labels, and retain their gate semantics. The trusted policy consumer executes the same classifier extracted from the trusted native definition. Its policy-created labels/comments keep github-actions ownership because existing fail-closed reconciliation and Dependabot pin-lane predicates require it. The selected-repository automation App performs only existing event-producing mutation duties, including label removal and propagation nudges; it has no registered reviewer standing and never approves or merges. Delayed review events retain their historical identity for archival and self-approval enforcement. Disagreement-label classification reads the live PR head/base instead and repeats that pair immediately before applying a new hold; drift or an unreadable binding preserves the existing label state. Agreement never removes an existing `needs-human-review` hold: the governing policy requires human release. These observations do not make the GitHub write atomic.

The existing Codex archive handoff/relay is generalized under the owner's [first additional scope decision](https://github.com/nathanjohnpayne/mergepath/issues/1547#issuecomment-6193479998). Format, source verifier, exact head/fingerprint, gate predicate, required context/app15368 and backstops remain intact. Same-repository events adopt the existing native Codex-name exception, with the disclosed delivery-availability cost. Old native failures require an actual native recovery or a new head; API success does not retire them. MCG/CodeRabbit native predicates and the existing trusted synthetic publisher remain separate, as specified in [required check publication](required_check_publisher.md). The source boundary composes with #906's existing canonical owned-generation writer and paired reader without adding a publication or attribution/release channel. Candidate jobs remain read-only; the early trusted pending hold and its exact parent-run/attempt/head proof remain distinct from a trusted evaluator's owned completion.

Auto-clear separates its existing queue/protective phase from the App's label writer. Only PR/full-head/base tuples cross jobs. The label writer re-runs the existing gate or pin-only proof, requires the protected tuple, refuses a newly appeared ordinary durable merge arm, and retains the exact live head/base and label-owner fences immediately before DELETE. The native Dependabot arm remains owned by its separate lane. Existing queue continuation independently revalidates its full policy and writer checks; a tuple is never a cleared/merge authorization. Dependabot reviewer approval and governing-author merge use separate protected jobs. Approval checks reviewer identity, commit provenance, the current head/base binding and human holds, then reads back the exact-head approval; it does not evaluate CI or feedback accounting. The merge phase revalidates governing-author identity, provenance, the current binding, approval, CI, merge clearance and human holds before requesting `--auto`; GitHub then enforces the required checks. Only the immediate fallback, used when auto-merge is unavailable, explicitly runs feedback accounting and the native/API approval-readiness gate before repeating the merge writer fences. These are the inherited phase-specific semantics; the credential split adds no new approval or merge authorization.

Derive each repository’s required destinations from its actual installed/carried job bindings; hub-only audit/proof jobs do not justify creating unused consumer environments or credentials. Each required environment permits only a custom literal-main branch policy, with administrator bypass disabled. The queue retains its existing no-reviewer/no-wait requirements. Do not activate a queue or provision unused queue credentials for this ticket. The audit/proof/maintenance workflows retain their existing triggers, identities and trusted checkout; environment restrictions also protect externally selected dispatch refs. No author PAT is loaded into the 1Password proof.

## Owner activation, readback and rollback

Before merging or otherwise activating source references, the owner must create/protect every missing destination and positively read back its policy. GitHub [automatically creates a referenced nonexistent environment without protections or secrets](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments); source activation is therefore gated on this owner-performed preparation, not permission for an agent to create settings implicitly. Same-named repository secrets remain a fallback until the owner verifies environment replacements and removes their repository copies. No new activation flag/controller is required. Where a consumer-owned `REVIEW_POLICY.md` enumerates the sanctioned label-removal workflows, reconcile the moved writer pointer to `trusted-pr-policy.yml` before that carrier activates; preserve exactly the existing two automation lanes and the interactive-agent prohibitions. Those owned policies are not overwritten by canonical propagation.

After the reviewed source is active, the owner provisions from the credential manager directly to the intended destination, verifies positive trusted runs and the complete source-binding matrix, then removes individually verified repository/organization shadows. Enumerated names are AUTHOR_MERGE_TOKEN, CI_ACTOR_TOKEN, REVIEWER_ASSIGNMENT_TOKEN, CLAUDE_PAT, CODEX_PAT, CURSOR_PAT, BRANCH_PROTECTION_AUDIT_TOKEN, OP_SERVICE_ACCOUNT_TOKEN and any queue policy/source shadows. The App private key must never exist at repository/organization scope. Obsolete per-agent copies have no replacement only after refreshed installed-source and inherited-secret metadata prove no remaining reader. Unrelated deployment/API secrets stay outside this removal operation.

Read back complete secret-name inventories and each protected environment, actual positive workflow identities and full-head check lineages after changes. Run the existing read-only isolation audit for every environment actually required by that repository’s bindings; audit PASS does not establish App scopes, independent reviewer attribution, queue readiness or consumer acceptance. The propagated site requires its own installed revision and actual post-execution readback. Security Cloud disposition stays owner-only.

Rollback stops affected automation and holds affected PRs while the owner repairs reviewed source/environment configuration. Do not restore broad repository copies, substitute an author/reviewer PAT into App automation, relax protections, reset review counters, deploy or rotate credentials as an automatic recovery. Shared-author policy and ordinary model-authoritative Phase4b remain unchanged; #2129 preparation does not implement live isolation or a new release channel.
