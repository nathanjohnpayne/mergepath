# Required Check Publisher

`.github/workflows/required-check-publisher.yml` is the consolidated refresher of the **synthetic** (Checks-API) lineage for the three script-backed required contexts — `Merge clearance gate`, `Codex P1 unresolved threads`, and `CodeRabbit unresolved blocking findings`. It exists because those contexts previously had two producers per workflow file, both reporting as `github-actions` and neither able to retire the other's entries, which stranded fully-cleared PRs behind stale verdicts (#835, #828, #842) and forced empty commits as the only universal escape. This spec states the publisher's behavioral contract in full. One source of truth: a change to the publisher's behavior belongs in this file, in the fence, and in the fixtures, in the same diff.

## What the fence pins, and what it does not

The contract stated below is larger than what `scripts/ci/check_required_check_publisher` currently enforces, and the boundary is deliberate rather than incidental. **Every property the fence pins is decided over the parsed workflow document, with exactly one disclosed exception** — the head-binding *site* scan under *Head binding*, which reads the file's shell text because a `head_sha` binding has no YAML-level expression to read. Test 25 in `tests/test_merge_clearance_gate.sh` proves each pin rejects the shape that loses it: every failure the fence can emit has a mutation case that trips it *and names its own cause*, so no assertion here passes vacuously. That is the whole of the enforcement claim; a spec sentence is not evidence that anything checks it.

Parsing the document is necessary and not sufficient — the fence has to parse it the way **Actions** parses it, and two classes of divergence were live findings on the introducing PR. PyYAML applies YAML 1.1 boolean resolution, so the plain mapping keys `on`, `On`, `ON` and `true` all construct to one indistinguishable value, while Actions is case-sensitive and reads the exact string `on`: a document respelled `On:` carries no trigger definition at all, yet a value-keyed check still finds a trigger mapping and passes it. The fence therefore keys every mapping on its **raw scalar text**, which is Actions' own semantics — a workflow mapping key is a string, never a boolean and never a number — and `"on":` stays the same key as `on:`. Separately, an assertion scoped to *the keys it names* is silent about the keys it does not: pinning `workflows` and `types` under `workflow_run` says nothing about a `branches:` filter added beside them. Mappings whose additions are dangerous are therefore pinned **whole**, as an exact key set, because an absence has no positive spelling to test for.

The publisher fence pins the complete `open` permission map (`contents`, `pull-requests`, `actions`: `read`; `checks`: `write`) and complete `publish` map (the same scopes plus `issues` and `security-events`: `read`). Missing, added and changed scopes fail with the job and scope named. Every other publisher job is prohibited from granting `checks: write`, including through `write-all`. The consuming phase-1 step must bind `GH_TOKEN` exactly to `${{ secrets.GITHUB_TOKEN }}` alongside its existing exact head binding. Test 25 mutates every required scope, extra scopes/writers, and absent or changed phase-1 tokens.

The publisher fence rejects any `concurrency` key at the workflow root or on each native producer job: `merge-clearance-gate`, `codex-p1-gate` and `coderabbit-severity-gate`. The check tests key presence, including a null value, because a cancelled native required check cannot be retired by the synthetic publisher. Test 25 exercises both placements in each workflow and null-valued keys.

The same reasoning governs presence. An assertion written as *"if this key is here, it must equal X"* is disarmed by deleting the key rather than tripped by it — the defect that let a one-line deletion from the parent workflow silently disable the parent-name check, and that recurred in two more places. Keys the contract requires are pinned as **required and exact**, so the deletion direction fails as loudly as the wrong-value direction.

The exception is stated rather than smoothed over because it carries a real residual. Scanning text rather than parsed shell arguments means a `-f head_sha=…` token in a here-document, a diagnostic string, or an unrelated command counts toward the pinned site total, so non-binding text could in principle backfill the count for a removed binding. The allowlist and the count still make a *new* or *respelled* binding site arrive as a conspicuous diff, which is what the assertion is for; what it cannot do is prove the tokens it counted are the arguments the POST actually uses. Restricting it to parsed shell arguments needs the same substrate as everything in #977, and it is tracked there with them.

**Not pinned, and tracked in [#977](https://github.com/nathanjohnpayne/mergepath/issues/977):** every property whose subject is the shell inside a `run:` body — which step opens the hold and whether it iterates all three contexts and POSTs; the count of `conclusion="success"` assignments; the read-then-write ordering of the freshness read and the head revalidation against the verdict POST — plus a job natively named for a required context, because `name:` may carry a `${{ }}` expression Actions evaluates and this fence cannot. Four review rounds on the introducing PR (#974) each found a *new spelling* of the same hole in the text-matching versions of these, which is the #849 non-termination signature; they return on a parsed shell AST rather than as a sixth regex. **Also not pinned, tracked in [#976](https://github.com/nathanjohnpayne/mergepath/issues/976):** the dataflow residual described under *Head binding*.

Stage A shipped the publisher under shadow context names that were not in branch protection, so nothing it published could affect a merge. Stage B promotes only the three context-name values; the structural fence remains name-agnostic, and the disclosed semantic residuals stay tracked in #976 and #977 rather than being smuggled into the promotion.

Nothing here describes the **native** lineage — the check run Actions materialises for each job. That lineage is retained deliberately and is out of the publisher's reach; see *Two lineages*.

## Two lineages, and why the native one is retained

Each required context has two independent producers, and under the resolution rule this repo has measured four times, the newest run of **each** must be green. The job-native lineage puts one suite per workflow run, with runs superseding each other across suites; the Checks-API lineage puts one shared suite per head, where the newest POST wins.

**A pending clearance verdict does not fail the job-native `Merge clearance gate` run (#2247).** Whatever the rule for the job-native lineage, an earlier failed job-native run in another check suite is not retired by a later green one in practice (measured on #2232: 18 such failures held a cleared head BLOCKED until each was rerun), so every review event during a Phase 4 review used to leave a failed run that had to be rerun after clearance. The event-driven job of `merge-clearance-gate.yml` concludes its job-native run non-failing only when `scripts/merge-clearance-gate.sh` reports the explicit pending verdict (through `MERGEPATH_GATE_VERDICT_FILE`, never its output), the job opened its own Checks-API hold, and `scripts/gate-api-lineage-blocking.sh` confirms that every current Checks-API run of the context on the head blocks and none shares the job's check suite. The second condition matters because the shared Checks-API suite is whichever suite was created first on the head: if that were the job's own suite, a non-failing job-native completion could compete with the Checks-API runs for the latest run of that suite. This publisher is unchanged by it. It never names a verdict file, maps the pending exit (rc 1) to a red verdict as before, and is therefore what keeps a pending head blocked; `tests/test_required_check_publisher_summary_hold.sh` pins that. `CodeRabbit unresolved blocking findings` has no pending verdict and keeps failing its job-native runs on every non-green state. `Codex P1 unresolved threads` has one narrow pending verdict (#2618): its event-driven job concludes its job-native run non-failing only when the only blocker is a non-blocking finding awaiting disposition, the gate script has ruled out every blocking-tier finding, the snapshot driver published that attempt as a red lease, and the same lineage helper confirms the block (REVIEW_POLICY.md § Required status checks). This publisher never names a verdict file for it either, so it publishes red for that head until the disposition exists.

"Single producer" therefore means **single owner of the synthetic lineage**, never the deletion of a natively-named job. Deleting the job named for a context does not merge the lineages — it deletes one, leaving a required context whose only producer is a workflow. If that workflow is absent from the default branch, renamed, disabled, or its `workflow_run` delivery drops, the context has no producer at all and every PR in the repo blocks forever with no partial degradation to warn anyone. The natively-named jobs keep their names and compute their native verdicts. Existing early event leases and trusted legacy refreshers remain; the #906 migration coordinates their API publications through owned generations rather than deleting native producers. Candidate-event publication authority is a separate #1547 migration, and this change adds no write scope to candidate jobs.

The structural fence also reads `pr-review-policy.yml` and rejects `schedule` or `workflow_dispatch` triggers, including quoted keys, inline mappings, sequences and scalar trigger definitions. Non-PR runs could otherwise place satisfying skipped checks under `Self-Review Required` and `Label Gate`. Missing, malformed or unreadable policy workflow input fails validation. Existing mutation coverage in `tests/test_merge_clearance_gate.sh` exercises these spellings and safe controls.

## Trust model

The publisher's definition always comes from the **default branch**: `workflow_run`, `schedule`, and `repository_dispatch` all execute the default-branch copy. A pull request therefore cannot edit the workflow that evaluates it, which is the closure for the P1a exposure — inline `gh api` calls and a `checks: write` grant sitting in PR-authored YAML.

`workflow_dispatch` is **absent by design**, not merely unused. A manual dispatch executes the *selected ref's* copy of the file, so a PR branch could be run with `checks: write` — P1a through the manual path. The operator break-glass is the `required-check-republish` `repository_dispatch`, which is PAT-gated and always runs the default-branch definition.

`checks: write` is granted at **job** scope, never at workflow scope. A workflow-level grant hands the scope to every future job added to the file, which is how the fleet's four-workflow exposure set grew in the first place.

The publisher's **top-level keys** are exactly `name`, `on`, `permissions`, `env` and `jobs`, and the fence pins that vocabulary. Two things depend on it. It is what makes the trigger block identifiable by its own key rather than by whatever key happened to resolve alongside it, and it reaches a shape no job-scoped assertion can: a **workflow-level** `concurrency:` block queues both phase jobs — including `open`, which the section below requires to stay groupless — while every assertion scoped to a job stays green. A legitimate new top-level key is a one-line change to the pinned set, made deliberately.

## Trigger model

Two parents, by role, in a fixed order (#867, #2167). `Merge Clearance Gate` carries every **review-side** refresh signal: its trigger set is a measured strict superset of both sibling gates' (it adds `labeled`/`unlabeled` and `repository_dispatch`), so a single delivery per PR event covers all three contexts and the per-event fan-in stays at one pass instead of three. `repo-lint` is the **CI-side** fan-in. None of the three contexts reads `lint` — `scripts/merge-clearance-gate.sh` deliberately skips `codex-review-check.sh`'s CI gate (a), because a required check that waited on the required-check rollup would deadlock on itself — so a `lint` completion changes no verdict. What it changes is the merge decision: `lint` is normally the last required context to land, and before #2167 nothing re-published the three slots for that head once it did, so the newest entry was whatever the push-time or approval-time pass had written, and an approval-fired gate run could sit in the Actions queue behind 30-minute lint jobs (on #2112 it queued for 38 minutes and ran for 12 seconds). Listening to `repo-lint` completion re-publishes a fresh, head-pinned verdict within one publisher pass of `lint` landing, for every open PR head regardless of label state, and no job anywhere reserves a runner while CI executes. The two activity roles differ per parent: `open` admits only the gate parent (a `repo-lint` `requested` arrives at push time alongside the gate's own and would duplicate it, and on a lint rerun it would pend three lint-independent contexts for the whole run), while `publish` admits a `repo-lint` parent only when that lint run's own event was `pull_request`. That second filter is the main-SHA confounder: `repo-lint` also runs on `push` to `main`, so a merge floods `completed` deliveries whose `head_sha` is `main`'s tip; those match no open PR, and because a member that enters the `rcp-publish` queue must run the full coalescing pass (and can cancel the pending member), the filter has to live at the expression level so those runs never enter the queue. A `pull_request` lint run whose head moved on before the pass takes the existing superseded-head path below.

`workflow_run` matches on each parent's exact top-level `name:`, so a rename on either side silently orphans every delivery from that parent — the failure mode is a workflow that never fires, which is indistinguishable from one that fires and finds nothing to do. The fence reads both expected names out of the two parent files rather than carrying copies of the strings, pins the `workflows:` list whole and in order against them, and then cross-checks the literal names inside the two pinned job conditions — the one consistent rename (parent file and `workflows:` entry together, pinned condition untouched) that would otherwise leave an `if:` arm comparing against a name no delivery carries. Reading the names from the files means a *missing* name must be as loud as a mismatched one: a parent that declares no top-level `name:` is named by Actions after its path, so the publisher's `workflows:` entry matches nothing and every delivery from that parent is orphaned. The fence therefore tracks whether each parent file loaded separately from the name that load yielded, because both an unreadable parent and a nameless one produce no name, and treating them alike lets a one-line deletion disarm the assertion instead of tripping it.

The three activity types have distinct roles. `requested` fires at parent-run creation, before its jobs execute, so holds land within seconds of the PR event. `in_progress` is the **rerun** cue: a rerun re-uses the run, so `requested` never re-fires and the re-evaluation window would otherwise carry no pending cover. On an ordinary first attempt, `in_progress` also acts as a fail-closed backup for a delayed, failed, partial or racing `requested` job. It skips its remaining work only when the parent-status guard does not report completion and one paginated Checks API read proves that the newest server-started entry for each context is pending with the exact parent-run-and-attempt marker and the `github-actions` producer slug used by this workflow's `GITHUB_TOKEN`. A failed parent-status read retains the existing fail-closed path; it is not evidence that the parent remains active. Same-name entries from another attempt or another producer, a newer completed entry, partial publication and an unreadable probe do not satisfy the pending proof. `completed` is the publish cue. The publisher never reads `workflow_run.conclusion` — deliveries drop and that field can be null upstream, and the verdict must not depend on how the parent finished; every pass re-evaluates from scratch.

Each trigger's mapping carries **only** the keys named here — `workflows` and `types` for `workflow_run`, `types` for `repository_dispatch` — and the fence pins those key sets whole rather than key by key. The reason is that the dangerous addition is the one that leaves every named value intact: `branches` / `branches-ignore` filter `workflow_run` on the *parent run's head branch*, so `branches: [main]` keeps the parent list and the activity types exactly as the contract states them while no PR-head delivery reaches the publisher again. Every phase stops at once — no hold is opened on `requested`, none is retired on `completed` — and the three contexts sit pending or stale with nothing in the repo going red.

The two phase jobs' **eligibility** is part of the trigger contract rather than an implementation detail, because it is what splits one delivery stream into the two phases, and the two sets are **disjoint**: `open` runs on the `workflow_run` `requested` and `in_progress` deliveries of the gate parent; `publish` runs on `workflow_run` `completed` deliveries (any gate delivery; a `repo-lint` delivery only for a `pull_request` lint run) and on every non-`workflow_run` delivery. `in_progress` is the rerun cue and belongs to `open` alone — a `publish` that also ran on it would overwrite the rerun's own hold before the parent finished evaluating, which is the stale-verdict window the hold exists to close. Neither job may declare `needs:`. They run on disjoint deliveries by construction, so a dependency between them is never satisfied — and a skipped dependency skips its dependent, which means `needs: open` on `publish` reads as harmless, leaves every other value in the file intact, and silently guarantees that no verdict is ever published while every hold phase 1 opened stays pending. The fence pins both conditions verbatim rather than screening them for conditions Actions cannot satisfy: screening cannot terminate against non-literal impossible conditions, and pinning states the narrower claim it can actually keep — that the condition deciding whether each phase runs is the reviewed one, and any change to it, equivalent or not, arrives as a diff.

The publisher holds **no runner while CI executes** (#2167). Every job evaluates once and exits; the only loops in the file are `read` loops over enumerated PRs and bounded three-attempt API retries. The fence rejects any other `while`/`until` loop at statement position and any `--watch` in either phase job's `run:` bodies — a text-level assertion with the same disclosed residual as the head-binding site scan (a wait respelled as a bounded `for` with a long `sleep` passes; #977's parsed-shell substrate is where that closes). The two spellings that have actually shipped in this repository (#1062 finding 5) cannot return silently.

The publisher carries **no schedule of its own** until #845 PR 4. The parent's `*/30` cron (`*/15` until #2167) already reaches it through the `workflow_run` chain (a schedule-parent delivery whose head matches no open PR degrades to a full-coverage pass), so an own cron would run a second full-fleet pass every interval for nothing. PR 4 re-adds it in the same diff that deletes the three gate workflows' schedules, so every stage keeps exactly one cron path.

The gate parent's own `scheduled-sweep` job still evaluates `scripts/merge-clearance-gate.sh` for every open PR on the same tick and writes the same Checks-API slot the chained pass then overwrites, about 147 installation-budget requests per tick at 8 open PRs. #2220 asked for that duplicate to go, and it is deliberately kept: a deferral decided before the gate run completes (by the publisher's file, or by its workflow state) cannot prove that this tick's `workflow_run` delivery will arrive, and a dropped delivery is one of the transitions the sweep exists to cover. Removing it needs a delivery-independent scheduled path, which is the publisher-owned cron of #845 PR 4; that work, together with the matching change for the Codex P1 and CodeRabbit sweeps, is tracked in #2224.

Chain depth is bounded but is **not** a reason to forbid observers, and the earlier wording here claimed otherwise. GitHub documents the limit as three levels of chained workflows and illustrates it with `A → B → C → D → E → F`, where "workflows `E` and `F` will not be run" — so `B`, `C` and `D` all run. The `Merge Clearance Gate` and `repo-lint` are directly triggered (`A`), the publisher sits at `B`, and a workflow observing the publisher sits at `C`: inside the cap, and it runs. What actually truncates is the *fourth* chained workflow, so the constraint binds an observer's own downstream, not the publisher. What the cap does not decide, the design does: the publisher stays **unobserved** via `workflow_run`, by owner decision on [#1670](https://github.com/nathanjohnpayne/mergepath/issues/1670) (2026-10-21). That is an architectural choice, not a consequence of the chaining cap. A publisher run concluding `success` means only that a pass finished; it says nothing about which verdicts it posted or whether the head is still live, so an observer keyed on it would read a pass outcome as a PR outcome. The one downstream consumer that needs the publisher's results gets them through the explicit path under *Auto-clear nomination*: a dispatch naming the PR, after which the receiver re-derives clearance itself and acts only if the head/base pair is still live immediately before it writes. That path stays as it is. A read-only observer is reconsidered only for a concrete use case that path does not meet, and publisher success must never be treated as PR clearance or merge authorization by any observer. The fence does not assert the absence of observers; the earlier blanket assertion (A7) was removed because its stated cause was false, and this decision does not restore it.

## Head binding

Every published `head_sha` binds to `github.event.workflow_run.head_sha` or to a shell variable derived from the open-PR list read. The event-side half of that is two step `env:` bindings — `HEAD_SHA` in `open`, `RUN_HEAD` in `publish` — and each is pinned as required-and-exact rather than checked-where-present, because the shell-side allowlist cannot cover a deletion: the POST would still name an allowlisted variable, now unset, the site count would be unchanged, and the publisher would open every hold on an empty `head_sha`. **Never `github.sha`**: on a `workflow_run` run that is the default branch's last commit, so one such binding puts all three contexts on a commit branch protection never consults — absent on every PR head, fleet-wide, permanently, with no partial degradation. The fence expresses this as an allowlist over every binding **site** — every argument that binds the Checks-API `head_sha` field, under any gh-CLI field-flag spelling (`-f`, `-F`, `--field`, `--raw-field`, quoted whole-argument or quoted value) — rather than as a denylist of wrong spellings, because `github.sha` → `base.sha` → literal-prefixed strings cannot be enumerated. The number of binding sites is pinned alongside the allowlist, so a new POST cannot arrive without its head binding being read. What the fence does **not** assert is the value an allowlisted variable holds when the POST runs: reassigning one immediately before the POST rebinds it without touching any binding site. That residual is a dataflow property, not a spelling, and closing it would require interpreting the shell rather than reading it.

Head-to-PR resolution comes from the open-PR list, exhaustively paginated, and never from `workflow_run.pull_requests`, which is empty for fork PRs. A capped list would silently exempt every head beyond the cap from both phases.

## Phase ordering

**Phase 1 (`open`)** POSTs an `in_progress` entry per context on the event head before any evaluation work. That ordering is the whole fail-closed argument: everything after that line — checkout failure, head resolution failure, a gate script crash, runner death, a dropped `completed` delivery — leaves the context *pending* rather than leaving a stale verdict standing. A pending required entry blocks (measured: `isRequired: true`, `mergeStateStatus: BLOCKED`). A step-level `if:` on the publisher skips exactly when the run it guards is the one that needed to retire a stale verdict.

Each phase-1 POST appends the hidden summary marker `<!-- required-check-publisher:pending:<parent-run-id>:<run-attempt> -->` to its fixed pending output summary. This marker grants no clearance and is never read by phase 2; it only lets the redundant first-attempt `in_progress` delivery prove that `requested` already established all three holds for the same evaluation. It deliberately does not use `external_id`: the required-context lineage gate uses an empty `externalId` to distinguish Checks-API publisher runs from native Actions job runs. The parent-status read remains first, so a delayed runner whose parent has completed still exits after one HTTP request instead of adding a deduplication probe. When the parent is active and all three exact holds exist, the duplicate path uses two one-page HTTP reads and zero writes instead of six requests and three writes: four HTTP requests saved, while all three workflow event deliveries and both phase-1 jobs still occur. An incomplete or unreadable proof adds one read and deliberately executes the six-request open path, preserving pending coverage. Request counts treat a paginated endpoint as one request for the one-page fixture; additional real pages add one request each. The successful open path retains both pre-write parent-status checks and omits the former post-write status GET: that read only logged a completion warning and could not change the already-published holds. This saves one GET per actual hold-opening pass without changing completed publication, freshness checks, event deliveries or executed jobs.

`open` does **not** skip its holds because a newer publisher verdict exists (#2171). Under runner contention the hold-opening job can reach a runner after a lint-parent `publish` pass has already evaluated the head (the #2112 shape), and its holds then re-pend the three contexts until this parent's own completed pass re-publishes. That latency is the accepted residual. A fence suppressing the holds was tried in three forms during #2171 and each was fail-open: a Checks-API verdict's `started_at` is the time of its POST, not the time its gate script read PR state, so a pass that read state before the parent's event and posted after it satisfies any timestamp comparison and leaves a stale green authoritative while the parent is queued. Making such a fence sound would need every verdict to carry its pass's pre-read start and a shared pass identity across the three contexts; until that exists, pending is the fail-closed direction and the publisher keeps it.

`open` is deliberately **groupless**. Queued behind `publish`, its hold would wait behind a mid-flight stale pass — reversing the write order but leaving a post-green window open until the queued job reaches a runner. It also skips when the parent run has already completed, because a hold opened after the completed pass has no future event to retire it.

**Phase 2 (`publish`)** opens its own `in_progress` generation before evaluating each selected context, then PATCHes only that owned check ID. No phase-1 identifier crosses the run boundary. Selected sweep targets open generations too: a missing or unreadable report cannot leave an earlier success authoritative merely because the sweep had no event-head hold. Phase-1 holds and incomplete openings remain non-green until a newer generation supersedes them. Nothing else completes them, so a hold whose writer died stays `in_progress` and keeps the head's check suite from ever completing (friends-and-family-billing#583, 2026-10-30, where an armed auto-merge never fired). The scheduled full-coverage pass therefore runs `scripts/workflow/reap-orphaned-holds.sh` after its publish step (#2907). It closes an incomplete Checks-API run on one of the three contexts only when the run is at least an hour old and a newer run of the same name on the same head has completed. It closes the run `cancelled`, never green, so the newer completed run keeps deciding the context. The opening summary stays as the prefix of the new summary, so a writer that is still alive can still bind and close its own id.

## Ordering and the stale-write defense

`publish` carries **one fixed concurrency queue** (`rcp-publish`, `cancel-in-progress: false`), and exactly those two keys — Actions permits no others in a job `concurrency:` mapping, and an unsupported one invalidates the publisher's own definition on the default branch, after which it refreshes nothing at all. It is not a per-head group. A per-head group leaves the sweep and dispatch paths outside the serialization entirely, so an older evaluation on one of those paths could read state before a transition and POST after a newer evaluation, restoring a stale verdict. The queue is safe on this file and was not safe on the gate workflows, and the difference is measured rather than argued: when a third member queues, GitHub cancels the *pending* member and materialises that run's native check. On a gate workflow that check is named for a required context and concludes `cancelled`, which is neither SUCCESS nor SKIPPED nor NEUTRAL and cannot be retired through the API slot. Here it is named `publish`, which nothing requires. **No job whose name is a required context may ever carry a `concurrency:` block.**

Cancellation is **coalescing, not loss**: every pass evaluates every open PR (event head, or dispatch-named PR, first), so whichever member survives subsumes the work of every cancelled one.

The queue coalesces evaluation work; it is not the ordering authority. `scripts/workflow/required-check-generation.sh` creates an `in_progress` check before evaluation and closes that same ID. The opening carries a repository, PR, full head, context and trusted revision tuple. Before PATCH, the helper verifies the owned check's immutable head/name and original tuple, the current trusted default revision, the live PR head and unique open-PR ownership of that head. Changed or unreadable inputs publish failure on the owned generation; an unreadable or mismatched owned-check binding leaves the opening non-green. A failed opening authorizes no evaluation or completed POST, and failed cleanup is an infrastructure error. Early phase-1 holds retain their existing pre-checkout timing. A superseded event head keeps any incomplete phase-1 hold rather than minting a new unleased completion on an unrelated PR.

The scheduled CodeRabbit sweep retains the head it used to open its owned generation; it never replaces that binding with a second PR-head read. A concurrent head move is handled by the existing final publication fence, which closes that original generation red and discards evaluator evidence for the changed inputs. A report mismatch without final input drift still refuses publication. In the separate escalation job, a well-formed outdated report tuple skips only that nomination so later independent nominated PRs still receive their escalation. Malformed escalation tuples retain their fail-closed errors (#2412).

The paired `codex-review-check.sh` selector requests each CheckRun's server `databaseId` and selects the highest opening ID within each controlled GitHub Actions API lineage. It does not rank these generations by completion time or prefer every historical pending entry forever. Thus an older evaluation can finish after a newer pending/failing generation without superseding it, and a later successful generation retires an older incomplete opening. Missing opening IDs fail closed. Native Actions, StatusContext and foreign-app selection retain their existing contracts. The helper never sets `external_id`, preserving the native/API discriminator.

This closes publication ordering after a generation opens. It does not provide atomic arrival-time fencing before the first opening (#1433), optimize fingerprint/read volume (#913), or complete #896's summary ledger and Phase 4b integration. Tests interleave a later opening between an old evaluation and its completion, assert owned-ID-only PATCHes, and exercise duplicate heads, source-revision/head drift and recovery refusal in `tests/test_required_check_generations.py`.

## Verdict mapping and failure directions

Each context's gate maps rc 0 to success, rc 1 to failure and infrastructure/configuration errors to failure. CodeRabbit's rc 3 is an evidence hold rather than a finding count: the publisher now closes its owned generation red with that explanation, allowing a later valid evaluation or explicit narrow recovery to retire it. Other gates' rc 3 remains an infrastructure error. A success missing a required verdict sentinel is a failure.

CodeRabbit evidence recovery follows the [adopted #906 decision](https://github.com/nathanjohnpayne/mergepath/issues/906#issuecomment-6132524365). Unreadable evidence retries for `coderabbit.max_wait_seconds` and any remaining published rate-limit window obtained from the existing read-only waiter probe. Two matching observations confirm persistent unrecognized serialization promptly. Neither state becomes clean because time elapsed. The newest owned generation stores the evidence episode; only an explicit readable evaluator report, retained after the final publication binding fence, ends that episode. Incomplete openings and metadata-free infrastructure/fingerprint-drift failures preserve its first observation and retry deadline. Persistent holds are reported by a separate trusted job with `issues: write` for parser-drift work and `pull-requests: write` for PR-targeted comments. It has no check-writing permission; it posts the exact recovery instructions and idempotently opens parser-drift work for unrecognized serialization.

Parser-drift work-item reuse requires the exact marker prefix on a non-PR issue attributed to `github-actions[bot]`. Unrelated or missing authors cannot capture the evidence update or make one attributed work item ambiguous; multiple matching Actions issues still refuse. Creation and evidence deduplication remain unchanged. This is actor attribution, not trusted-workflow provenance; the existing PR-controlled-workflow residual remains. Native generation tests cover unrelated authors, mixed matches, attributed duplicates and PR markers (#2449).

Each recovery-helper GitHub subprocess, including paginated reads and escalation writes, has a 30-second deadline. A timeout exits3 without a recovery verdict; an uncertain write is not retried. Workflow-level deadlines still bound the aggregate work. This does not change recovery authority, episode timing or readable-blocking precedence.

Escalation isolates expected read, transport, timeout and malformed-evidence failures per nominated PR. It reports each failed PR, continues later targets and returns exit3 if any failed. An unreadable shared source tip remains a global failure. Tuple mismatches retain their existing skip behavior; a malformed or ambiguous record still cannot authorize a write or recovery. Uncertain writes are not retried.

The recovery caller resolves `author_identity` from the exact governing base policy and passes the typed identity and full base SHA to the selector. An absent identity retains the shared-author fallback; malformed explicit values remain unreadable. The identity and policy base join the evidence fingerprint, and the final live binding check refuses a changed base before emitting recovery. An unrelated account cannot release the hold.

A new owner-attributed PR comment must begin with the exact token emitted for this repository, PR, full head, episode ID and evidence fingerprint. It must include one nonempty `Reason: ...` line of at most 4000 characters (the canonical metadata must fit the check summary without truncation) and one `Decision: https://github.com/OWNER/REPO/issues/PR#issuecomment-ID` line linking to that same comment. The comment must be created after the episode began. Duplicate eligible records, old episodes, different evidence/trusted revisions, wrong heads/PRs, observed A-B-A force-push transitions, malformed or unreadable records fail closed. Recovery remains labeled `RECOVERY (not a clean provider review)` with reason and decision link. The recovery comment refreshes the API lineage. If the native CodeRabbit required check is red, rerun that native job/workflow on the exact unchanged full head after API recovery appears, then verify both lineages; API recovery alone cannot retire a native failure. A push invalidates the decision. The native rerun executes the same trusted evaluator and labels recovery in its output. A readable blocking verdict never enters the recovery selector; it supersedes recovery in the next owned generation. Recovery releases only this CodeRabbit gate: CI, feedback accounting, conversations, review clearance, labels and owner-decided model-authoritative Phase 4b stay required.

Attribution to `nathanjohnpayne` is forgeable by agents holding the shared author token. This is the explicit accepted #928/#2129 residual, not independent proof of a human. An infrastructure admin merge is a separate path and is not this recovery mechanism. Consumer remediation still requires reviewed propagation, consumer revision readback and behavior verification; source tests alone do not close the site finding.

Exactly **one** place in the file may assign `conclusion="success"`. Every other failure direction here is an availability cost with a known remedy; an unearned green is the only one that merges something, so the number of code paths able to produce one is pinned at one and any new green-producing path is a conspicuous diff.

Two postures are red-by-construction. A head carried by **more than one open PR** publishes red on all three contexts, once: one commit slot cannot honestly carry two PRs' differing policy state, so red-until-disambiguated is the only verdict wrong for neither. A **superseded head** — an event head matching no open PR — retains any incomplete phase-1 opening, which is invisible to current-head branch protection. It does not authorize an unleased completed POST or a PATCH to an ID this evaluation did not open.

Everything else fails toward *pending*. A stuck pending is an availability cost with a known remedy (the dispatch in seconds, the cron within one interval); a stale green is a correctness hole.

## Coverage and the installation budget

Every gate script call spends the repository's Actions installation budget (`secrets.GITHUB_TOKEN`, 1,000 REST requests per hour), about 30 to 40 gate reads per open PR per pass, plus owned-generation opening and binding reads. Coverage is therefore narrowed in four places, and each narrowing only ever **withholds a write**: a PR a pass does not evaluate keeps whatever verdict its own head already carries, so none of them can produce a green.

**Due-only event passes (#1130).** A pass whose parent is a PR event evaluates its event head, plus every other open PR unless there is positive proof that PR's slot is current: for each of the three contexts the newest Checks-API run (by id; job runs are excluded) is a completed success, completed after the PR's last activity, and younger than `DUE_MAX_AGE_SECONDS`. Holds, reds, missing contexts, missing activity data and failed reads all make a PR due. Schedule-parent passes, dispatches and superseded-head passes keep full coverage. `DUE_MAX_AGE_SECONDS` is the gate parent's sweep interval, 1800 seconds at `*/30`; it was left at 900 when #2167 relaxed the sweep, which made every green PR due again after 15 minutes, and fence assertion A16 now fails when the two differ.

**Budget guard (#2220).** Each pass reads `GET /rate_limit` once with the job token (the endpoint does not count against the limit) and budgets both buckets the gate scripts spend: the REST core bucket at `BUDGET_PER_PR_REQUESTS` (60, including owned-generation binding reads) per PR it would evaluate plus `BUDGET_RESERVE_REQUESTS` (100), and the separate GraphQL bucket (the Codex P1 and CodeRabbit gates paginate review-thread queries) at `BUDGET_PER_PR_GRAPHQL_POINTS` (10) plus `BUDGET_GRAPHQL_RESERVE_POINTS` (50). Each due-proof read the pass issues is charged against the REST snapshot, one request per page fetched (the read's `--jq` emits a page marker per page), so the proof reads cannot consume the reserve unseen. A read that fails partway is charged the pages it already printed plus one for the request that failed (#2229). A pass the budget cannot cover evaluates the heads it claimed with holds — the event head, or the dispatch head — plus a **rotating batch** of the other PRs it would have evaluated, as many as the remaining capacity covers, and skips the rest with a notice. The batch starts at position `tick % n` of the `n` other PRs, where `tick` counts sweep intervals since the epoch, so the start advances by one every interval whatever the capacity: each position is a batch start once every `n` ticks, and each of a stable set of PRs is evaluated within `n` ticks under any positive capacity, even one that changes from tick to tick (#2229). An offset scaled by the batch size would cover PRs faster at a steady capacity, but a capacity that changes between ticks can make it jump over the same position indefinitely. An all-or-nothing rule would never run a full pass once the per-PR estimate plus the reserve exceeds the whole bucket, leaving the scheduled backstop dead. On an event pass the decision is made after the due reads, because only they say which PRs are due; when the budget cannot cover even the head plus one more, the due reads are skipped too. A dispatch claims its named PR only when the budget covers it, so with no capacity it evaluates nothing new and opens no hold it could not close. An unreadable `/rate_limit` or a malformed knob proceeds exactly as before, with a warning (an unreadable GraphQL bucket alone drops only the GraphQL check): the guard fails toward evaluating, never toward silence. When the budget cannot cover even the event head's own evaluation, the pass does not run the gate scripts on it at all, because they would fail partway on the empty bucket and every write after that would fail too. On a gate-parent pass, whose `open` job held the head, it claims the head without new holds and closes each context with the budget red straight away, a few requests out of the reserve. On a `repo-lint`-parent pass there are no holds and nothing the gates read has changed, so it leaves the head exactly as it is. If even those writes fail, the holds stay pending: fail closed, never a green.

**Stop at the first rate-limit failure (#2220).** When a gate script exits with an infrastructure code (not 0 or 1) and its output contains `rate limit exceeded for installation` (REST) or `rate limit already exceeded for installation` (GraphQL), the pass stops evaluating. That context gets the usual infra red; every later PR is left as it was and named in a warning; and a head the pass claimed has its remaining contexts closed with the same red without running their scripts, so no hold is orphaned while the reserve lasts. When the token is empty, those writes fail like every other request, and the holds stay pending until a later pass: the residual is fail-closed. The CodeRabbit summary hold (#886) closes only its own generation red, and the stop still applies after it. The trigger reads gate output, which can quote PR text, so it fires only together with an infrastructure exit; its worst effect is a deferred evaluation, never a green.

**Rate-limit back-off (#2220).** The red written for a rate-limit failure, or for an event head the budget could not cover, is titled `<context> — installation API budget exhausted (rc=N); re-evaluated after <reset>`. The reset is that of the bucket that ran out: on a failure the pass reads it from the `X-RateLimit-Reset` header of one probe on the same bucket, which an exhausted bucket refuses without counting it (#2286: `GET /rate_limit` has read healthy while calls on the same token were refused), and falls back to `/rate_limit`'s empty bucket(s) when the probe is answered or carries no header; on a head it could not cover, the later reset of the short bucket(s). On an event pass, a context whose newest verdict carries that mark is not due before the recorded reset, capped at one hour after the red (and exactly one hour when the title records no reset). Any other context of the same PR that is due still makes the PR due, the PR's own events still evaluate it as the event head, and the first pass after the reset evaluates it with no manual rerun. Ordinary reds, holds and missing contexts are unchanged. The title is written only by trusted default-branch workflow code through `ib_backoff_title` in `scripts/workflow/installation-budget.sh` (this file's `gate()` helper, and since #2286 the event-driven gate workflows below), never by gate output, so the mark cannot be injected through a comment body.

**Event-driven gate workflows (#2286).** The budget reader above lives in `scripts/workflow/installation-budget.sh`, and the event-driven gate workflows read the budget through it before they spend it: the Codex Feedback Archive Relay, the Codex P1 Gate's event job, the CodeRabbit Severity Gate's event job and its `issue_comment` path, the Merge Clearance Gate's event job, and Auto-clear blocking labels' event job. Each budgets one evaluation (its measured cost, in its step env) plus a 200-request, 75-point reserve: the publisher's own floor for one event-head evaluation (60 plus 100) and room for the skip-path writes of the other workflows the same review event starts, so the event workflows stop spending before the publisher has to. A run the budget cannot cover does not evaluate, and never publishes a green:

- On a required context (Codex P1, CodeRabbit, Merge clearance), the event head's Checks-API slot gets this file's back-off red: the run closes the hold it opened (Codex P1, Merge clearance) or posts one completed red (CodeRabbit, which opens none). The publisher closes its own event head the same way when the budget cannot cover it, and the event that started the run may have changed the verdict, so a previous green is not left standing on it. Because the title carries the mark and the reset, the PR is not due before the reset and is due on the first pass after it: any event pass, or the `*/30` chained full pass, re-evaluates it with no manual rerun. The job-native run then concludes non-failing only when `scripts/gate-api-lineage-blocking.sh` confirms the Checks-API lineage blocks the head outside the run's own suite, the #2247 condition; otherwise it fails as before. A failing job-native run would sit in its own suite until someone reran it. A fork or Dependabot clearance run, which holds no Checks-API hold of its own, is never skipped.
- The archive relay skips only a source that cannot need it: a `pull_request*` run whose head repository is this repository, on a branch that is not Dependabot's. Its PR's native gate job owns the check, so the skip writes nothing and leaves nothing to re-evaluate. A fork, Dependabot or `issue_comment` source always runs, because the relay is the only writer of its PR's required context and of the one-shot archive records.
- Auto-clear removes no label and posts no `auto-clear-blocking-labels` run when skipped (an infrastructure-failure run there makes the PR UNSTABLE until healed, #2193); the label stays, and the unguarded `*/5` sweep re-evaluates it.

The first installation rate-limit failure inside one of these runs stops it the same way: the snapshot driver and the gate scripts already stop at their first failed read, the relay stops retrying its binding, and the run's event head gets the same back-off red, its reset read from a refused probe's headers. Auto-clear reads the budget again before every PR a run resolved, stops before the first one the budget cannot cover, and never reclassifies a PR whose evaluation failed: that PR keeps its infrastructure error. A fork or Dependabot CodeRabbit run, whose read-only token could not post the back-off red, is never skipped. An unreadable budget, or a default branch that predates the library, evaluates as before. The scheduled sweeps are not guarded: they are the delivery-independent backstop (#2224).

Together these qualify *Cancellation is coalescing* above: a surviving member subsumes the cancelled ones' work only for PRs it actually evaluates, and a PR skipped by the due proof, the budget guard, a rate-limit stop or the back-off is evaluated by a later pass once the budget recovers: the next schedule-parent pass covers every open PR when the bucket holds them all, and otherwise reaches each of a stable set of `n` rotated PRs within `n` ticks.

## Auto-clear nomination

`auto-clear-blocking-labels.yml` removes `needs-external-review` once the merge gate clears, but it observes no publisher run, so a green `Merge clearance gate` verdict posted here used to reach the label only through that workflow's `*/5` sweep (#2239). A publish pass therefore records every PR whose clearance verdict it **posted green on the live head** (a withheld verdict, a red one and a head-moved red record nothing) and, after its evaluation loop, nominates:

- each such PR that carries `needs-external-review`, read from the fourth column of the open-PR list the pass already fetched, so the nomination itself costs no request; and
- on a full-coverage pass only (schedule-parent, dispatch or superseded-head; never a due-only event pass, and never after a rate-limit stop), each such PR that does not carry it and whose newest `auto-clear-blocking-labels` check-run on that head (by completion time, then id) is a failure. That is a heal that failed after an earlier removal, which no other routine trigger retries (#2205). One read per such PR; an unreadable read nominates nothing and warns.

The step writes the nominated numbers to its `autoclear_prs` output before its final exit, so another PR's infra red does not drop them. A third job, `nominate-auto-clear`, runs only when that output is non-empty and sends one `auto-clear-evaluate` `repository_dispatch` per number, carrying `client_payload.pr` and nothing else. It is a separate job because `POST /dispatches` needs `contents: write`, which the publish job (it runs the gate scripts) must not hold; the job checks out nothing, runs no action, uses the job `GITHUB_TOKEN` (no PAT), and validates each number before sending. A failed dispatch warns: the auto-clear sweep bounds a dropped nomination of a labeled PR, and the next full pass repeats a heal nomination.

The receiving side trusts the payload for the PR number only. Its evaluate-and-clear job resolves a positive-integer `client_payload.pr` (anything else fails that run and evaluates nothing), re-reads the label, re-derives clearance with the same gate and pin-bump lane every other trigger uses, and removes the label only if the head/base pair captured before the gate is still live immediately before the `DELETE`. A label-absent nominated PR goes to the heal step, which posts only when the newest run on the live head is still a failure.

The fence pins the job whole (fence A17): its key set, `needs: publish`, its condition, `permissions: {contents: write}` exactly, one step with only `name`, `env` and `run`, the exact env bindings, the publish job's single output and its step id, and the dispatched event type against the single type the auto-clear workflow listens to. Test 29 in `tests/test_merge_clearance_gate.sh` trips each pin; `tests/test_required_check_publisher_due.sh` case 14 exercises the nomination step and the dispatch loop.

## Staging

Stage A shipped the publisher under **shadow** context names, which were not in branch protection, and rehearsed the trigger shape, head binding, PR resolution and rc mapping against production traffic. Stage B changes exactly the three `env:` values to the live required-context strings while retaining the native producers as independent fallbacks. The structural fence is name-agnostic by construction: it pins the *shape*, so it does not change at the flip; the fixture suite separately pins the current live names so a shadow suffix or other identity drift cannot return unnoticed.

The publisher's introducing PR could not exercise it — a `workflow_run` workflow runs the default branch's definition — which is why the fence, the fixtures and this specification substituted for in-vivo validation on the introducing diff, and why Stage A used shadow names before the live promotion. Stage B still requires its own post-merge observation period before any producer-removal stage.

## Propagation posture

The publisher travels as a manifest `canonical` entry requiring the gate parent workflow and the three gate scripts (the `repo-lint` parent, `.github/workflows/repo_lint.yml`, is itself a `canonical` entry every consumer already carries); the fence travels in the `scripts/ci/` kit and additionally requires the publisher, so a wave cannot ship the fence without its subject. A consumer that has the fence and not yet the workflow is mid-rollout, not broken: the fence SKIPs when its subject and the hub marker are both absent, and fails loudly only when the subject is absent on the hub itself, where that means the single writer was deleted.
