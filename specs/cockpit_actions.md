# Cockpit Actions budget

## Scope and sources

The read-only #1594 provider and four-card presentation reuse the foundation GitHub client, scheduler, six-state components and panel projection seam. `ActionsProvider.fetch(deadline)` returns a strict native JSON `Sample` under `actions-budget/v1`. It never registers its own scheduler or starts a browser network loop. Root wiring registers source `actions` at hot 15 seconds / idle 120 seconds and maps panel `budget` to it; billing reads are internally cached for 1,800 seconds, including denials, within the attempted UTC report month. A month or year rollover forces a new-period read immediately; a denied refresh retains the prior report and its original period identity as stale while the new-period denial remains cached. All fast GETs use the shared client's ETags, pagination, finite page/body/deadline bounds, response-header accounting, local reserve and shared secondary-limit backoff. Rotating repository order and per-repository subdeadlines leave billing a fair remaining slice. A denied repository or billing source remains independently unavailable; other observations survive.

The configured reviewer client received HTTP 404 on the account billing usage endpoint during the prerequisite probe. This establishes unavailability through that client, without proving whether permissions, account access or the endpoint caused it. The endpoint-specific official REST reference documents enhanced billing and fine-grained Plan user read permission; the older reporting tutorial still describes classic tokens. This implementation does not provision credentials, expand scopes or switch identities. Source contract and probe evidence remain in the #1594 dispatch evidence bundle.

Spend reads `/users/{billing_owner}/settings/billing/usage?year=Y&month=M`. Only Actions rows' native finite nonnegative `netAmount` values count; `grossAmount` and CSV `net_amount` are never fallbacks. A bounded `repositoryName` matching the existing owner/repository grammar retains its reported identity; a bare repository name is prefixed only as a compatibility fallback. Reported attribution never changes the configured billing endpoint or repository inventory. Invalid Actions amounts or attribution invalidate the whole observation, avoiding deceptively low partial totals. Decimal accumulation avoids ordinary floating-point summation drift, with a $1 billion data bound. Repository attribution and unattributed net spend remain separate; REST does not provide workflow attribution. Top spenders are reported repositories, with workflow attribution explicitly unavailable. A selected repository has no account budget applied to its share; absent attribution stays unavailable rather than implying zero dollars.

A configured positive budget and explicit current UTC calendar-month start/end boundaries matching the observed API report year/month can supply a usable denominator. The presentation also checks that exact report identity and boundaries before applying current-cycle percentages or projections; a prior-period last-good amount cannot become a current-period value. A projection additionally requires positive elapsed cycle time. Its labelled estimate is net cycle-to-date spend / elapsed cycle time × cycle duration. No default $25 budget, billing cycle, measured coefficient, workflow amount, drain rate or exhaustion ETA comes from the prototype. A missing budget/cycle leaves the projection unknown. Last-good amounts stay visibly stale after read failure. A fresh readable spend source alone does not imply complete panel coverage.

## Run volume, installation and queue evidence

The bounded fallback reads complete paginated queued, in-progress and last-hour run lists for each repository. The launcher injects `ci_observation(envelope, repo, now)` from the registered CI source: `ci/v1`, a coverage window of at least an hour, a fresh successful per-repository observation, and all repository run rows. It deduplicates normalized run IDs across PR associations and causes no polling or on-demand log fetch. An unavailable/stale CI snapshot leaves Actions counts unavailable rather than silently issuing duplicate reads. Queue counts and rolling-hour volume remain independently useful when token estimates are unavailable.

An optional `settings.measurements[repo]` input must carry its exact repository, requests, positive run count, observation window, observed_at and bounded provenance. Native numeric bounds, an at-most-one-day measurement window and an at-most-one-hour age apply. Published provenance trims outer whitespace after validating the original text, preserving control-byte refusal and literal inner content; its limit is 240 Unicode code points in both producer and presentation. The estimate is last-hour run count × measured requests / measured runs, labelled `est.` with provenance; missing/invalid/expired measurements give no estimate. The 1,000 requests per hour per repository denominator is labelled a reference limit, never observed headroom.

The launcher reads the settings file once at startup, and the provider keeps a copied snapshot. To adopt updated measurement or cycle inputs, update the file and restart Cockpit. Restarting alone does not refresh an expired measurement's observation timestamp. Expired measurements and cycle bounds outside the current report month deliberately remain unavailable; automatic settings reload is a separate follow-up (#1784).

A failed recent run's actual bounded `API rate limit exceeded for installation` message, a failed CI check diagnostic bound to that run, or that message emitted in the job log of one of the run's failed jobs, establishes installation exhaustion. A log line counts only as output: the runner's echoed step script (between `##[group]Run` and `##[endgroup]`) and bash xtrace lines (`+ `) are skipped, and the message must sit where an emitted error line puts it: bare, optionally after a runner `##[error]` marker (not `##[warning]`, which can quote it); after `label: ` prefixes whose last one names an error (`gh: `, `Error: `, `RequestError [HttpError]: `, `[tool] ERROR: `, so `note: ` does not count); or as the `"message"` value of a JSON response line, where only labels, an opening brace and other fields may precede it, compact objects included. It must end as GitHub ends it, with a period, `ID`, the end of the line, or the JSON value's closing quote. A step that greps for it, or a line that quotes it, is not evidence (#1842). A gate that exhausts its `GITHUB_TOKEN` usually prints the limit only in its job log (observed on nathanpaynedotcom on 2026-10-07), and the busiest repositories are the ones the CI scan covers least, so the launcher enables an installation scan (`installation_scan=True`) that reads each repository independently of the CI snapshot: at most every 120 seconds it lists the five newest failure-class runs created in the last hour (one bounded list each for `status=failure`, `timed_out` and `action_required`, each reading ten runs, merged newest first, with every run tied at the fifth slot also sampled, #1841; a full list whose last row still sits on that boundary second may hide a tie on its next page, so without a proof that scan is `incomplete`; an `action_required` run resumes in place after approval, so job lists are cached under the run's conclusion and update time and log verdicts under each job's conclusion and completion time, which keeps progress through a held run's jobs and drops it when the run resumes; URL cutoff floored to five minutes so an unchanged list revalidates as a free 304; each run's zoned `created_at` must then fall inside the exact last hour, a run dated ahead of the clock waits until it enters it and leaves the scan `incomplete` because it took a sample slot, and a run without one, or dated more than 60 seconds ahead, fails the scan `invalid_page`), reads every page of the failed jobs of every attempt of each run once (`jobs?filter=all`, since an earlier attempt can hold the limit a rerun hides; at most five pages, and a longer list fails `page_limit` rather than reading as clean), and reads at most three unread failed-job logs per repository per scan, newest run first. The first logged limit settles the scan: an exhausting repository adds fresh failed runs faster than every job could be read (285 in one hour on nathanpaynedotcom), so one proven exhaustion is a complete observation, while a clean answer needs every listed failed job read. A completed attempt's jobs and a completed job's verdict are cached (at most 1,024 entries each). Every failure-class job (`failure`, `timed_out`, `action_required`, `startup_failure`, the CI taxonomy `ci.FAILURES`) is eligible for inspection, within the read window and until a proof settles the scan; a clean answer needs every eligible job read. A job row that is not an object with a positive integer id and one of the finished conclusions in `ci.TERMINAL` fails the scan `invalid_page` rather than dropping out of it. A scan observation counts as a budget observation for coverage even when no CI row has been observed. Each repository row carries `installation_scan` with its last settled observation time, an error (`incomplete` when the read cap left logs unread and none proved exhaustion, or the failed read's category) and the exhausted run ids proven within the last hour, newest first. A settled scan samples only the newest five runs, so it cannot disprove an earlier proof: each proof stands until its run leaves the hour, and proofs outside the exact window, including any dated after a clock that stepped back, are pruned before every refresh, so a failing or incomplete scan cannot keep one. A proof that expires inside the 120-second interval ends the cached answer and the scan runs again. A scan the deadline cut short retries on the next tick instead of waiting the interval, and marks the sample hot so that tick comes on the hot cadence; its job lists and log verdicts are cached, so each attempt advances from where the last stopped. Any rescan inside a 120-second window, a deadline retry or a proof-expiry rescan, continues that window and shares its three log reads. The window runs on the monotonic clock, so a wall-clock step cannot refill it (#1840). A stale CI-only exhaustion keeps the CI observation time even beside a newer clean scan. These stay apart from the CI-derived `installation_runs`, so each ages by its own observation: an incomplete or failed scan keeps the last settled runs, which the page shows as last-known exhaustion with the hazard marked stale once that scan errs, is older than 300 seconds, or arrives in a stale scheduler envelope. A stale envelope never counts as fresh scan coverage. The token card ages with token evidence alone: a last-known token row marks it stale, a fresh scan proof keeps it fresh beside a stale CI row, and CI-row staleness stays on the queue card. An incomplete or failed scan is never clean evidence. This scan is the provider's one read beside the injected snapshot; without the flag the provider makes no run reads of its own. Generic failed conclusions and success messages do not. The run is named; reset stays unknown without observed evidence. Hard signals retained from last-good data remain visible as stale.

Queue ≥10 is a speed bump warning reference, not runner capacity. A queue ≥40 with ≤1 running continuously for strictly more than 30 minutes is a Cockpit jam heuristic and a boulder. Proof requires consecutive comparable successful samples with positive time progression, no gap above the sampling bound, and unchanged repository identity. The bound is 120 seconds for the provider's own fallback reads; for the injected CI snapshot it is the CI source's `OBSERVATION_GAP` (270 seconds, derived from that source's registered cadence), which also bounds that snapshot's freshness, because the CI source renews a repository's observation only that often. Repeated timestamps do not accumulate time; failures, gaps, restarts, time reversal or a below-threshold sample reset continuity. This deliberately uses count/time predicates rather than the generic 70% budget rule. Jam and installation signals have NOW timing; unmeasured queue drain and token exhaustion timing remain unknown. Queue bars scale to the busiest observed repository and distinguish amber queued from blue running.

## Separate robot pool

The foundation reviewer credential is not `nathanpayne-robot`. Without an explicitly injected robot snapshot, the shared CI PAT card and per-repository pool shares remain unavailable. The optional callback must identify `nathanpayne-robot` and supply fresh observed header/rate-limit evidence with an unexpired reset and a valid denominator; arbitrary fields are not published. No reviewer amounts or design limits populate this pool. Primary exhaustion and secondary throttling remain distinct: observed secondary failure carries a boulder even with primary headroom, and expired primary headroom cannot clear that last-observed secondary signal. Per-repository attribution remains unavailable without separate source evidence.

## Projection, layout and motion

`CockpitActions.install(CockpitApp)` registers the pure `project` and persistent `BudgetView` renderer through the foundation seam; root loads the namespace-relative JS/CSS. The projection returns explicit per-card availability/staleness, `hasObservations` and `coverageValid`, preserving partial coverage and preventing a clear aggregate when a required card is unavailable. Only bumps/boulders become owned `budget` Road hazards. Budget projections use the configured cycle end; unknown prediction rates stay unknown. Filtering keeps current and projected account spend hazards, their aggregate danger state and cycle horizon, alongside shared robot hazards, while the selected repository share receives no account budget denominator or projection. Dynamic source data uses textContent and bounded domain schemas; the renderer creates no upstream links, HTML injection, fetch loop or extra SSE connection.

Four cards follow the pinned reference at design commit `4453251f417efd5850e4015a37de01e4287233cb` and the owner runnable export SHA-256 `ed8a20689ee570f773ffcd4873974e59a5504857948d171d5a4804cf268f92e2`: 14px grid gap, 12px/14px card padding, 14px radius, 13px titles, 11px denominators and 18px main amounts. The 460px card breakpoint collapses on narrow screens. Both themes use foundation tokens. Meter fills and queue segments transition for 700ms with cubic-bezier(.2,.8,.2,1), card color/border for 360ms, warning stripes loop every 1s, and shared MeterView applies a 900ms boulder landing only on threshold entry. Spend fill represents current spend while projection timing and worst-card tone remain separate. Persistent row/meter identity prevents repeated snapshots from replaying entry motion. Reduced motion uses the foundation zero-duration tokens plus explicit local loop suppression, retains all values/shapes/labels and responds while open.

## Verification and integration

`tests/test_cockpit_actions.py` covers net/gross separation, malformed billing, denied independent sources, measured provenance/expiry, hard installation messages, comparable jam observations and failures/gaps/repeats, fair deadlines/order, real-client local reserve, pagination/ETag behavior, distinct robot identity/secondary evidence, read-only CI reuse and report-period configuration. `tests/test_cockpit_actions_ui.cjs` covers four-card unknown/partial coverage, threshold predicates and timing, estimates, stale hard signals, primary/secondary separation, explicit projections, missing repository attribution, stale last-good values, filtering/hazard schema, literal DOM text and persistent repeated-update identity. Native server browser fixture and source hash freeze receipts live in the #1594 evidence handoff. Root owns launcher/server/app/index/check and aggregate integration changes; this provider adds no runtime dependency or propagation manifest entry.

The header shows the Actions `GITHUB_TOKEN` chip first, ahead of the connection and API chips, so an exhausted budget is visible without scrolling. It reads only the budget panel's token card: an observed installation exhaustion names the repositories and up to three runs, with reset unknown, whether or not the CI-derived row is fresh; a fresh measured estimate reads "Near the limit" at the speed-bump threshold and "At the limit by estimate" at 1,000, naming the repositories, labelled as an estimate with exhaustion not observed, and without waiting for the log scan; otherwise it reads "No exhaustion seen" only when every repository has a complete installation scan from the last 300 seconds, and "Not fully observed" with the count of scanned repositories. The chip is fleet-wide: a repository filter narrows the panels but never the chip. When every exhausted repository's evidence is last-known, or the local stream is not live, the note says last known, and without a live stream the chip never reads "No exhaustion seen". The display clock re-renders when a settled scan passes 300 seconds, a repository row passes the CI observation gap, or a measured estimate passes its hour, so the chip changes without waiting for another source event. Repository rows count as fresh for the CI source's observation gap (270 seconds, `ci.OBSERVATION_GAP`), because they come from that snapshot.
