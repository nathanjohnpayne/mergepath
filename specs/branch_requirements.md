# Required branch checks

`scripts/lib/branch-requirements.sh` resolves classic protection and applicable repository rulesets into one required-context union. `known` requires both surfaces to be readable and complete; `unknown` is never a known empty list. Existing ruleset bypass completeness, app-pinned ruleset entries, retry bounds and caller fallback behavior remain unchanged.

Classic `refUpdateRule.requiredStatusCheckContexts` is a viewer-scoped projection. An admin bypassing classic protection can receive an empty array even when required checks are configured (#2571). Prefer `ref.branchProtectionRule.requiredStatusCheckContexts`, the configuration listing, whenever its rule object is available. Its complete array must contain only strings; malformed configuration cannot fall back to a potentially incomplete projection.

When that configuration object is unavailable, accept the projection only when the same response proves `isInOrganization: false` and `viewerPermission: WRITE`. This is the ordinary personal-repository collaborator path, with no administrator or organization custom-role bypass. A null projection then means no classic rule. Missing context arrays, malformed arrays, admin projection alone, organization/custom-role ambiguity and other unproved reader cases resolve `unknown`. This bounded proof adds no credentials or privileges. `viewerCanPush: true` alone is not proof: both the bypassing owner and ordinary collaborator can push.

The live reproduction used separate cached author and reviewer tokens against the same personal repository: the admin projection returned `[]` while its configuration listed five contexts; the WRITE collaborator projection listed all five while configuration was null. The native fixture pair covers both paths, configuration preference, genuine empty configuration, missing reader evidence and malformed arrays. Existing union, pagination, retries and fail-closed fixtures remain in `tests/test_branch_requirements.sh`. Classic producer/app pinning remains the separate #1213 policy question.

[GitHub's protected-branch documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) describes the default administrator/custom-role bypass. [Personal repository permissions](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository) describe the owner/collaborator boundary.
