# CodeRabbit Review Sensing

Feature: head-anchored CodeRabbit review sensing. `scripts/coderabbit-wait.sh` (polling mode and the read-only `--probe` mode, #814) classifies CodeRabbit activity on a PR and reports whether the bot has completed a review of the current HEAD; the CodeRabbit arm of the Phase 4b same-head barrier (`p4b_barrier_class_coderabbit` in `scripts/phase-4b/lib.sh`) maps one such result to a barrier class. This spec pins the classification taxonomy, the probe `observed` classes, the exit-code contract, and the barrier's reported conditions, including the #869/#875 corroboration rules.

## Acceptance criteria

### Comment classification taxonomy

- `classify_comment <body> [fresh_at]` emits exactly one of `rate_limit | paused | in_progress | status_probe | review`. Precedence, in evaluation order: the stable rate-limit marker, then the legacy rate-limit prose — BOTH skipped when the corroborated finished-review rule below holds, which is why that rule is decided ahead of either — then the paused marker, then the in-progress marker (#593: markers, never prose, are the primary keys; these two are never bypassed, so a durable pause or a mid-review state carried on the same body still wins), then `review` for a corroborated finished body, then the narration (status-probe) patterns, then the legacy in-progress prose, then `review` as the fallback.
- A comment that is ONLY a fair-use limit notice (carries the rate-limit marker, states no completion) classifies `rate_limit`; the pre-completion "Full review triggered." wording of the actions-performed block also classifies `rate_limit` when the notice is appended. The #714/#489 rate-limit machinery (window parse, retry trigger, Codex failover) keys on this class and must keep receiving it.
- The finished claim is matched as a STANZA, never as two body-wide phrase greps: the generated block is a standalone heading line whose whole content is "Actions performed" plus non-alphanumeric decoration, with the completion statement inside that same stanza — before the next wrapper comment, blockquote, heading, rule, or fence. Phrase greps match any body DISCUSSING the mechanism, including CodeRabbit's own walkthrough of a diff that touches this matcher, and a genuine summary mislabelled as an attestation is SKIPPED by the probe's publication scan — carrying its summary-only blocker past the barrier with it.
- Finished-with-limit-note rule (#869, corroboration-gated per #875): a body whose actions-performed block states the review FINISHED classifies `review` even with the fair-use limit note appended to the same comment — but ONLY when `head_completion_corroborated` accepts it. Uncorroborated, the body takes the class it would have had without the rule (`rate_limit` when the limit marker is present). Even corroborated, the finished reply is TERMINALITY evidence only, never verdict material: the rc-0/rc-2 body is the genuine summary — selected with finished attestations excluded in the probe publication scan, and by summarize-marker identity under a head-anchored at-or-after floor (the newest head-pinned review object's submitted_at when one exists, else the freshness anchor) in the polling arm — so a reply posted or edited after the real summary cannot shadow a blocking marker the summary alone carries, and a prior-head summary inside the wallclock freshness window is never verdict material for the new head. With no genuine summary present, the probe falls through to the awaiting-summary / rc-7 semantics and the polling arm KEEPS POLLING until the summary publishes or the wait budget expires through the ordinary advisory-timeout semantics — neither mode emits a verdict off the reply. Every polling-mode route to a verdict applies that rule, not just the poll arm: the probe-wait timeout boundary, and the StatusContext fast path, which scans inline findings only and would otherwise clear rc 0 on a corroborated attestation before the summary that can carry the sole blocking marker exists.
- Marker identity establishes WHICH comment is the summary, never that its current body is a verdict. CodeRabbit edits the one summarize comment in place, so the same marker rides the mid-review body and every pending state appended to it; the polling selector therefore classifies each candidate and accepts only `review`, excluding a finished attestation for the shadowing reason above. A candidate in any non-`review` class yields no selection, and the caller keeps polling.
- Corroboration requires head-anchored evidence that the claim temporally FOLLOWS, ordered against the comment's `fresh_at` (max of created/updated — the claim's last-stated time; CodeRabbit creates the actions reply at trigger-ack and edits it to finished after the review, so a created_at ordering would reject the genuine completed shape): either the NEWEST CodeRabbit review object pinned to the current HEAD by `commit_id` with the claim at-or-after its `submitted_at`, or — only when NO head object exists and `coderabbit.trust_status_context_for_clearance` is true — a per-SHA CodeRabbit StatusContext `success` with the claim at-or-after its refresh time.
- The reviews lookup inside corroboration keeps three outcomes distinct: a FAILED lookup denies corroboration outright without consulting the status leg; a successful lookup with zero head objects may fall through to the status leg; a successful lookup with an object makes the object ordering authoritative. Every unreadable timestamp or failed read fails closed to the uncorroborated class, never to a clear. An exit-0 API response with a BLANK body is a failed read, not a zero-row page: a REST array endpoint always writes at least `[]`, so the shared array fetchers reject a blank body before normalizing it — otherwise `jq -s 'add // []'` would mint an `[]` no type check can tell from a real one, and the outage would arrive at the caller wearing outcome (b)'s clothes.

### Probe observed classes

- `probe.observed` is one of `none | rate_limit | paused | in_progress | summary-without-head-review | awaiting-summary | terminal`. `none` = no classifiable bot activity for this head; `rate_limit` / `paused` / `in_progress` = the newest non-narration bot comment names that active state; `summary-without-head-review` = the bot has spoken but nothing is pinned to this head (a prior-head summary shape); `awaiting-summary` = a HEAD-pinned review object exists but the PR-level summary publication has not been observed — including when the only post-object comment is a corroborated finished attestation (terminality noted, verdict deferred to the summary or to the barrier's corroborated-status conjuncts); `terminal` = the probe reached a real verdict. Narration replies and finished attestations are never an observed class (#833, #875 round 5).
- On the rc-7 review-object (`awaiting-summary` family) path — and only there — the probe samples the per-SHA StatusContext into `probe.context_state` and `probe.context_updated_at` (trust-gated; null everywhere else) and emits the evidence object's own `review.submitted_at`.
- TOCTOU re-scan (#875 round 4): when that sample reads `success` while the summary is still unseen, the probe re-fetches the issue comments exactly once and re-scans; a summary found on the second pass takes the normal rc-0/rc-2 verdict (with the rc-7-only context fields cleared to null), and only a still-absent summary emits the rc-7 payload. A failed re-fetch is an infra rc 3, never an rc-7 success payload.

### Exit-code contract

- `0` — polling: cleared (review on HEAD, no blocking markers); probe: REPORTED (a HEAD-pinned review object with its summary published, or a head-pinned completed summary with no object, #851) — NOT "no findings".
- `2` — polling: findings (blocking `Potential issue`/warning markers on HEAD); probe: the ONE verdict probe mode makes (#535) — a blocking marker carried solely by the PR-level summary, which no required gate dispositions.
- `3` — API/infra error, including any failed probe read.
- `4` — polling timeout (advisory to callers that treat CodeRabbit as advisory). Never emitted by a probe.
- `5` — rate-limit stalled (retry budget exhausted); non-blocking only when `codex_failover_requested` is true in the JSON.
- `6` — auto-review skipped and not re-invocable (`skip_reason`: `paused` / `non-base-branch` / `draft`).
- `7` — PROBE_NO_REVIEW, `--probe` only: no terminal signal on this head. `probe.observed` names the surface the scan landed on; the JSON may still carry head-anchored evidence (the review object) for the barrier to weigh. Polling mode never exits 7.

### Phase 4b barrier — CodeRabbit arm reported conditions

- rc 0 maps to `reported` only when the result's `head_sha` equals the head under review (#794 stale-clearance posture); rc 2 and rc 3 escalate; rc 4 and every rc 6 skip are `not-yet`; rc 5 is `waived` only when the #489 failover engaged, else escalate.
- rc 7 maps to `reported` only when ALL hold: `head_sha` matches the head under review; `probe.observed` is in the completion family (`awaiting-summary` or `terminal` — an active `rate_limit` / `paused` / `in_progress` observed state, or a missing/unmodelled value, fails closed); the evidence endpoint is `reviews` (a HEAD-pinned review object — `issues` evidence never opens); `probe.context_state` is `success`; and `probe.context_updated_at` is at-or-after `review.submitted_at` (same-run correlation — a success left over from a previous run against the same sha predates the new object and must not open past its pending summary). Any missing field or unparseable timestamp fails closed to `not-yet`.
- The classifier is pure — jq over the passed JSON string only, no I/O — so every condition above is decidable from the probe emission alone.

## Non-goals

- Verdict quality: rc 0 in probe mode asserts a report exists, not that it is clean; inline-finding disposition stays owned by `scripts/coderabbit-severity-gate.sh` and the conversation-resolution gate.
- Closing the disclosed #595 residual: a spurious per-SHA success that lands on the exact head, postdates that head's own review object, and coexists with no adverse pending notice can still open the barrier while the summary is in flight (bounded by the round-4 re-scan); the pre-#869 alternative was a full-budget escalation on every #866-shaped wedge.
