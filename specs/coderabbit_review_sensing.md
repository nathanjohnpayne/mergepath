# CodeRabbit Review Sensing

Feature: corroborated CodeRabbit barrier evidence on the Phase 4b rc-7 path. When `scripts/coderabbit-wait.sh --probe` (#814) finds a HEAD-pinned CodeRabbit review object whose PR-level summary has not published, it returns rc 7 `observed=awaiting-summary` — deliberately not a report, because the summary can carry the ONLY blocking marker (the #535 summary-only class, e.g. the auto-pause note). On #866 that state persisted for hours while the head was in fact fully reviewed (two COMMENTED head objects plus a per-SHA status success), and the barrier held not-yet until it escalated. This spec pins the additive evidence the probe now emits on that one path and the conjuncts under which the CodeRabbit arm of the Phase 4b same-head barrier (`p4b_barrier_class_coderabbit` in `scripts/phase-4b/lib.sh`) counts that state as reported. Comment-classification behavior is unchanged by this feature and is out of its scope.

## Acceptance criteria

### Probe rc-7 evidence contract

- rc 7 (PROBE_NO_REVIEW) is `--probe`-only: no terminal signal on this head; `probe.observed` names the surface the scan landed on (`none | rate_limit | paused | in_progress | summary-without-head-review | awaiting-summary`), and the JSON may still carry head-anchored evidence for the barrier to weigh. Polling mode never exits 7.
- On the rc-7 review-object (`awaiting-summary` family) path — and only there — the probe samples the per-SHA CodeRabbit StatusContext into `probe.context_state` (success|failure|pending|error|missing) and `probe.context_updated_at` (the newest status' refresh time), both null everywhere else, and both gated on `coderabbit.trust_status_context_for_clearance` (null when the policy opts out, which fails closed at the barrier).
- The rc-7 `reviews`-endpoint evidence additionally carries `review.submitted_at` — the evidence object's own timestamp, emitted explicitly for the barrier's temporal comparison.
- The StatusContext is never existence evidence on its own (CodeRabbit can flip a spurious success while rate-limited, #595/#596); its sole probe-mode role is this conjunctive ride-along, seconding a claim the head-pinned review object already made.
- Bounded re-scan (TOCTOU): the issue-comments snapshot predates the status read, so when the sampled status reads `success` while no summary was seen, the probe re-fetches the issue comments exactly once and re-scans — a summary found on the second pass takes the normal rc-0/rc-2 verdict (with the rc-7-only context fields cleared to null, preserving the null-outside-rc-7 contract), a failed re-fetch is infra rc 3 (emitting the success payload after a failed re-fetch would recreate the unscanned-summary hazard), and only a still-absent summary emits the rc-7 evidence; the re-scan reuses the single status sample rather than reading a status surface postdating the one it corroborates.

### Phase 4b barrier — CodeRabbit arm reported conditions

- rc 0 maps to `reported` only when the result's `head_sha` equals the head under review (#794 stale-clearance posture); rc 2 and rc 3 escalate; rc 4 and every rc 6 skip are `not-yet`; rc 5 is `waived` only when the #489 failover engaged, else escalate.
- rc 7 maps to `reported` only when ALL hold: `head_sha` matches the head under review; `probe.observed` is in the completion family (`awaiting-summary` or `terminal` — an active `rate_limit` / `paused` / `in_progress` observed state, or a missing/unmodelled value, fails closed); the evidence endpoint is `reviews` (a HEAD-pinned review object — `issues` evidence never opens); `probe.context_state` is `success`; and `probe.context_updated_at` is at-or-after `review.submitted_at` (same-run correlation — a success left over from a previous run against the same sha predates the new object and must not open past its pending summary). Any missing field or unparseable timestamp fails closed to `not-yet`.
- The classifier is pure — jq over the passed JSON string only, no I/O — so every condition above is decidable from the probe emission alone.

### Required severity gate — PR-level summary surface

Feature (#832): `scripts/coderabbit-severity-gate.sh` is a REQUIRED merge check that read only `pulls/{pr}/comments`, so a blocking finding CodeRabbit carried solely in its PR-level summary — the #535 summary-only class, which has no inline anchor and therefore no review thread — was dispositioned by no gate at all. The gate now also reads `issues/{pr}/comments`. These are the invariants that read must hold; they are stated here rather than only in the script because the advisory waiter (`scripts/coderabbit-wait.sh`) carries a deliberately duplicated copy of the same predicates, and a change to either copy has to be checkable against one contract.

- **Identity.** The normal summary is selected by CodeRabbit's auto-generated summarize marker at BYTE ZERO (`startswith`, not containment — the same predicate the waiter uses at its own selection site), latest by comment id, never as "the newest bot comment". A CodeRabbit chat reply carries no marker of its own but can QUOTE one further down its body, and can embed a pasted 40-hex head sha (#794, #518); such a reply always has the higher comment id, so containment would let it stand in for the summary, be rejected as carrying no stanza, and suppress the real report. CodeRabbit also emits a known markerless full-review format whose first line is exactly `**Actionable comments posted: <decimal>**`, and in production it writes that format in the REVIEW OBJECT body: measured across ten real PRs (#886, #902, #889, #884, #874, #873, #866, #872, #880, #867) the line occurs ZERO times in `issues/{pr}/comments` and SEVENTEEN times in `pulls/{pr}/reviews`. So the PRIMARY acceptor for it is the body of a head-pinned review RUN object, scoped by that object's GitHub-owned `commit_id` and by nothing else — a stronger anchor than the marker-led path can offer, because it travels WITH the report instead of having to be re-stamped onto a comment afterwards. The same first-line shape is still accepted on the PR-comment surface as a secondary acceptor, since that read costs nothing and can only ADD candidates; there it is selected only when a completed CodeRabbit review run anchors the exact head AND the comment is fresh at-or-after that run's `submitted_at` (`max(created_at, updated_at)`), because on that surface the object is what supplies the identity and scope the format omits, so an older markerless body or generic bot chat reply cannot become a report merely because it mentions a head. All three acceptors are evaluated independently and their in-scope findings are combined: a stale marker-led comment must not shadow a current markerless report, or the reverse.
- **Scope.** A marker-led summary comment carries no `commit_id`. Its anchor is the END of the `between <prev> and <head>` commits range CodeRabbit writes into its own body — bot-authored content naming a sha, the same shape as the Codex path's `Reviewed commit:` line. The range START (the force-push shape) does not count. Both range endpoints must be full 40-character object IDs, and the end must equal the API-provided head (case-insensitively); an abbreviated end cannot uniquely identify the current commit and fails closed. The range is read from UNFENCED text only, since a quoted `between X and <head>` string is enough to make a stale summary read as this head's report. A summary carried by a review object is scoped by that object's `commit_id` alone, and TWO acceptors recognise one: the markerless `Actionable comments posted: N` result line, or the object's OWN `📥 Commits` range naming this head (the marker-led predicate applied to the run body, corroborated there by the GitHub-owned `commit_id` — two independent anchors rather than one). Two are needed because one does not cover CodeRabbit's ordinary terminal report: across `pulls/{pr}/reviews` for 20 mergepath PRs, 2 of 22 non-empty bot review bodies (9%) carry no result line at all and open straight into `<details><summary>🧹 Nitpick comments (N)</summary>` (mergepath#880 review 4848342765, mergepath#849 review 4833684457) — complete terminal reports, and on #880's head the only review object there was. A body whose own markup declares the publication a non-review (a non-benign outcome stanza) is not accepted by the commits-range acceptor; the marker format's all-benign test is NOT applied to a run body, which legitimately carries no stanza at all. The same markerless format on the PR-comment surface is scoped by its exact-head review object plus its fresh-at-or-after-review timestamp floor instead. The marker-led commits range is therefore an ACCEPTOR and not a REQUIREMENT: CodeRabbit updates the walkthrough comment IN PLACE and does not reliably re-stamp that range per head, so requiring it made the gate hold forever on a demonstrably terminal review (measured on #886 — review object present, commit StatusContext `CodeRabbit = success`, walkthrough still naming an older head). These predicates are among the few here where precision matters rather than a fail-direction argument — accepting a quoted range treats a stale summary as current, and failing to find the genuine one drops a real report out of scope, and BOTH clear the gate. The marker-led predicate is deliberately NOT narrowed to the `📥 Commits` section: that heading is CodeRabbit presentation which can change without notice, and if it did, every summary would silently fall out of scope. No timestamp, `created_at`, `updated_at`, or freshness floor participates in the marker-led path on the arrival-independent paths: nothing ages out of view, and no pusher-controlled clock can move that boundary. The one exception is the review-triggered publication hold below, where the SHA-only predicate is not sufficient on its own — see **Correlating a same-head re-review**.
- **Completeness.** The commits range describes whatever run last touched the comment, including runs that produced no review. The summary counts as a completed report only when every outcome stanza present is benign, by ALLOW-list (`summarize`, `release notes`) — a stanza kind CodeRabbit has not shipped yet reads as not-a-report, never as clean.
- **One fence reader, CommonMark-correct.** Four scans have to distinguish CodeRabbit's own markup from content CodeRabbit is QUOTING — stanza detection, the pre-merge strip, the commits-range match, and the finding classifier — and each was a demonstrated false verdict when it got that wrong. They share one implementation, because the first attempt carried three copies and they were three different degrees of wrong. Fence recognition follows CommonMark, not a convenient subset: an opener is 3+ backticks or 3+ tildes indented up to 3 spaces, optionally with an info string; a closer must use the same character, be at least as long, and carry nothing but whitespace after it. A backtick-only or fixed-length-3 reader lets a `~~~` or ````` quote walk past every fix built on it.
- **Stanza detection is structural, not substring.** A stanza counts only as a whole line at column 0 in the `<!-- This is an auto-generated comment: KIND by coderabbit.ai -->` form, and only outside a fenced code block; `end of ...` closers are not openers. Counting the bare substring anywhere in the body let PR-CONTROLLED text decide the outcome — CodeRabbit quotes changed code, so a PR that merely contains a rate-limit marker as source text inflated the non-benign count, suppressed its own complete summary, and cleared the gate. Both narrowings can only shrink the non-benign count, which is the safe direction: over-counting fails OPEN (summary skipped, findings ungated), under-counting fails CLOSED (a body that produced no review carries no blocking markers, and the #790 stale-text case gates rather than clears).
- **Classification.** The shared `coderabbit_tier_of` classifies the summary — there is deliberately no second classifier. It is applied per line because the classifier truncates its input to the first 600 chars, which is right for one finding body and wrong for a multi-kilobyte summary; line-wise application is exactly a whole-body scan with the truncation removed. Only UNFENCED lines are classified, with their ORIGINAL line numbers preserved so a reported location still points at the real line. This one errs the other way from the rest: a fenced quote of a classifier marker manufactures a finding and turns the required check red on a PR that merely contains the marker as source text. It is safe to skip fenced lines here because CodeRabbit writes its finding markers as markdown emphasis rendered in PROSE — a finding's code snippet sits inside a fence, but the marker line that classifies never does. CodeRabbit's pre-merge check table is stripped first: its `⚠️ Warning` docstring-coverage row grades PR hygiene, not code. That strip matches its delimiters by the same structural, fence-aware rule as the stanza parser, and the reason is sharper here because the strip DELETES text: a start delimiter quoted by CodeRabbit above the genuine table made the suppressor span from the quote to the real table's end, silently removing every blocking finding in between. Only a start delimiter that has an end delimiter AFTER it strips anything, so a stray one cannot latch the suppressor to EOF.
- **Fail closed on failure, not on absence.** A `issues/{pr}/comments` read that FAILS — transport error, non-2xx, unparseable body — exits 2; it is never degraded into an empty list and read as "no findings". A read that SUCCEEDS and legitimately returns `[]`, or returns comments among which no current summary appears, normally means there is no summary in scope yet, and the gate passes on that surface. That is not a fail-open hole: this gate does not generally enforce review ARRIVAL — that is the advisory waiter's job (`scripts/coderabbit-wait.sh`, and the Phase 4b same-head barrier that consumes it) — and blocking merge on "CodeRabbit has not commented yet" would make every new PR red until a bot got round to it. There is one publication exception, and it has its own exit code: with `REQUIRE_REVIEW_SUMMARY=true`, a completed CodeRabbit review RUN on the current head for which NO acceptor recognises a summary exits **3** — explicitly not 1, because "no readable summary for this run" is not a finding count. The distinction is between a read whose result cannot be trusted, a result that is trustworthy and empty before a review begins, and a run whose report the gate cannot locate after a review has begun. Because the primary acceptors read the summary out of the run object's own body, that last state no longer covers "the walkthrough comment has not caught up" — a run carrying a recognised serialization is a candidate the moment it exists — and what remains under it is a serialization this gate cannot classify. Holding there is correct (a gate that cannot read the review must not certify it) and the held run's object ids are printed so the unrecognised body is identifiable. The claim that this is rare is a claim about ACCEPTOR COVERAGE and is measured, not assumed: the two acceptors between them recognise all 22 non-empty CodeRabbit review bodies across the 20 PRs sampled, while either alone leaves a gap. That is where any future widening belongs — bounding the hold instead would trade an unretirable red for an uncertified pass. Bounding the residual hold is #906 / #896, which own the ordered-publisher work both publishers of this check need.
- **Every publisher of the required check honors the hold, and they answer it differently.** Setting `REQUIRE_REVIEW_SUMMARY` on the `pull_request_review` path alone does not close the gap: the scheduled and `issue_comment` sweep publishes the SAME check name through the Checks API, so a sweep landing inside the window ran the arrival-independent scan and posted success over the review run's red. Both arms therefore set it, and each sets it UNCONDITIONALLY, because the publisher is the JOB and not the event: scoping the event-driven arm's flag to `pull_request_review` left that same job running the arrival-independent scan on its other triggers, so a `pull_request_review_comment` (CodeRabbit's own inline comments fire one each) or a `pull_request` [edited] landing inside the window published a native success over the review run's red — the sweep hole reached through a sibling event. An event allow-list is not the fix and would only have to grow with the next trigger: the flag does not decide a hold, the anchor does, and only a completed CodeRabbit review RUN on the CURRENT head can arm one. A push therefore cannot be held, because its `synchronize` event carries a new head no review has touched. rc 3 then routes by what each arm can actually do. The event-driven job goes non-green: it owns the native check for that head and cannot decline, so declining would leave the previous event's success standing — the very thing being withheld. The sweep DECLINES TO PUBLISH: it is the only arm that can restore this check, and a red it posts here has no acknowledgement channel and no break-glass under `enforce_admins: true`, which is the unretirable-required-check shape mergepath#843 measured. Skipping leaves the event run's verdict standing and self-clears on the next sweep once the summary publishes. The hold therefore withholds a success rather than posting a red of its own — but the event arm's red is real, and nothing retires it while the hold persists, so "can never manufacture a red that nothing retires" is a property of the ACCEPTORS and not of the routing. It holds exactly as far as every terminal CodeRabbit serialization is recognised, and it failed twice while it was assumed rather than measured: a header-less terminal body matched no acceptor (mergepath#880), and a correlation floor taken from any non-empty run rather than from runs carrying a recognised summary discarded the summary that was in hand. Both produced a stable red on an unchanging body, retirable only by a new head — which can land in the same state.
- **Only a review RUN anchors — and carries — a summary.** The correlation floor, and the primary markerless-summary body itself, are taken from head-pinned CodeRabbit review objects with a NON-EMPTY body. CodeRabbit also creates a head-pinned `COMMENTED` review object for a conversational REPLY on a review thread — its answer to a rebuttal, or to the `[mergepath-resolve:<class>]` tag reply `scripts/resolve-pr-threads.sh` posts to clear the pre-merge conversation gate — and a reply starts no run, so no summary ever follows it. Taking the newest head-pinned object outright let a reply landing after the summary push the floor past it, and the genuine current summary was then discarded as uncorrelated: a hold that never clears on a PR whose review demonstrably finished, re-armed by the very replies the review loop requires. The non-empty-body discriminator is the one mergepath#900 measured for the Phase 4b barrier, and it is the same fact here. A `DISMISSED` review still anchors: the question is whether the bot reviewed this head, not whether its review is still standing, and `pull_request_review: [dismissed]` is one of the gate's own triggers — so dropping that state made dismissing the review re-run the gate with its anchor removed, giving dismissal a second job as a bypass of the collaborator ack that is the only documented exit from the summary surface.
- **The sweep's snapshot guard samples every surface the verdict depends on.** It fingerprints all FOUR of them before and after the gate runs: the PR-comment surface (`issues/{pr}/comments`, the summary), the review-object surface (`pulls/{pr}/reviews`), the inline-finding surface (`pulls/{pr}/comments`), and thread resolution state (GraphQL `reviewThreads`, sampled as `id:isResolved` — the only thing that surface contributes, since the finding bodies are already covered by the inline part). Review objects became an input when the sweep opted into the publication hold: a review submitted between the gate's `pulls/{pr}/reviews` read and the Checks API POST leaves a comment-only fingerprint byte-identical, so a comments-only guard published a success computed before that review existed, over the `pull_request_review` job's hold. The inline pair is the gate's ORIGINAL input and had the same hole one level down — a thread resolved, or a finding posted, edited, or deleted, inside that window republishes a stale success over a now-unresolved blocking finding until the next sweep. A surface the verdict depends on and the guard does not sample is not guarded. Any read failing fails the whole fingerprint — a half-read surface must never become one, since it would compare equal to another run's half-read and read as "unchanged", which is the guard disabling itself. **The gate's own fail-closed exit outranks both guards.** rc 2 publishes a failure and must reach the check even when the guard cannot compare, because the two failures are correlated rather than independent: the fingerprint and the gate read the same `issues/{pr}/comments` endpoint, so an unreadable endpoint trips the guard and exits the gate 2 in the same breath, and a guard ordered first swallowed the fail-closed verdict and left whatever check_run was already on the head — a SUCCESS recorded before an acknowledgement was edited away, which is the hole the rc 2 rule exists to close, reopened through the guard in the common case rather than a rare one. It is safe past a guard that cannot compare precisely because rc 2 is not a verdict read off a stale surface but "this run could not read", and the failure it posts is retired by the next sweep the moment the read succeeds. rc 3 stays inside the guarded path for the opposite reason — it must never mint a red no arm can retire.
- **Correlating a same-head re-review.** "No correlated summary yet" above cannot be decided by the SHA-only scope predicate alone. CodeRabbit re-reviews the SAME head on demand (`@coderabbitai full review`, the mergepath#898 recovery), and the previous publication's marker-led summary keeps naming that head in its commits range, so it stays in scope and the publication hold never fires — letting the review-triggered run publish success off the old, possibly clean, summary during the window before the replacement lands. On the `REQUIRE_REVIEW_SUMMARY=true` path only, a candidate must therefore also be fresh at-or-after the `submitted_at` of the newest run that CARRIES A RECOGNISED SUMMARY — never of any non-empty run. The distinction is the difference between a hold and a verdict: a run this gate cannot read is not a publication a candidate can be late for, and taking the floor from one discarded every earlier candidate including the review-object body whose own `submitted_at` set it, so a head carrying a readable summary with a Major in it reported neither the Major nor a success. The floor and the hold's arming condition are deliberately different values: the hold asks whether CodeRabbit ran on this head at all, the floor asks which publication a candidate belongs to. A candidate must be fresh at-or-after that floor (the same `max(created_at, updated_at)` floor the markerless format already carries); one that predates it belongs to the previous publication and is dropped. The verdict then comes from the newest run's OWN summary body rather than from the dropped one — the hold is reached only if no acceptor recognises that run's summary either. This does not reintroduce a spoofable clock: both timestamps are GitHub-assigned on CodeRabbit-authored objects, neither is writable by the pusher, and an absent or unparseable one sorts below every real one and is dropped. The restriction to the review-triggered path is load-bearing in the other direction — on the arrival-independent sweep, zero candidates PASSES, so applying the same floor there would discard a real blocking summary finding and fail open.
- **Resolution channel.** A summary finding has no thread, so "Resolve conversation" does not exist for it. A fixed finding clears itself on the next push. A rebuttal or deferral is recorded by a PR comment whose FIRST LINE is exactly `[mergepath-summary-ack: <head sha> <finding-set fingerprint>]`, from a non-`[bot]` account whose GitHub-computed `author_association` is OWNER / MEMBER / COLLABORATOR. Without this channel a false positive would deadlock the PR permanently, since `enforce_admins: true` leaves no break-glass.
- **The ack is pinned to the head AND to the finding set.** Head-pinning alone binds an ack to a commit, but the summary can change without the head changing: a same-head re-review (`@coderabbitai review` / `resume`, or the rate-limit retry the waiter posts itself) rewrites it, in place or as a later comment. The fingerprint is a truncated SHA-256 of the WHOLE classified body, not of the marker-bearing lines: CodeRabbit writes the `⚠️ Potential issue` marker on its own line with the finding underneath, so hashing classified lines alone hashed a constant and one finding's ack cleared its replacement. Content fingerprinting rather than comment-id ordering is what survives an in-place edit, which leaves the id untouched. With neither `sha256sum` nor `shasum` on PATH the gate exits 2 rather than falling back to head-only pinning. The fingerprint is additionally SALTED with the resolved `required` tier set: that set comes from the trusted default-branch policy and can tighten while a PR is open, and a body carrying both P1 and P2 text hashes identically under `{p1}` and `{p1,p2}`, so without the salt an ack written when only the P1 blocked would clear a P2 that a later policy made blocking.
- **An ack carries its rationale.** The acknowledging comment must have at least one non-blank line after the token. The check is mechanical rather than a judgement about substance — a merge gate should not be grading prose — but without it a bare copied token cleared a required check with no recorded disposition at all, leaving the documented contract and the enforced one in disagreement.
- **The gate re-runs when the PR-level comment surface changes.** `.github/workflows/coderabbit-severity-gate.yml` listens to `issue_comment` (created / edited / deleted) as well as the `pull_request*` events, because a summary-only finding — and the ack that clears one — lands on a surface no `pull_request*` event covers. That trigger routes to the SWEEP job, not the event-driven one: Actions attaches a check to a PR's head SHA only for `pull_request*` events, so an `issue_comment` run of the event-driven job would never update the required check, while the sweep already posts a check_run on the head SHA through the Checks API. Scoped to the single commented PR, and guarded on `github.event.issue.pull_request` so plain issues are a no-op. Because same-name check runs supersede one another, an older concurrent run finishing last could republish a stale SUCCESS over a newer correct FAILURE; the sweep therefore fingerprints the PR-comment surface before and after the gate runs and skips its publication if that surface moved, letting the newer run's verdict stand. The fingerprint covers each comment's BODY, not just `id:updated_at`: GitHub reports that timestamp at second resolution, so a comment edited twice within one second changes the verdict while identity metadata stays byte-identical. A failed read preserves its nonzero status; either unreadable snapshot skips publication and leaves a fresh event or scheduled sweep to retry. That compare-and-swap is deliberately NOT a `concurrency:` block: mergepath#843 established that `concurrency` on a job publishing a required check cancels the PENDING member even with `cancel-in-progress: false`, leaving a `cancelled` check that blocks merge permanently and cannot be retired — an unfixable deadlock traded for a transient window, under `enforce_admins: true`.
- **The ack is anchored, not substring-matched.** The token must BE the comment's first line, with no leading whitespace, after stripping CR and trailing whitespace. The gate prints the token INDENTED in its own failure output, so a verbatim paste of any contiguous region of that output cannot ack — an invariant, not a likelihood, and asserted directly by the suite so unindenting it fails the tests.

## Non-goals

- Verdict quality: rc 0 in probe mode asserts a report exists, not that it is clean; finding disposition stays owned by `scripts/coderabbit-severity-gate.sh` and the conversation-resolution gate. That gate now covers both the inline and PR-level-summary surfaces (see above); the barrier feature this spec opens with does not.
- Comment classification: how CodeRabbit comment bodies (including the finished-with-limit-note actions reply observed on #866) are classified is unchanged here and deferred to the dedicated classification-redesign issue, which will key on CodeRabbit machine markers rather than prose.
- Closing the disclosed #595 residual: a spurious per-SHA success that lands on the exact head, postdates that head's own review object, and coexists with no adverse pending notice can still open the barrier while the summary is in flight; the pre-#869 alternative was a full-budget escalation on every #866-shaped wedge.
