# Cockpit CI observations

`mergepath/cockpit/ci.py` owns the read-only `ci/v1` provider. `CIProvider(client, inventory)` is a scheduler callback returning `Sample`; it uses the existing shared client and deadline. Register source `ci` once, with 20-second hot and 120-second idle cadence, and bind the fixed CI panel before scheduler start. Complete bounded REST pagination covers open pulls, Actions runs in an explicit default three-hour rolling recent window plus all queued/in_progress/waiting/pending/requested runs regardless of age, and detail for the runs that can inform a verdict: live runs, failed runs (failure, timed_out, action_required, startup_failure) and runs whose SHA is an open-PR HEAD. Detail means every job across attempts (`filter=all`) for those runs plus the latest check-runs (`filter=latest`) for every open-PR HEAD and only those SHAs. Scheduled sweeps attach check-runs to SHAs for days: one open head carried 567 check-runs (54 with `filter=latest`) and one mergepath default-branch SHA carried 2,052 even with `filter=latest`, past the page bound and the deadline, so check-runs on SHAs that are not open HEADs are never read and a failed run there keeps `check_evidence_unknown`. Under the latest filter, a failed run whose job check-runs are absent from the list while a later check-run of the same name exists for that SHA is superseded history (not actionable, `superseded: true`, no check evidence) because the later run carries the verdict; absence without a same-name successor remains `check_evidence_unknown`. A row repeated across page edges while a list grows is deduplicated by id, first observation first, instead of failing the repository. The window cutoff is floored to the hour so the list URL stays stable within the hour and unchanged pages revalidate as free 304s; the effective window is therefore recent_seconds to recent_seconds plus one hour. A completed success on any other SHA is history: it keeps its workflow result with `jobs_scope: not-fetched`, empty jobs and no check rows, and the browser says so instead of reporting missing jobs. GitHub paginates these repository endpoints through its numeric `/repositories/<id>/` alias; the shared client follows that alias without ever requesting it (see the foundation spec). At observed fleet volume (about 9,000 runs a day across eight repositories) detailing every run exceeded the scan deadline on every repository while spending the reviewer budget, which is why detail is scoped. The payload names recent_seconds; this is recent history, never all history. Completed jobs are cached by repository/run/attempt in at most 1,024 entries; active jobs and same-SHA checks refresh each scan. Each repository scan is atomic: reaching a page bound or encountering a denied/malformed/deadline response retains that repository's last-good runs/groups and original observed_at, with stale/error/attempted_at/retry_at metadata. A never-observed repository retains no invented rows or age. Successful repositories remain usable. Per-repository failures use bounded exponential retry delay, preserving shared provider Retry-After/backoff. The projection conservatively downgrades the selected coverage to stale if any selected repository is stale or missing; the shared registry must OR this downgrade with scheduler staleness, never permit a freshness upgrade. No partial scan establishes absence or clearance. Each callback reserves 250 ms of the source deadline for publication and rotates repository priority. Once the request budget is spent, it starts no additional scan and marks untouched coverage unavailable/stale for the next fair attempt; deadline exhaustion does not delay those untouched repositories behind a per-repository error backoff. This publication margin is operational slack, not an absolute CPU-time guarantee for arbitrary ordinary JSON trees. Unexpected whole-callback failures still retain the scheduler sample.

Rows group by enrolled repository, PR number (or null when unattached) and exact SHA. Current HEAD is determined from the separately observed open pull, never from the old run's pull-request metadata. Workflow ownership includes every separately observed open PR whose HEAD matches the run SHA, even when workflow pull-request metadata is empty or omits that PR; historical metadata associations remain visible. Multiple PR rows retain the same actual workflow ID rather than inventing extra runs. Missing or closed PR HEAD evidence remains unknown. Successful workflow history with an old or unknown HEAD remains visible as idle history; only independently observed current-HEAD success can establish clearance. Unmatched check-runs on SHAs within detail scope (open HEADs and the SHAs of live or unclean runs), including other-app checks and checks on an open HEAD with no Actions run, remain in the separate `check_rows` collection as explicit SHA-level `kind: checks` rows; `runs` remains actual Actions workflow observations for existing consumers. They retain check IDs, app/workflow producer evidence, individual timestamps and diagnostic provenance; their Actions run/attempt/workflow IDs and aggregate run timestamps are null, jobs are empty with `jobs_scope: none`, and rerun_command is null. Their keys include repository, SHA and PR identity. A separately observed open HEAD with no workflow or check observations retains an explicit unknown `kind: checks` coverage row: checks and jobs are empty, status is unknown, conclusion and Actions identities/timestamps/rerun are null, and visible copy states that no workflow or check runs were observed. This marker adds no Actions run or check-run count, failure, log control or hazard; it prevents missing current evidence from establishing clearance. Open pull HEADs establish current ownership; observed run groups retain old-HEAD history. Existing workflow rows keep only their job-linked checks, avoiding duplicated check hazards. Groups retain workflow `run_keys` and list unmatched-check `check_keys` separately. Both kinds use the same supersession and diagnostic rules; unknown current ownership cannot establish clearance. Check-only disclosure displays observed check names/statuses/producers/durations without offering Actions step logs or reruns. Each run names its latest run attempt and explicitly labels jobs_scope as all-attempts, or not-fetched for a completed success off every open HEAD; each job retains its observed run_attempt or null/unknown instead of pretending every job belongs to the latest attempt. The panel names the configured recent_seconds window in visible copy. Each run retains jobs and every observed step, including `check_*`, with status, conclusion and timestamps; no suite-count parsing is performed. Opaque API IDs, PR numbers and step identities are canonical positive decimal strings even beyond JavaScript's safe integer range. Unknown timestamps remain null. Names are capped at 1,000 Unicode code points and check-output diagnostics at 4,000; browser validation counts the same units as the Python producer. A job check-run URL must retain the exact HTTPS API authority, endpoint structure and canonical check ID. Only its owner/repository path, within the existing ASCII inventory grammar, compares case-insensitively with the enrolled repository; the payload keeps the inventory spelling.

A failed check is superseded only by a successful check with matching repository, SHA, name and known producer identity, whose observed start is later. Actions producer identity includes its app ID and workflow ID; supersession additionally requires a proven common `workflow_run_id` from the existing check-suite mapping. The producer string retains its established UI schema; a passing independent run cannot clear a failure even if workflow and triggering event match. An ambiguous suite-to-run mapping or missing run lineage preserves every observation. Genuine retries within the same run may supersede earlier attempts under the existing later-start requirement; another workflow with the same job name cannot clear it. Other apps use their app ID. Missing producer or ordering evidence never proves supersession. Failed history remains visible with superseded and old-HEAD labels. A check aggregate retains its queued/running tone while any independent check is live, even when all historical failures in that aggregate have been superseded; individual check supersession evidence remains visible. Unsuperseded failed current-HEAD checks are actionable speed bumps. A run whose failure cannot be tied to check evidence remains visibly failed with unavailable current-check evidence; it cannot establish a clear claim. An observed cancellation on selected current-HEAD workflow or check evidence prevents an otherwise clear panel from claiming clearance. Applicable non-live, unsuperseded current rows with stale or unknown conclusions or unknown status likewise cannot establish success; eligible terminal observations require completed status. It adds no hazard and does not override running, bump or boulder tones. Historical cancellations do not poison current success; existing neutral/skipped idle-row semantics remain. Queue age is information only. The exact `gh run rerun <id> --failed --repo <repo>` is display text, never executed.

Observed bounded check output diagnostics have check-run provenance. The specific installation-rate-limit message establishes token exhaustion without fabricating remaining/reset/secondary-pool evidence. Explicit CodeQL diagnostic text stating a not-retryable failure establishes that condition; workflow names and generic finalize errors do not. These observations may contribute boulders only for unsuperseded current-HEAD failed checks. FAIL extraction is separately sourced from job logs and does not reinterpret diagnostics as log lines.

`LogExcerptCache` is the on-demand seam. Trusted construction injects `read_log(repo, job_id, deadline)` through the shared read transport, never an alternate credential/subprocess/transport. The authenticated scoped GET route `api/ci/excerpt` accepts exactly repo, run, attempt, job and step. Each input must match the current observed CI envelope and a failed step in an enrolled repository; no URL or command is accepted. A stale envelope refuses new fetches explicitly. The documented step-log endpoint returned 404 in root's authenticated probe; no speculative index retry is made. Cache identity includes repo, run, attempt and job; selected-step time-window extraction uses timestamped job lines when both observed step boundaries are available. Repeated requests coalesce behind one bounded job read, cache complete log bytes (including empty logs), deterministic permission denials and oversized-body refusals for 120 seconds in at most 32 jobs, and share a maximum of two active reads with no executor queue. Requests already waiting on a pending job read receive that completed read's result, including a transient failure, under their own deadlines. This result remains only with those pending participants, not in the durable TTL cache; a subsequent explicit request can retry without following another waiter into a new read. Transient failures, including deadline exhaustion before a read starts, are returned without caching; an explicit retry can read again while still honoring the shared client's backoff and transport fence. Deadline exhaustion remains unavailable. Body cap is 2 MiB at the shared reader and extraction seam; extracted output retains the newest tail in chronological order, at most 80 FAIL lines, each at most 1,000 Unicode code points, and 32 KiB total. When step timestamps are absent, a FAIL line is untimed, a FAIL timestamp lies anywhere in the second containing an integral observed start boundary, or a fractional FAIL timestamp falls in the remainder of the second containing the observed completion boundary, extraction falls back to the labelled whole-job tail. Numeric integral starts cannot distinguish truncated REST precision from a true zero fraction; a preceding step may have failed earlier in that same second. A nonintegral observed start retains the precise comparison and excludes failures before that known boundary. Second-resolution REST metadata cannot distinguish that failure from an adjacent step; no widened window is presented as selected-step evidence. C0 control bytes other than tab and supported CSI/OSC escape sequences are removed; OSC supports BEL and ESC-backslash terminators. Additional DCS/PM/APC terminal-string families are tracked separately in [#1769](https://github.com/nathanjohnpayne/mergepath/issues/1769); this seam does not promise terminal emulation. Display remains literal textContent and upstream conclusions remain the source of failure state. Empty, denied, unavailable and stale outcomes are distinct. Callback exceptions publish finite existing error categories only.

`assets/ci.js` projects the single shared SSE snapshot and registers `ci`; it adds no polling or EventSource. It preserves one expanded run, stable nodes and keyboard focus across updates. Runs that need attention (live, actionable, failed, on an open HEAD, or check-only rows) stay in the main list; every other completed run sits behind a counted history disclosure ("N completed runs off open heads · show"), collapsed by default and scrolling past 560px, so sweep-heavy repositories do not bury the operator's runs; a run moves between the lists without losing its node or disclosure state. Browser excerpt requests resolve relative to the authenticated namespace and abort/discard obsolete responses. Themes and glyphs reuse shared tokens; running pips blink at the reference's cadence, tone/detail changes use 360 ms, and normal entry uses the shared ease. Manual/OS reduction removes movement, stagger and loops with readable resting frames, including preference changes while open. Reference mock queue thresholds and generic CodeQL-finalize claims are superseded by the settled acceptance contracts.

Tests: `tests/test_cockpit_ci.py` covers provider, grouping, supersession and bounded on-demand reads; `tests/test_cockpit_ci_ui.cjs` covers projection and DOM/disclosure/request behavior. Its producer fixtures are materialized in one bounded Python subprocess and each case receives a fresh nested clone. Root integrates these suites into the hub-only Cockpit check/test wrappers and spec mapping. The provider, assets, tests and spec remain hub-only. Authenticated actual-server visual/motion evidence is recorded externally; unit tests alone do not complete browser acceptance.
