# Stalled pull-request finder and resume entry point (#2165)

The largest share of pull-request wall-clock in the fleet is time when nothing is waiting on a machine: a reviewer verdict lands outside working hours and no session is alive to act on it. Two scripts in the `scripts/workflow/` kit close that gap from the tooling side; the end-of-session rule in `docs/agents/shared-operating-rules.md` closes it from the behavior side.

## Finder: `scripts/workflow/stalled-prs.sh`

Read-only. Lists the open, non-draft pull requests of one repository (`--repo`, default the current repo) and classifies each by whose turn it is and how long nothing has happened. The only GitHub calls are paginated REST GETs (open PRs, each PR's reviews, issue comments, inline comments and head check runs, and the head commit date only as a fallback) and one read-only GraphQL scalar (the head's `statusCheckRollup.state`). It never comments, labels, requests or merges.

Evidence rules: the head's push time is server-generated, never the commit's own committer date (author-controlled metadata: a future-dated commit would read as perpetually live and a cherry-picked old one as instantly stale). In order: the repository activity API's push entry for the head SHA; else the earliest check-run start on the head; else the pull request's server-set `updated_at`, a value stable across runs and never earlier than the push. The source is reported as `head_pushed_at_source` (`push-activity`, `check-run`, `pr-updated-at`). Codex evidence (review objects, inline findings, verdict and Review Summary comments) is restricted to the Codex bot login; a CodeRabbit or code-scanning review on the head is a verdict, never a Codex signal. A posted handoff stays in force until an author-side event or a verdict lands after it; bot activity after it (a summary edit, an acknowledgement) does not clear it. A `CHANGES_REQUESTED` review counts only when it is anchored to the head commit or submitted after the head was pushed. A body-less `COMMENTED` review from a bot is the wrapper GitHub emits around a bot's inline reply (a CodeRabbit resolve acknowledgement) and is bot activity, never a verdict. Any non-bot reply on a finding thread answers it, since fix and rebuttal replies are posted under a registered reviewer identity rather than the author login, but only a reply posted after the finding was last edited or re-raised (the inline comment's `updated_at`). A provider rate-limit notice that outlives the threshold with no failover request is `rate-limit-stale` and routes to `investigate` (the provider wait requests the sanctioned Codex failover itself), never to an automatic Codex request.

Classes, one per PR:

- `stalled` — an agent must act and nothing has happened for at least the threshold (`--threshold-minutes`, default 60). Reasons: `unanswered-verdict` (the newest event is a bot review, a bot verdict comment, a reviewer-identity review or comment, or a human reply, with nothing after it); `head-unrequested` (the newest event is author-side, the head is CI-complete, and no review was requested and no Codex signal exists on it); `idle` (author activity after the verdict, then nothing); `request-unanswered`, `rate-limit-stale` and `ci-pending-stale` (a machine wait outlived the threshold).
- `live` — an agent must act and the newest event is younger than the threshold.
- `waiting-on-ci` — the newest event is author-side and the head's check rollup is `PENDING`.
- `waiting-on-bot` — a review request (`@codex review` / `@coderabbitai …` in any markup) is newer than the head with no verdict after it, Codex's Review Summary reports the head `Running`, or the newest event is bot activity that is not a verdict (a rate-limit notice, a resolve acknowledgement).
- `waiting-on-human` — a fork PR or one not authored by the configured author identity (`author_identity` in `.github/review-policy.yml`, default `nathanjohnpayne`), since an agent cannot push to a contributor's branch; a `human-hold`, `needs-human-review` or `policy-violation` label; or a handoff comment (`[mergepath-handoff]`, `<!-- mergepath-handback:`, or the `## External Review Required` heading) that no author-side event or verdict has superseded. Never picked up by the resume entry point.

Next action, reported for every PR, in this precedence: `push fix` (CI red on the head — checked before any re-request — the latest head-scoped verdict requested changes, or findings on the head with no agent reply), `request codex` (a request outlived the threshold unanswered, or no Codex signal on the head and CI green or absent — a `NONE` rollup in a repository with no checks), `merge` (the repository's own complete policy agrees: the newest `Merge clearance gate` check run on the head is `success`, or that check does not exist in the repository and `scripts/codex-review-check.sh` exits 0 on the head; a passing Phase 4 gate with a failed clearance check is `investigate`), `investigate` (the gate's one-line reason, or a stale CI wait), `wait` (a machine or a human acts next). The gate runs only for stalled PRs on an agent's turn, under a bounded timeout, and only in live runs; `--no-gate` skips it.

Verdict bodies are read with U+00A0 normalized to a space, because Codex posts NBSP inside `Reviewed commit:` lines. Draft PRs are excluded. The report is sorted stalled-first, oldest newest-event first. `--json` emits `stalled-prs-report/v1`; the human table prints one line per PR. `--dump FILE` writes the `stalled-prs/v1` snapshot after the gate stage, and `--input FILE` classifies a snapshot without any network call, which is how the suite builds its fixtures. `--now` pins the clock.

Exit codes: 0 nothing stalled; 1 at least one stalled PR; 2 usage; 3 a read failed (nothing is decided — a failed list is a status, never an empty report).

## Resume: `scripts/workflow/resume-stalled-pr.sh`

Runs the finder, selects the stalled PR whose newest event is oldest (or `--pr N`, which must still be stalled), and prints a work order: PR, head, reason, next action, the worktree checkout under the hidden per-repo folder, and the exact commands the review policy prescribes for that action. Every PR-controlled value in a printed command (the head ref, the repository slug) is shell-escaped, and the PR title is printed with control characters replaced. Fork PRs never reach the work order (the finder routes them to `waiting-on-human`), so the head branch is always on `origin`. The `merge` work order lists the complete pre-merge sequence (feedback accounting, the thread gate, the Phase 4b classifier, the Phase 4 gate, the clearance check state) before the author merge line. The calling session executes the round per `AGENTS.md` § Workflow Summary.

Under `--execute` it performs exactly one action itself: `request codex`, through `scripts/codex-review-request.sh --trigger-only` with `MERGEPATH_PHASE_4A_GATED=true`, which posts through the author wrapper and is idempotent on an existing head trigger. `push fix` needs code and `merge` needs the accounting and thread gates plus the author identity, so both stay with the session; the script never merges. `--execute` is refused on a replayed `--input` snapshot.

Exit codes: 0 a stalled PR was selected (and the executed step, if any, succeeded); 1 nothing to resume; 2 usage; 3 the finder could not read the repository or the requester hit an infrastructure error; 4 the Codex request was refused by policy, a routing outcome rather than a failure. On 4 the requester's exit 6 maps to `next: disposition findings`, its exit 7 with `cap_exhausted.kind: request-ceiling` to `next: phase 4b` (run `scripts/phase-4b-review.sh` from a trusted main checkout) and with `blocking-reviews` (or an unknown kind) to `next: human tiebreaker`; the line is printed and, under `--json`, emitted as an `execute` record. A routine acts on that line instead of retrying, because the requester keeps refusing.

## Scheduled routine

The routine itself is configured outside the repository. From a checkout at the default branch, with a read-only token for the finder and the author credential the request wrapper resolves, it runs `scripts/workflow/resume-stalled-pr.sh --repo <owner/repo> --execute` and then continues the printed work order; `docs/agents/operating-rules.md` § Session finalization carries the operator detail.

## Coverage

`tests/test_stalled_pr_resume.sh` replays a fixture snapshot through `--input` for every class and reason above, the next-action derivation and its precedence, head-scoped change requests, handoff persistence across bot activity, Codex-only head evidence, the merge-gate condition, NBSP tolerance, markup-tolerant trigger matching, draft exclusion, ordering, shell-escaped and fork work orders, and the exit-code contracts of both scripts; then runs the live fetch against a PATH-shimmed `gh` with stub gate and requester scripts to assert pagination on every list read, the push-activity, check-run and `updated_at` push-time sources (the commit date is never read), the requester exit-code mapping, gate delegation once per stalled agent-turn PR, `--dump`/`--input` round-tripping, the `--execute` hand-off shape, and that an unreadable PR list exits 3 with nothing on stdout. `scripts/ci/check_stalled_pr_resume` wires it into `repo_lint.yml`.
