# Merge-group required-workflow authorization

## Purpose

GitHub's native merge queue is the #1058 base-freshness mechanism. It integrates the reviewed pull-request head with the latest target branch on a synthetic `merge_group` ref, without rewriting the pull-request head, and removes an entry when required checks fail, time out, or the integration conflicts.

An ordinary workflow stored in the target repository and triggered by `merge_group` is not the authority for this boundary. Its trigger and executable definition live inside the repository whose future changes it is meant to judge, so it cannot anchor its own trust transition. The target repository must contain zero `merge_group` triggers. The two queue-required workflows come instead from a separately protected organization-owned public policy repository and are attached to the target by an organization-level required-workflow ruleset. A separate repository-level ruleset supplies the native merge-queue rule because GitHub does not offer merge-queue rules in organization rulesets.

This design replaces the direct-merge, update-branch, target-local merge-group, and queue-controller prototypes. Mergepath never updates the PR branch, calls a direct merge endpoint, dequeues an entry, disables non-Dependabot native auto-merge, or retries an ambiguous merge mutation.

## Trust split

The boundary has four distinct surfaces.

- The target repository's `merge-queue-authorization.yml` is a trusted `pull_request_target` observer for `auto_merge_enabled` and `enqueued`. It checks out the event's exact target-base SHA with persisted credentials disabled. On `auto_merge_enabled`, it validates the live governing-author action and may write one hidden author-attributed marker for the event's exact PR head. On `enqueued`, it re-reads the exact live entry, queue action, active rulesets, protected environment, complete secret inventories, source workflows, and branch protection before writing one author-attributed entry attestation bound to the immutable queue-entry id, head, base, enqueue event, action event, queue, merge method, rollout ids, source pin, and topology fingerprint. It never changes PR, queue, or merge state, and it is one of exactly two #1058 components that receives `AUTHOR_MERGE_TOKEN` comment-write authority.
- The organization policy repository materializes `.github/workflows/mergepath-merge-queue-authorization.yml`. An organization-level required-workflow ruleset pins that source repository's numeric id, exact workflow path, protected source ref, and full source commit SHA. Its pull-request admission job jointly proves that the target's effective active rules contain the pinned organization workflow rule and the separate repository singleton merge-queue rule. Its merge-group path has read-only precheck and postcheck jobs that execute the exact target event base around one intervening source-pinned handshake job. Only that handshake job receives job-scoped `contents: write`, fetches and executes the exact `job.workflow_sha` policy source without credentials, sends one same-repository `repository_dispatch`, and never checks out or executes target-base code. The policy-source repository must therefore be organization-owned and public for every target-repository visibility.
- The target repository's `merge-queue-final-audit.yml` is the protected `repository_dispatch` responder and the second #1058 author-token writer. Exact job-level repository, actor, action, `main` ref, event-base SHA, workflow-ref, and workflow-SHA guards run before the `merge-queue-policy` environment makes its three secrets available. The job then checks out that exact authenticated target base, re-reads the private topology, source workflows, action, queue, PR, group, and rollout state, and may write one unique author-attributed final-audit marker bound to the request nonce and both workflow runs. It never changes PR, queue, merge, or protection state.
- The same policy repository materializes `.github/workflows/mergepath-repo-lint.yml` at the same protected source ref and full SHA. The organization rule requires it alongside authorization so both the pull-request head and synthetic merge-group SHA receive the target's canonical lint decision without adding a target-local `merge_group` trigger.

The required-workflow jobs validate their runtime `job.workflow_repository`, `job.workflow_file_path`, `job.workflow_ref`, and `job.workflow_sha` before trusting their own result. The target-base precheck and postcheck use read-only `github.token`; the handshake's sole elevation is job-scoped `contents: write`, required for the one same-repository dispatch. That write-capable job executes only the exact SHA-pinned public policy source fetched without credentials, while the read-only jobs execute only the exact target event base, never the candidate merge-group tree. The effective organization rule independently binds the configured numeric source-repository id, and preactivation administrator proof binds that id to the runtime public organization-owned source and safe source metadata. Candidate pull-request code is never executed with any of the three queue credentials and candidate-controlled workflows reference none of their secret names. The trusted `pull_request_target`, `workflow_run`, scheduled, and `repository_dispatch` jobs that need these credentials all bind the protected `merge-queue-policy` environment before a secret expression is evaluated.

`MERGE_QUEUE_POLICY_TOKEN` is a distinct preactivation-and-runtime credential for administrator topology and armed-state proofs. It must be an author-owned fine-grained PAT restricted to the selected target repository, with organization `Administration: write`, target-repository `Administration: write`, and target-repository `Actions: read`, `Secrets: read`, `Environments: read`, `Contents: read`, `Issues: read`, `Pull requests: read`, plus the fine-grained token's automatic `Metadata: read`. Both write permissions are unavoidable read-evidence scopes: GitHub withholds `bypass_actors` from the exact organization and repository ruleset detail endpoints without the corresponding ruleset write access. The additional read scopes expose the repository, inherited-organization, and environment Actions-secret inventories plus the exact environment and custom-branch policy used by the topology proof. Every #1058 use of this token is read-only through REST `GET` requests or fixed GraphQL queries; no #1058 path may call a ruleset, environment, secret, repository, or GraphQL mutation with it.

`MERGE_QUEUE_SOURCE_TOKEN` is a separate author-owned fine-grained PAT restricted to the selected public policy-source repository with only `Actions: read` and automatic `Metadata: read`. It proves the two source workflow identities and their `disabled_manually` state without broadening the topology token to the source repository. Both read tokens are runtime requirements for every live `enqueued` observer attestation and every final administrative audit, not rollout-only credentials. `AUTHOR_MERGE_TOKEN`, `MERGE_QUEUE_POLICY_TOKEN`, and `MERGE_QUEUE_SOURCE_TOKEN` are pairwise distinct and exist only as Actions secrets in the protected target environment named `merge-queue-policy`; none may exist at repository or organization secret scope. That environment disallows administrator bypass, has no required reviewers or wait timer, and permits exactly one custom deployment branch named `main`. Its secret inventory contains exactly those three names. Rollout reads the complete repository, inherited-organization, and environment secret inventories, probes both read-token identities, and stops unless placement, identity, and environment policy match exactly. `AUTHOR_MERGE_TOKEN` is not widened to carry either proof; for #1058 it remains only the trusted observer's marker/attestation and protected final auditor's nonce-bound marker credential, and it remains the separately governed Dependabot merge credential from that same protected environment.

## Root and transitive executable trust

The immutable organization required-workflow pin is the root of trust. The read-only group precheck and postcheck intentionally execute policy helpers from the exact target event base so they evaluate the policy that will govern that base rather than a stale copy embedded elsewhere. The intervening write-authority handshake instead fetches the organization-owned public policy repository without credentials, proves the exact `job.workflow_sha` checkout and executable blob, and runs only that source-pinned code. The protected target final auditor is guarded to the exact live `main` base and workflow definition before environment secrets are available.

That target-base executable trust is transitive, not self-asserted. Before first activation, the owner exact-byte audits the implementation on the manually merged disabled base against the materialized policy-repository workflows. After activation, every target base that can supply a later bridge was itself admitted by the previously pinned required-workflow bridge. A PR that changes the bridge is therefore judged by the prior bridge, and its new implementation becomes executable only after that judgment and merge. Changing the organization workflow source id, path, ref, or full SHA is a new root-of-trust rollout and cannot be authorized merely by target-repository content.

## Exact-head authorization

A direct, already-ready queue action is authorized by the unique ordered `AddedToMergeQueueEvent`, the live singleton entry, its exact `headCommit`, `enqueuedAt`, queue id, and governing actor/enqueuer. The trusted `pull_request_target: enqueued` observer then writes the separate post-enqueue administrative attestation; the external merge-group workflow never treats the public queue event alone as proof of the private no-bypass, environment, secret-placement, source-workflow, or branch-protection state.

A deferred native auto-merge request needs more evidence because GitHub may preserve it across a later push by a writer. The observer's `auto_merge_enabled` path reads the live GraphQL `autoMergeRequest`, records the event payload's exact head and base, the governing enabler, the native merge method, and the selected enable-event id in an author-attributed marker. GitHub represents the three methods as `AutoMergeEnabledEvent`, `AutoSquashEnabledEvent`, and `AutoRebaseEnabledEvent`; the policy normalizes all three and also observes `AutoMergeDisabledEvent`. The bridge resolves the latest native arm state before the selected queue-add event. When no arm event exists or that latest state is disabled, a fresh governing-author `AddedToMergeQueueEvent` may use direct authorization. When the latest state is enabled, the bridge requires the current entry head to equal the exact marker head, the marker method to equal the queue method, and the marker's source event to equal that latest enable event.

Label and arm ordering comes from one complete filtered GraphQL timeline connection, not second-precision timestamps. Completeness is established through cursor exhaustion and unique node ids; GitHub's `timelineItems.totalCount` describes the unfiltered timeline and is not compared with the filtered node count. Pull-request commit, head force-push, head deletion, and head restoration items make head history monotonic: moving from A to B and force-pushing back to A cannot resurrect A's old marker. Any intervening or later head change, blocking label, rearm, disable, or distinct queue-add event invalidates the selected action, even if the current SHA or label set later returns to its prior value. A changed head therefore needs a fresh owner action and marker.

An historic enable followed by a later disable does not force marker authorization forever; the later disabled state permits a fresh direct governing-author queue action. A preactivation arm that remains the latest state must be replaced by a fresh owner action after activation, and missing or delayed marker delivery for a latest-enabled state fails closed. The merge-group leg bounded-polls for the post-enqueue attestation because the trusted `enqueued` observer and the external group workflow start independently; every retry rechecks the immutable entry, group ref, and blocking-label state, and exhaustion fails closed. Legacy quarantine rejects a `mergepath-armed-base-freshness/v1` artifact only when it decodes as a valid governing-author intent bound to the same repository, PR, head, and base. A malformed, foreign, or different-head/base legacy marker is not adopted, but it also does not brick a fresh head.

## Two rulesets and admission

The first rollout permits only a singleton queue and group. Two rulesets jointly form the boundary on literal `refs/heads/main`. The repository-level ruleset is `ACTIVE`, is sourced from the target repository, targets only `refs/heads/main`, has zero bypass actors, and contains exactly one `merge_queue` rule. That queue rule is `ALLGREEN`, with build, group, and merge maxima/minima fixed to one. The organization-level ruleset is separately `ACTIVE`, is sourced from the owning organization, targets only the separately recorded numeric target repository id and `refs/heads/main`, has zero bypass actors, and contains exactly one `workflows` rule. Its `do_not_enforce_on_create` value is `false`, and it names exactly the two policy-repository workflows; each entry binds the separately recorded source repository id, exact path, protected ref, and full source SHA. Neither ruleset may contain an extra rule.

Administrator topology and activation proofs under `MERGE_QUEUE_POLICY_TOKEN` read both exact detail endpoints: `GET /repos/{owner}/{repo}/rulesets/{repository_ruleset_id}` and `GET /orgs/{org}/rulesets/{workflow_ruleset_id}`. Each response must carry a present, array-valued, empty `bypass_actors`; the repository response must prove its exact target source, `refs/heads/main` condition, `ACTIVE` enforcement, and singleton queue rule, while the organization response must prove its exact organization source, target repository id, `refs/heads/main` condition, `ACTIVE` enforcement, and two pinned workflows. The same topology read proves `merge-queue-policy` has administrator bypass disabled, exactly one branch-policy protection rule, no reviewers or wait timer, custom-branch mode, and exactly one branch policy for literal `main`; proves all three queue secret names absent from complete repository and inherited-organization inventories; and proves the environment inventory contains exactly those three pairwise-distinct credentials. It also proves classic branch protection requires exactly `Label Gate`, `Self-Review Required`, `CodeRabbit unresolved blocking findings`, `Codex P1 unresolved threads`, `Merge clearance gate`, and `lint`, with strict status freshness, every check pinned to the GitHub Actions app, administrator enforcement, stale-review dismissal, no user/team/app pull-request-review bypass, and conversation resolution. The arm-policy proof requires both authorities before an armed state can be queue-proven. The pull-request leg reads target metadata with the target's read-only `github.token`, validates the immutable runtime workflow name/path/ref/SHA, and reads the target's effective active rules; it performs no cross-repository source REST read. It jointly requires one effective `merge_queue` rule sourced from the configured repository ruleset id/source and one effective `workflows` rule sourced from the configured organization ruleset id/source, with the singleton `ALLGREEN` parameters and exactly the two workflows pinned by source id, path, protected ref, and full SHA. The effective-rules response is corroboration of joint enforcement, not a substitute for either exact ruleset-detail proof. A same-named check, inactive or evaluate-only rule, target-local workflow, shortened SHA, different source repository, extra workflow, extra queue rule, or different effective ruleset source/id is not admission authority.

While rollout is `canary` or `enabled`, the pull-request leg also rejects every delta under `.github/workflows/**` before queue admission. Its authority is an immutable Git tree comparison between the exact event base and head commits in the trusted checkout; the head object must resolve to that exact SHA, and any unavailable object or comparison error fails closed. This catches additions, edits, deletions, and renames into or out of the directory without trusting a mutable paginated API read. The complete paginated file inventory still checks both each destination `filename` and a rename's `previous_filename` as defense in depth, bracketed by stable PR snapshots, but an A-to-B-to-A force push around that pagination cannot change the immutable decision. This freeze is required because a target workflow introduced or changed to consume `merge_group` could receive secrets and begin executing before the trusted external group gate rejects the synthetic group. A later fail-closed authorization result cannot undo that earlier exposure.

The pull-request leg treats draft state as admission-neutral because GitHub's organization-required workflow ignores activity-type filters and does not create a new run for `ready_for_review`; draft exclusion remains mandatory at queue-entry and merge-group time. Admission rejects a head branch whose name resembles a full Git object id, because GitHub suppresses `pull_request_target` for that branch class and the trusted observer could not produce its marker or attestation. Admission also reads GraphQL `PullRequest.stack` and rejects every stack member before queueing. The merge-group leg independently rejects drafts and stacks, so admission mistakes cannot authorize either state.

The policy stores the target repository id and required-workflow source repository id separately. A repository rename therefore does not silently retarget either side, and a source repository cannot satisfy the target identity by name collision.

## Merge-group binding and policy replay

The merge-group precheck and postcheck jobs each check out the exact target `merge_group.base_sha` with persisted credentials disabled and use read-only `github.token`. Each validates the runtime `job.workflow_ref` and `job.workflow_sha` against the organization rule, maps the synthetic group to exactly one live native queue entry, and requires all of the following:

- The target is organization-owned, its default branch is literal `main`, and the live default-branch SHA equals the event base.
- The complete queue contains exactly one standalone, non-stack entry with `jump == false`; its id, queue, state, enqueue time, base commit, head commit, PR id/number, PR creation time, PR author, and enqueuer are stable, and its exact post-enqueue administrative attestation is present.
- The PR is open, same-repository, non-draft, on `main`, authored by the governing author, and has the exact entry head.
- The event ref names that PR under `refs/heads/gh-readonly-queue/main/pr-<number>-...`, and the live ref still points to the event head SHA.
- The authorization base, when present, is an ancestor of the entry base; the entry base is an ancestor of the event base; and the target default branch remains at the event base throughout evaluation.
- The effective active rules still jointly match the configured repository queue-ruleset source/id, organization workflow-ruleset source/id, singleton `ALLGREEN` parameters, and two pinned workflow entries proved on the PR leg, while the live queue matches those parameters and remains stable. Exact target conditions and each ruleset's no-bypass state come from the separate administrator topology/activation and arm-policy proofs; they are not inferred from the effective-rules response.

GitHub does not expose the queue-entry id in the `merge_group` event. The singleton queue, PR-number ref, live ref SHA, exact queue entry, post-enqueue attestation, and base ancestry form the fail-closed mapping. A rebuilt group with different content has a different event SHA and cannot reuse the prior check result. The group waits only within a bounded poll for the independently delivered attestation; it revalidates the entry, group ref, and blockers between polls and fails when the bound expires.

The bridge reads complete paginated labels, issue comments, review comments, reviews, and review threads through the target base's existing policy helpers. It re-evaluates the PR body and Self-Review contract, all blocking labels, complete review-feedback accounting, zero unresolved conversations, CodeRabbit blocking findings, Codex required-tier findings, the merge-clearance gate pinned to the PR head/event base, and approval independence.

The read-only precheck evaluates every public predicate, re-reads the queue, effective active rules, runtime workflow identity, PR, authorization, target base, and group-ref binding, then repeats the complete predicate set and a handoff fence. Only after that succeeds may the source-pinned handshake generate a cryptographically random 64-hex nonce and issue exactly one same-repository `repository_dispatch` whose request fields are nested under `client_payload.request`. The handshake does not retry a failed or ambiguous dispatch; it continues polling only for the unique exact response to that same nonce and requester run, then reports outcome-unknown if none arrives within the queue timeout.

The protected target auditor accepts only a dispatch whose actor and triggering run resolve to `github-actions[bot]` for the exact target repository. Its job-level guards require the exact dispatch type, literal `main` ref, live base SHA, target workflow ref, and target workflow SHA before `merge-queue-policy` can expose secrets. It then checks out that exact authenticated base, verifies all three environment-only credentials are nonempty, governing-author owned, and pairwise value-distinct, and re-reads the complete private ruleset, branch-protection, environment, secret-placement, policy-source, PR, queue, action, and group topology before and after its sole author-attributed comment write. The unique marker binds the nonce, requester run and attempt, source workflow identity, exact PR/head/base/group/entry/action, normalized topology fingerprint, and auditor run and attempt.

The handshake accepts neither a marker alone nor an older successful run. It requires exactly one marker in the nonce/requester namespace and an exact target auditor run whose repository, `repository_dispatch` event, `main` branch, base head, workflow path, actors, attempt, creation/start times, and successful conclusion bind it between request and marker. After its final marker and auditor-run rereads succeed, the handshake exposes only two non-secret outputs: the exact GitHub comment id and SHA-256 of the canonical decoded marker, including GitHub-authenticated comment metadata. The nonce and request timestamp never cross the job-output boundary. Before evaluating a public predicate, the read-only postcheck requires both outputs, reloads the one marker for the requester run, matches its exact id and canonical digest, privately extracts and validates its nonce and request time, rechecks namespace uniqueness and the exact successful auditor run, and completes an initial full binding fence. It then replays the entire public predicate set and performs the same final full binding read. Deletion, editing, duplicate insertion, comment replacement, or auditor-run drift fails closed at either fence.

These checks narrow but cannot eliminate GitHub's unavoidable interval between the final required-check read and native merge. From the final-audit handoff through native merge, the operator must freeze every mutable governing input: repository and organization rulesets, branch protection, environment policy and all three secret inventories, target and policy-source workflows and source pin, rollout policy, PR state/body/head/base, labels, reviews, comments, review threads, feedback accounting, checks and statuses, queue entry/action/configuration, default-branch SHA, and merge-group ref/SHA. Any mutation ejects or aborts the entry and requires a fresh governing-owner action and fresh merge group; no prior marker, auditor run, or successful required check may be reused.

## Rollout state machine

The target's trusted `.github/review-policy.yml` owns rollout state. Missing keys mean `disabled`; consumer policy files are not propagated, so every consumer remains dark until separately configured.

`disabled` requires zero/empty canary and promotion selectors, an empty activation timestamp, and empty repository-ruleset, organization-ruleset, and source identity fields. The target observer skips cleanly and both required-workflow legs fail closed.

`canary` requires an activation timestamp, one exact canary PR/head pair, a distinct predeclared transition PR number, both ruleset ids, the numeric target repository id, and the required-workflow source repository name/id/ref/full SHA. The transition head clears all selectors into exactly `enabled` while retaining the activation timestamp, or exactly `disabled` while clearing both ruleset bindings, the source bindings, and the timestamp. An enabled transition is rejected until the configured canary PR and exact head are merged into the event base; a disabled rollback transition deliberately has no such prerequisite. The transition head is not embedded in the canary base because that would make the transition commit depend on a base commit containing its own hash. The later human action and, for deferred auto-merge, its marker bind the transition's live exact head.

`enabled` requires empty selectors, retains both audited ruleset identities, the source identity, and the activation timestamp, and permits governing-author PRs created at or after the activation epoch. Any invalid combination is an infrastructure error, never an implicit enable.

## Armed-state cleanup

GitHub exposes no compare-and-swap precondition for disabling native auto-merge. No non-Dependabot cleanup path therefore calls native disable. An exact queue-proven arm is preserved; every other armed state, including a disabled rollout, future rollout, malformed policy, missing helper or credential, stale target base, ineligible scope, blocker, unreadable rule/queue state, or newer action, remains untouched and returns nonzero for explicit human/admin disposition. An unarmed state continues normally, and the exact `dependabot[bot]` login remains under its dedicated workflow.

This removes the read-then-disable race in which an old run could revoke a newer owner action. The required-workflow result and native queue ejection carry the fail-closed decision once rollout is active. Neither automation nor rollback treats uncertainty as permission to mutate an arm.

## Rollback

An owner can stop a queued item immediately with a blocking label. Removing either active rule while a deferred arm exists is unsafe because it can remove the boundary that must judge that action. The durable rollback uses the predeclared transition PR to change the target policy to exact `disabled` while both rulesets remain `ACTIVE`. After that transition merges, the owner disables native auto-merge, drains the queue, and verifies that the queue is empty and no PR has a live arm. Only then may the repository queue ruleset be deactivated or removed. ## Workflow maintenance

No target `.github/workflows/**` maintenance enters the active queue, including a rename whose source path was in that directory. To change a target workflow, first merge the predeclared `disabled` transition through both still-active rulesets. Then disable native auto-merge, prove the queue is empty with no live arms, remove the active repository queue rule, and only then remove the active organization workflow rule before using the ordinary fully reviewed manual author lane for the workflow change. Before reactivation, prove that the target again contains zero `merge_group` triggers, repeat the exact-byte and two-ruleset topology audit, create both exact rulesets in `evaluate`, merge a new future-dated canary policy manually, activate and verify the organization workflow rule first and the repository queue rule second, reopen or synchronize both canary and transition PRs for fresh required-workflow runs, and complete a fresh owner-driven canary. An agent never uses workflow maintenance as authority to merge, arm, or enqueue.
